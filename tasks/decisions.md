### T-250 · DD: представление коллекций — персистентные структуры
<!-- meta
priority: P0

- **Файлы:** `docs/01-language-design.md` §4.2–§4.6 (сложность операций), §15.1; `internal/runtime/value.go`; T-104 (#173)
- **Тест-якорь:** — (решение); пробы X-1, `make bench-scaling` (T-247)
- **Вопрос:** `List`, `Vector`, `Map`, `Set` — срезы Go; `[x, ..acc]`, `Map.put`, `Vec.push` копируют всё. 8 000 элементов — 4–7 с, 16 000 — 28–61 с. Какое представление коллекций принять и мигрировать ли вместе с `Value` (T-104)?
- **Варианты:**
  - **A.** Персистентные структуры: `List` — неизменяемый односвязный список (или чанки с общим хвостом), `[x, ..xs]` и `[h, ..t]` — O(1); `Vector` — 32-арный trie (§4.4 это уже обещает); `Map`/`Set` — HAMT, `put`/`get`/`remove` — O(log₃₂ n). Спека получает таблицу сложности. Миграция одна, вместе с T-104 вариант B (tagged `Value`). Цена: 3 large-задачи (T-271…T-273) + docs T-270 + миграция T-104; ~140 обращений к `.List`/`.Map`/`.Vector`/`.Set` в 30+ файлах. Сломается: ничего в языке; риск регрессий равенства, term order, `KeyEqual` — ловят `runtime`-тесты и fuzz.
  - **B.** Только `List`: O(1) prepend (список «в обратном порядке» с общим хвостом), `Map`/`Vector` — как сейчас, сложность O(n) записана в спеке. Цена: 1 medium-задача. Сломается: §4.4 (trie) — правка спеки; стейт-мапы акторов остаются квадратичными.
  - **C.** Ничего: записать O(n) в спеку, в гайде — «строить через `map`/`fold`/`list`». Цена: docs. Сломается: §4.4; библиотеки с мапами в стейте — невозможны.
- **Рекомендация аудита:** A, порядок `List` → `Map`/`Set` → `Vector`; T-104 решить как B в том же DD.
- **DoD:** вариант записан комментарием в issue (для T-104 — тоже); судьба T-270…T-273 (делается / won't-fix / объём) записана; issue закрыт.
- **НЕ делать:** писать код; менять API коллекций; решать модель heap (research 11).

- **Тест-якорь:** — (решение); проба X-3: после `exit(sup, :kill)` дети живы
- **Вопрос:** `link` ≡ `watch` без ref, `spawn_linked` ≡ `spawn_watched` без ref. Механизма «ребёнок умирает с родителем» нет: убитый супервизор оставляет поддерево. Что должен значить `link`?
- **Варианты:**
  - **A.** Однонаправленная связь владелец → ребёнок: смерть владельца по любой причине — `exit(child, (:linked_exit, reason))` (§12.7: не `raise`, `trap` не ловит, `ensure` выполняются). Наблюдение — только `watch`/`spawn_watched`. `link(pid)` — владельцем становится вызывающий. Цена: T-275 (medium, `scheduler.go`, §12.2, §12.7). Сломается: тесты VM, где `spawn_linked`-ребёнок переживает родителя; `stdlib/supervisor.brig` начинает работать правильно без правки.
  - **B.** Удалить `link` и `spawn_linked` (§0.2: дубли `watch`); сирот лечит `Supervisor` — каждый ребёнок сам следит за супервизором. Цена: medium (спека, stdlib, тесты); дети обязаны знать протокол супервизора.
  - **C.** Ничего; сироты — известное ограничение §13.1.
- **Рекомендация аудита:** A: §16 запрещает эскалацию **ошибок**, а `exit` — не ошибка; дерево супервизии чистится само.
- **DoD:** вариант записан (с формой причины); судьба T-275 записана; issue закрыт.
- **НЕ делать:** писать код; вводить `trap_exit`; менять `watch`.

- **Тест-якорь:** — (решение); проба k3: `else if` → `expected NEWLINE after else, got if`
- **Вопрос:** многоветочное условие пишется только вложенными `if` (+1 отступ на ветку) или вспомогательной `fn` с guard'ами: guard'ов в `match` нет (§8.3). Вводить ли `else if`?
- **Варианты:**

  - **B.** Guard'ы в ветках `match` (`pattern when cond ->`). Цена: medium (парсер, компилятор, §8.3). Сломается: §8.3 и §6.1 («не разрешён в `match`»).
  - **C.** Ничего.
- **Рекомендация аудита:** A (§0.2 не нарушается: одна форма в AST, как `if`-сахар над `match`).
- **DoD:** вариант записан; судьба T-263 записана; issue закрыт.
- **НЕ делать:** писать код; вводить `elif`/`cond`; менять однострочный `if`.

### T-256 · DD: JSON — маппинг и форма ошибок
<!-- meta
priority: P2
type: design-decision
effort: low
model: human
wave: 17
depends_on: —
findings: G-24, S-21 (AUDIT_REPORT-3)
extra_labels: design-decision

- **Файлы:** `docs/01-language-design.md` (новый подраздел JSON, §10.4, N10); `internal/runtime/json.go`
- **Тест-якорь:** — (решение); пробы G-24
- **Вопрос:** `Json.encode`/`Json.decode` не описаны в спеке. Сейчас `decode` возвращает `Error(Str)` с текстом терма, `encode` бросает `(:json_encode_error, Str)`, `None` → `null`, но `null` → `()`, `Ok(2)` → `2`. Какой маппинг и какие ошибки?
- **Варианты:**
  - **A.** `Json.decode(s) -> Result<V, (:json, reason)>`, `reason` — атом или кортеж (`:syntax`, `(:number, s)`, `:depth_limit`, `:trailing_data`, `:invalid_utf8`); `null` ↔ `None` в обе стороны, `Some(v)` ↔ `v`; `Ok`/`Error`, `Pid`, `Ref`, функции в `encode` — `raise((:json, (:unsupported, v)))`; объект → `Map` со `Str`-ключами; записи — по полям; таблица маппинга в спеке. Цена: T-266 (medium). Сломается: код, читающий `null` как `()` (`corpus/`, `examples/json.brig` — проверить в T-266).
  - **B.** Маппинг как сейчас (`null` → `()`), только структурные ошибки. Цена: low. Сломается: ничего; `encode ∘ decode` для `None` не тождественно.
