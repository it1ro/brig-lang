Да, это может быть не просто фича, а **архитектурный инвариант**, и именно в таком виде он превращается в киллер-фичу. Причём для Brig он ложится почти идеально: рантайм на Go, ставка на edge/event-driven/отказоустойчивость, иммутабельность и акторы. Один статический бинарник без внешних зависимостей — это ровно то, чего не хватает Elixir/Erlang (нужна VM, OTP, релизы), Python/Node (нужны рантаймы и пакеты) и даже Go (там один бинарник — норма, но нет акторов и иммутабельности).

## Почему это киллер-фича

- **Zero-install**: скачал один файл — запустил REPL, скрипт, сервис.
- **Edge / IoT / air-gapped**: копируешь бинарник на устройство, и всё работает без пакетов, зависимостей и сети.
- **Docker scratch**: образ = один бинарник. Минимальный размер, максимальная безопасность.
- **CI/CD**: не нужно ставить тулчейн, менеджер пакетов, рантайм. `brig test` из одного файла.
- **Воспроизводимость**: версия языка, stdlib и зависимостей зашиты в бинарник.
- **Обучение**: студент скачал один файл и уже пишет акторы.
- **`brig build app.brig -o app`**: можно сделать так, чтобы `brig` дописывал байткод в копию себя и на выходе получался **single-file executable приложения**. Это уже уровень Deno/Bun, но с акторами и иммутабельностью.

## Что должно быть в одном бинарнике

Фактически это не «интерпретатор», а **весь тулчейн**:

- байткод-компилятор;
- регистровая VM;
- stdlib (Brig-модули + нативные встройки);
- REPL;
- debugger / profiler / tracer;
- formatter;
- test runner;
- package manager (build-time);
- документация;
- LSP-режим;
- `--dump-bytecode`.

Подкоманды как у `go`: `brig run`, `brig repl`, `brig build`, `brig test`, `brig fmt`, `brig doc`, `brig lsp`.

## Как этого добиться технически

1. **Ядро — чистый Go, `CGO_ENABLED=0`.**
   Статическая линковка, кросс-компиляция, никаких системных `.so`.

2. **`go:embed` для stdlib.**
   Исходники и/или предкомпилированный байткод stdlib вшиваются в бинарник. Никаких внешних файлов.

3. **Нативные встройки — в Go.**
   `map`, `filter`, `fold`, `len`, `Map.get`, `Vec.set`, I/O, акторы — регистрируются в VM как встроенные функции. Не требуют динамической загрузки.

4. **Пакетный менеджер — build-time.**
   Зависимости резолвятся и вендорятся в бинарник при сборке. Никакого runtime-fetch. Lock-файл фиксирует версии.

5. **Wasm-плагины через pure Go (wazero).**
   Это ключ к расширяемости без нарушения single-binary. Wasm-модули загружаются в песочницу, а wazero — pure Go, без CGO. Более того, wazero умеет JIT для Wasm на amd64/arm64, тоже pure Go. То есть можно компилировать горячие функции Brig в Wasm и исполнять их JIT, **не ломая один бинарник**.

6. **`brig build` как self-extracting.**
   Бинарник `brig` при запуске проверяет, есть ли в конце файла appended payload (байткод + манифест). Если есть — исполняет его. `brig build` создаёт копию себя с этим payload. Получается single-file app.

## Что придётся урезать или сделать опциональным

- **C-ABI FFI / динамическая загрузка `.so`** — только в «extended» сборке с CGO. Это ломает pure static и кросс-компиляцию. В core — нет.
- **Runtime hot reload** — в проде не нужен; в dev-режиме можно читать Brig-модули с диска. Но single-binary инвариант для продакшена сохраняется.
- **JIT через LLVM** — не в core. Wasm + wazero даёт JIT без CGO.
- **Пакетный менеджер, тянущий пакеты в рантайме** — нет. Только build-time vendoring.
- **Обновления stdlib без замены бинарника** — нет. Обновление = замена бинарника. Для edge это нормально.

## Killer-сценарии

- **Edge-шлюз**: один файл `brig` на устройстве, акторы, супервизоры, backpressure, офлайн.
- **CLI-утилита**: `brig build tool.brig -o tool`, один файл, без зависимостей.
- **Air-gapped контур**: принёс бинарник — запустил.
- **Docker scratch**: `COPY brig /brig`, `ENTRYPOINT ["/brig", "run", "app.brig"]`.
- **CI**: `brig test` без установки тулчейна.
- **Обучение**: скачал один файл — пишешь акторы.
- **Встраивание в Go**: Brig как библиотека + single-binary CLI для разработки.

## Предлагаемая формулировка для дизайн-документа

Можно добавить принцип:

> **Принцип #14. Single-binary invariant.**
> Ядро Brig поставляется одним статическим бинарником без внешних зависимостей. VM, компилятор, stdlib, REPL и инструменты встроены. Расширения — только через Wasm-плагины (pure Go runtime) или нативные модули, скомпилированные в бинарник. C-ABI FFI и динамическая загрузка — вне core. `brig build` создаёт single-file executable с встроенным байткодом.

И обновить §13/§14:

- В Must: single-binary runtime, `go:embed`, pure Go, wazero для Wasm.
- В Should: `brig build` с appended payload.
- В Nice/Extended: C-ABI FFI, динамические библиотеки, hot reload.
- Пакетный менеджер: build-time vendoring, lock-файл.

Это действительно сильный ход. Он не только не противоречит дизайну Brig, а наоборот — усиливает его позиционирование: **«Erlang/Elixir-семантика, Go-деплой, один бинарник»**. Для edge, CLI, CI и air-gapped это может стать главной причиной выбрать Brig.
