# Splink — дизайн синтаксиса

Сводный документ по итогам обсуждения. Фиксирует принятые решения, обоснования и открытые вопросы.

---

## 1. Общий стиль

**Цель:** лакончность, идиоматичность, изящество. Минимум символов без потери однозначности.

**Принцип:** сокращение допустимо, только если читатель, не знающий языка, может угадать смысл. Если символ начинает значить два разных действия в зависимости от контекста — это не лакончность, а ловушка.

**Синтаксис блоков:** indent-driven, как в Python / Nim / F#.

Правила:

- Только пробелы. Tabs запрещены.
- Пустые строки не закрывают блок.
- Комментарии на отдельной строке не влияют на отступы.
- Продолжение выражения — по ведущему оператору (`|>`, `and`, `or`, `+`, `->`, `<-`).
- Скобки `{}`, `[]`, `()` — для данных и для вложенных блоков внутри выражения.
- Однострочная форма допустима только там, где она однозначна (см. §11, §14).

## 2. Функции

### Именованная

```splink
fn classify(n) -> match n
    0 -> "zero"
    1 -> "one"
    _ -> "many"
```

### Анонимная (лямбда)

```splink
pow = x -> x**2
nums |> map(pow)
```

### Правила

- `fn name(args) -> expr` — именованная.
- `fn(args) -> expr` или `x -> expr` — анонимная.
- Тело после `->` может быть на следующей строке с отступом.
- Многострочная лямбда в позиции аргумента требует скобок или выносится в именованную функцию.

### Приоритет `**`

- `-x**2` = `-(x**2)`
- `2**3**2` = `2**(3**2)` — правая ассоциативность, как в математике и Python.

### Равенство функций

**Identity equality.**

- `f == f` → `true`
- `f == g` → `true` только если это один и тот же объект-функция.
- `f == nil` → `false`, если `f` не `nil`.
- Функции можно класть в `Map`/`Set` — хэш по идентичности.
- Семантическое равенство — через явные дескрипторы (`HandlerId`, `{module, function}`, теги).

**Запрещено:**

- «Всегда false» — ломает рефлексивность, словари, отписки.
- `type_error` — только для строгих статических языков.

## 3. Списки и паттерны

**Список — persistent cons-list** (как в Lisp / Erlang / Haskell).

Обоснование:

- O(1) prepend, O(1) pattern match.
- Рекурсия, `fold`, `map`, `filter` — за O(n).
- Без cons-list накопление становится O(n²).

### Литерал

```splink
[1, 2, 3]
```

### Паттерны

```splink
[1, ..rest]        // min 1, tail = rest
[1, 2, ..]         // min 2, tail ignored
[1, 2, _]          // exactly 3, third ignored
[1, 2, _, ..rest]  // min 3, third ignored, tail = rest
```

### Правила

- `_` — один элемент, неважно какой.
- `..` — хвост, неважно какой.
- `..name` — хвост с именем.
- `.._` — **синтаксическая ошибка** (дубль `..`).
- `..` работает **только в паттернах**, не в выражениях.

### Range

Через `...` без скобок:

```splink
r = 1...10
nums = list(1...10)
```

- `..` — cons, `...` — range. Различие на один символ, требует подсветки и документации.
- `[1...10]` не использовать: визуально похоже на список из одного элемента.

### Индексированный доступ

Отдельный тип `Vector` / `Array`, если понадобится. Список остаётся cons-list.

## 4. `nil` vs `Option`

**Правило:** один способ отсутствия значения.

- **`nil`** — unit / no-op / «функция ничего не вернула».
- **`None`** — отсутствие значения в `Option<T>`.
- **`Error`** — ошибка в `Result<T, E>`.

### Запрещено

- Неявное приведение `nil -> None`.
- `nil` там, где ожидается `Option<T>`.
- Смешивание `nil` и `None` в pattern matching.

### Пример

```splink
fn find_user(id) -> Option<User>
    return None        // можно
    return Some(user)  // можно
    return nil         // запрещено
```

### Доступ к полям

- `config.debug` — частичный доступ, ошибка при отсутствии поля.
- `config[:debug]` — безопасный доступ, возвращает `Option<T>`.

**Обоснование:** pattern matching становится однозначным, типы не врут, нет двух идиом проверки, меньше багов на null.

## 5. Типы и записи

### Объявление

```splink
type User {
    id: Int,
    name: Str,
    email: Str,
}
```

### Создание

```splink
user = User{ id: 1, name: "Alice", email: "a@b.c" }
```

### Обновление (record update)

```splink
updated = User{ ..user, name: "Bob" }
# updated == User{ id: 1, name: "Bob", email: "a@b.c" }
```

Правила:

- `..user` — spread полей из `user`.
- Поля после spread переопределяют значения.
- Порядок важен: `User{ name: "Bob", ..user }` вернёт `name: "Alice"` из `user`.
- Тип можно опускать, если он выводится: `{ ..user, name: "Bob" }`.

Единообразно с `..rest` в списках: `..` везде означает «остальное».

### Планируется

- Опциональные аннотации типов в функциях: `fn classify(n: Int) -> Str { ... }`.
- Иммутабельность по умолчанию.

## 6. Операторы

### Логические — слова, не символы

```splink
yes = true
no = false

ready = yes and not no
# true and not false
# true and true
# => true

either = yes or no
# true or false
# => true
```

**Приоритет:** `not` > `and` > `or`.

**Short-circuit обязателен:**

```splink
fn safe_div(a, b) -> b != 0 and a / b > 1
# если b == 0, правая часть не вычисляется
```

**Возвращают `Bool`**, а не последнее значение, как в Python. Строже и предсказуемее.

### Арифметика

- `+`, `-`, `*`, `/`, `**`.
- `div` — целочисленное деление.
- `rem` — остаток.
- `%` — нет.

```splink
half = 7 div 2        # 3
remainder = 7 rem 2   # 1
is_even = x rem 2 == 0
```

`div` и `rem` — инфиксные слова, приоритет как у `*` и `/`, левоассоциативны.

### Pipe

```splink
doubled = nums |> map(x -> x * 2)
```

- `x |> f(a, b)` → `f(x, a, b)`.
- Без каррирования.
- Продолжение цепочки — по ведущему `|>`:

```splink
result = nums
    |> map(x -> x * 2)
    |> filter(x -> x > 1)
    |> find(x -> x > 2)
```

## 7. `with` / `else`

### Краткая форма

```splink
fn show(r) -> with Ok(v) <- r
    log(v)
else
    Error(:not_found) -> log_error("missing")
    Error(e)          -> log_error(e)
```

### Блочная форма

```splink
fn show(r) ->
    with Ok(v) <- r
        log(v)
    else
        Error(:not_found) -> log_error("missing")
        Error(e)          -> log_error(e)
```

### Правила

- `<-` внутри `with` — bind (паттерн слева, выражение справа).
- `else` — на том же уровне отступа, что `with`.
- Тело `with` — на уровень глубже.
- Ветки `else` — на уровень глубже, их тела — ещё глубже.
- `else` должен покрывать все оставшиеся случаи.

## 8. Модули vs Акторы

### Модули

Пространства имён для функций.

```splink
json.encode(config)
http.get("/health", handler)
```

- Не имеют состояния.
- Не имеют почтового ящика.
- Синхронные вызовы.
- Не могут получать сообщения.

### Акторы

Процессы с PID и почтовым ящиком.

```splink
worker = spawn(fn -> loop() end)
worker <- { :work, data }
```

- Асинхронные сообщения.
- Имеют состояние.
- Могут падать и перезапускаться.
- Отдельный жизненный цикл.

**Запрещено:** смешивать модули и акторы. `json.encode(x)` — вызов функции, не отправка сообщения.

## 9. Акторы: создание и связывание

**Три отдельных примитива:**

```splink
pid = spawn(fn -> ... end)      // создать без связи
link(pid)                        // связать существующий
pid = splink(fn -> ... end)     // атомарно создать и связать
```

### Правила

- `spawn` — создать актор, вернуть PID.
- `link(pid)` — связать существующий актор.
- `splink` — атомарно создать и связать. Критично для супервизоров.
- `spawn` + `link` — **не атомарны**, между ними есть окно.
- `slink` — запрещено (плохие ассоциации).
- `spawn_link` — допустимо, но `splink` предпочтительнее.

**Почему атомарность важна:** если процесс упадёт между `spawn` и `link`, ты потеряешь его. Для супервизоров это критично.

## 10. Отправка сообщений

### Основная форма

```splink
send(pid, msg)
```

### Короткая форма

```splink
worker <- :hello
worker <- { :work, data }
```

### Правила

- `<-` слева — получатель (PID), справа — сообщение.
- Не путать с `<-` в `with` (bind). Парсер различает по контексту.
- `<<<` — **запрещено** (ассоциации со сдвигом, визуальный шум).
- `!` (как в Erlang) — опционально, если нужна ещё более короткая форма. Пока не введён.

## 11. `recv` — приём сообщений

### Полная форма

```splink
recv
    { :value, v } -> v
    { :done }     -> :done
else msg
    log("unhandled: " + msg)
after 5000 -> :timeout
```

### Два варианта `else`

```splink
# Явный, для любителей explicit
else pull msg
    log("unhandled: " + msg)
```

```splink
# Краткий, для эстетов
else msg
    log("unhandled: " + msg)
```

Семантика идентична: несовпавшее сообщение **извлекается** из ящика и передаётся в блок. `pull` — явное указание на извлечение.

### Семантика

- `recv` — блокирующая операция.
- Возвращаемое значение — последнее выражение в ветке.
- Согласовано с `match`.
- `after` — таймаут от входа в `recv`, wall-clock.
- `after 0` — не блокироваться, проверить ящик.
- `after infinity` — ждать вечно.
- Без `after` — ждать вечно.

### `recv` без `else` — запрещён

```splink
# Ошибка компиляции: нет else/pull
recv
    { :value, v } -> v
after 5000 -> :timeout
```

Для selective receive — явный opt-in через `recv!`:

```splink
recv!
    { :ready } -> :ok
after 5000 -> :timeout
```

- `recv!` — опасная версия. Несовпавшие сообщения остаются в ящике.
- Может привести к mailbox overflow. Документировать как опасное.
- `!` — суффикс «опасная версия», как `File.read!` в Elixir.

### Однострочная форма

Разрешена, **только если**:

1. Ровно одна ветка.
2. Нет `after`.
3. Нет `else` / `pull`.

```splink
x = recv { :value, v } -> v
x = recv! { :ready } -> :ok

fn wait_for_ready(worker) ->
    worker <- { :start }
    recv! { :ready } -> :ok
```

**Запрещено:**

```splink
# after на отдельной строке — непонятно, к чему привязан
recv! { :ready } -> :ok
after 5000 -> :timeout

# несколько веток в одну строку
recv { :ok, v } -> v { :err, e } -> e

# else в одну строку
recv { :value, v } -> v else msg -> log(msg)

# after в одну строку
recv { :ready } -> :ok after 5000 -> :timeout
```

**Правило одной строки:** только когда весь `recv` — это «получить одно конкретное сообщение и вернуть его значение». Как только появляется выбор, таймаут или обработка неожиданного — блок.

### Примеры

**Актор-счётчик:**

```splink
fn counter_loop(state) ->
    recv
        { :inc }        -> counter_loop(state + 1)
        { :dec }        -> counter_loop(state - 1)
        { :get, from }  ->
            from <- { :value, state }
            counter_loop(state)
        { :stop }       -> :ok
    else msg
        log("counter: unexpected " + to_str(msg))
        counter_loop(state)
```

**Синхронный запрос-ответ:**

```splink
fn get_value(worker) ->
    worker <- { :get, self() }
    recv
        { :value, v } -> v
        { :error, e } -> Error(e)
    after 5000 -> Error(:timeout)
```

**С обработкой ошибок и таймаутом:**

```splink
fn worker_loop(state) ->
    recv
        { :work, data } ->
            match process(data)
                Ok(result) -> worker_loop(state + 1)
                Error(e)   ->
                    log_error(e)
                    worker_loop(state)
        { :status, from } ->
            from <- { :ok, state }
            worker_loop(state)
        { :stop } ->
            :ok
    else msg
        log("worker: unknown " + to_str(msg))
        worker_loop(state)
    after 30000 ->
        log("worker: idle timeout")
        :ok
```

**`recv` как выражение:**

```splink
fn ask(worker, question) ->
    worker <- { :ask, question, self() }
    recv
        { :answer, a } -> Some(a)
        { :no_answer } -> None
    after 5000 -> None
```

### Заимствования

- **Erlang/Elixir:** `spawn`, `link`, `recv`, `after`, pattern matching, cons-list.
- **Akka:** явный `Stash` вместо неявного selective receive.
- **Orleans:** FIFO-обработка, без selective receive, каждое сообщение обрабатывается ровно один раз.
- **Go:** `<-` для отправки в канал.

**Обоснование consume-модели:** исключить overflow, сделать поведение предсказуемым, каждое сообщение обрабатывается ровно один раз.

## 12. Многострочные лямбды

### Где можно

**В правой части присваивания — без скобок:**

```splink
double_plus_one = x ->
    y = x * 2
    y + 1
```

**В позиции аргумента — только в скобках:**

```splink
result = nums
    |> map(x ->
        y = x * 2
        y + 1
    )
    |> filter(x -> x > 1)
```

**Как значение поля записи:**

```splink
config = {
    debug: true,
    transform: x ->
        y = x * 2
        y + 1,
    retries: 3,
}
```

### Где нельзя

**В позиции аргумента без скобок:**

```splink
# Запрещено
result = nums |> map(x ->
    y = x * 2
    y + 1
)
```

**В pipe-цепочке без скобок:**

```splink
# Запрещено
result = nums
    |> map(x ->
        y = x * 2
        y + 1
    |> filter(x -> x > 1)
```

**В условии:**

```splink
# Запрещено
if (x ->
    y = x * 2
    y > 10
) then ...
```

### Как избежать сложных лямбд

Если тело больше 2–3 строк — выноси в именованную функцию:

```splink
fn transform(x) ->
    y = x * 2
    z = y + 1
    w = z * z
    w - y

result = nums
    |> map(transform)
    |> filter(x -> x > 1)
```

## 13. `recv` vs `match`

### Общее

- Ветки: `pattern -> expr`.
- Возвращаемое значение — последнее выражение в ветке.
- Оба — выражения, можно использовать в правой части присваивания.
- Оба поддерживают многострочные тела веток через отступ.

### Различия

- `match` — чистый, не блокирует, всегда блочный.
- `recv` — блокирует, имеет `after`, `else`/`pull`.
- `recv!` — опасная версия без `pull`.

### Почему `match` всегда блочный

`match` с одной веткой — почти всегда ошибка: либо не покрыл все случаи, либо это не `match`, а `if`. Поэтому однострочная форма для `match` не вводится.

`recv` — другое дело: «ждать ровно это сообщение» — легитимный сценарий, особенно с `recv!`.

## 14. Открытые вопросы

1. **`after` обязателен?** Или опционален с предупреждением линтера?
2. **Range:** `1...10` без скобок — окончательно? Нужен ли `list(1...10)`?
3. **`Vector`:** нужен ли отдельный индексируемый тип?
4. **`!` для send:** вводить ли как альтернативу `<-`?
5. **`spawn_link` vs `splink`:** окончательно `splink`?
6. **`recv` и `match`:** унифицировать ли обработку многострочных тел веток полностью?
7. **`recv!` без `after`:** предупреждение линтера или запрет?
8. **Record update без типа:** `{ ..user, name: "Bob" }` — окончательно?

## 15. Принципы (сводка)

1. **Лакончность без двусмысленности.** Сокращение допустимо, если читатель угадает смысл.
2. **Один способ для одной задачи.** `nil` vs `None`, `..` vs `.._`, `else` vs selective receive — везде один вариант.
3. **Явное лучше неявного.** Consume вместо накопления, `splink` вместо `spawn`+`link`, `Option` вместо `nil`.
4. **Отсутствие значения — в типе.** `Option<T>`, `Result<T, E>`.
5. **Акторы — runtime, модули — неймспейсы.** Не смешивать.
6. **Indent-driven для кода, скобки для данных.**
7. **Функции сравниваются по identity.** Семантика — через явные дескрипторы.
8. **Overflow исключён by design.** Каждое сообщение обрабатывается ровно один раз.
9. **Примеры для подсветки — валидный код.** Прогонять через парсер.
10. **Документировать жирным шрифтом** всё, что отличается от Erlang (`recv else`, `..`, `splink`, `recv!`).
