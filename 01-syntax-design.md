# Dreki — консолидированный дизайн языка v0.3.0

Документ фиксирует консолидированное состояние дизайна Dreki: исходный синтаксис, дополнение по равенству/видам записей, документ по обработке ошибок и все решения, принятые по итогам критического ревью v0.2.0 (`AUDIT.md`). **Заменяет все предыдущие документы целиком.** Места, где решение v3 отличается от v2, помечены ⚠.

**Референсный интерпретатор Dreki реализуется на Go (Golang)** — см. §13.

---

## 0. Принципы

1. Лаконичность без двусмысленности — сокращение допустимо, только если читатель угадает смысл.
2. Один способ для одной задачи.
3. Явное лучше неявного.
4. Отсутствие значения — всегда в типе: `Option`, `Result`, `()` как Unit. **`nil` в языке нет.**
5. Акторы — рантайм, модули — неймспейсы. Не смешивать.
6. Indent-driven для кода; скобки — для данных: `[]` списки, `()` кортежи, `{}` записи, `%[...]` векторы, `%{...}` мапы.
7. Функции сравниваются по identity; записи — гибридно, номинально или структурно (см. §2.10).
8. Рост очереди видим (`mailbox_size`) и ограничен (HWM). Переполнение — контейнированное падение актора, наблюдаемое через `watch`. Скрытых stash-механизмов уровня языка нет.
9. `..` имеет одну идею («остаток / развёртка») во всех позициях, где применим (см. §3).
10. Примеры — валидный код, прогоняются через парсер.
11. VM гарантирует TCO для хвостовых вызовов.
12. Единственное присваивание: имя связывается один раз в области, rebinding запрещён (исключение — REPL, §10.4).

## 1. Синтаксис блоков, отступы, комментарии

- Только пробелы, tabs запрещены. Пустые строки не закрывают блок. Отступ комментария не учитывается.
- Продолжение строки — по ведущему оператору, **закрытый список**: `|> and or + - * / ** div rem to == != < > <= >= .. <-`. Оператор-продолжение обязан быть первым токеном строки; отступ строки-продолжения — строго больше отступа первой строки стейтмента.
- Скобки — для данных и вложенных выражений внутри выражения.
- Однострочная форма допустима только там, где однозначна (см. §7, §10.4).
- **Комментарии** — однострочные, `#` до конца строки. Многострочных нет. `#` — только комментарий, исключений (`#[` и т.п.) нет.
- **Идентификаторы.** Имена переменных/функций — с малой буквы, типов/конструкторов — с заглавной. Допустим опциональный финальный `?` как маркер предиката (`eligible?`, `:ok?`): `?` — **только последний символ** имени или атома, никогда не оператор, не повторяется.
- **Зарезервированные слова:** `fn match recv with else if then after when alias import module type ensure and or not div rem to true false as` и операторы из списка выше.

⚠ Убрано целиком: правила многострочных лямбд из v1 (§12) — см. §4.2.

## 2. Литералы и типы данных

### 2.1 Числа

- `Int` — целое произвольной точности по умолчанию (как Python) — в динамическом языке тихое переполнение фиксированной ширины было бы отдельным классом багов.
- `Float` — IEEE754 double.
- **Литералы (Must):** `0x`/`0b`/`0o` (шестнадцатеричные/двоичные/восьмеричные), `1_000_000` (разделитель тысяч), `1e9` (экспонента).
- `Decimal` — точная десятичная арифметика, литерал `dec"1.50"` (сигил, см. §2.2). **(should have)**
- `Rational` — stdlib, не ядро. **(nice to have)**

### 2.2 Строки и Bytes

- Интерполяция: `"Привет, \(name)!"` — открывается `\(`, закрывается `)`.
- Стандартные escape: `\n`, `\t`, `\\`, `\"`, `\(` для буквального `\(`.
- Строка — последовательность кодпоинтов UTF-8, всегда валидный UTF-8.
- Многострочный литерал: `"""..."""`, отступ первой закрывающей кавычки обрезается из каждой строки. **(should have)**
- **`Bytes` — произвольные бинарные данные** (HTTP-тела, чанки, криптография, не-UTF8 заголовки). Литерал `b"\x89PNG"`. **Must** — без него заявленная веб-ниша не работает. Преобразование: `bytes.to_str(b)` (валидация UTF-8) / `str.to_bytes(s)`.
- **Сигилы — закрытое семейство из трёх:** `b"..."` (Bytes, Must), `dec"..."` (Decimal, Should), `rx"..."` (regex, Should). Новый сигил — только отдельным решением дизайна.
- `regex` — литерал `rx"..."` компилирует регулярное выражение на этапе загрузки модуля. **(should have)**

### 2.3 Кортежи (Tuple) ⚠ новое

Фиксированной длины, гетерогенные, позиционные.

```dreki
t = (1, "a", :ok)
(a, b, c) = t
```

Правила:

- `()` — пустой кортеж, он же **Unit** (замена `nil`, см. §2.9).
- `(x)` — просто группировка выражения, не 1-кортеж.
- `(x,)` — 1-кортеж, запятая обязательна (как в Python).
- `..` в кортеже запрещён **и в паттерне, и при конструировании** — арность всегда фиксирована.
- Равенство — структурное: по длине и поэлементно.

Кортежи — стандартный способ передавать «тег + данные»: `(:work, payload)`, `(:ok, value)`, `(:error, reason)`. Это чинит место в v1, где `{ :work, data: [...] }` смешивал позиционный тег и именованное поле внутри одних и тех же `{}` — теперь роли разведены: `{}` только для именованных полей, `()` только для позиционных данных.

### 2.4 Списки (List) и паттерны

Persistent cons-list, без изменений по существу.

```dreki
[1, 2, 3]
```

Паттерны:

```dreki
[1, ..rest]        # хвост с именем
[1, 2, ..]         # хвост без имени
[1, 2, _]          # ровно 3, третий неважен
[1, 2, _, ..rest]
```

`_` — один любой элемент. `..`/`..name` — хвост, **только последним элементом, не более одного раза**. `.._` — синтаксическая ошибка. Конструирование (не паттерн) с `..` подчиняется другому правилу — см. §3.

### 2.5 Диапазоны — `to` ⚠ изменено

Слово вместо символов, по прецеденту `div`/`rem`/`and`/`or`. Убирает проблему v1 «`..` и `...` отличаются на один символ, требуют подсветки».

```dreki
r = 1 to 10          # включительно с обеих сторон
nums = list(1 to 10)
```

Нисходящий диапазон — композицией, без нового слова:

```dreki
(1 to 10) |> reverse()
```

`...` в языке больше не используется.

### 2.6 Vector ⚠ изменено

Персистентный индексируемый вектор. Нужен, потому что cons-list даёт O(n) произвольный доступ, а заявленная ниша (бэкенд/веб) гарантированно требует O(1)/O(log n): JSON-массивы, пагинация, буферы.

```dreki
v = %[1, 2, 3]
v[0]                  # 1; ошибка при выходе за границы
vec.set(v, 0, 99)     # новый вектор, старый не изменён
vec.push(v, 4)        # добавить в конец, O(1) амортизированно
length(v)
```

- Реализация: персистентная trie-структура (по образцу Clojure) — O(1) amortized append, O(log32 n) чтение/обновление. Совместимо с требованием «интерпретируемый язык», без мономорфизации.
- Литерал — **`%[...]`**, а не `#[...]`: `#` остаётся только комментарием (принцип №1), а `%` даёт мнемонику «персистентная хеш-коллекция» — единое семейство с `%{...}` (Map).
- Обновление — **`vec.set(v, 0, 99)`** (модульный вызов), чтобы не конфликтовать с конструктором `Set` `set(1, 2, 3)` (§2.8).
- Паттерн-матчинг — только по точной длине и поэлементно, **`..` не поддерживается**: rest-захват дорог для индексируемой структуры и плохо сочетается с идеей O(1)-доступа. Для рекурсивной обработки — используйте List.

### 2.7 Map ⚠ изменено

Персистентная хэш-таблица, ключи — произвольные значения, вычисляемые в рантайме.

```dreki
m = %{ "a" => 1, "b" => 2 }
m["a"]                 # безопасный доступ -> Option
map.put(m, "c", 3)     # новый Map
m2 = %{ ..m, "c" => 3 }  # спред разрешён, позднее — приоритетнее
```

Символ пары — `=>`, а не `:` как в записях: поле записи — идентификатор, известный при разборе; ключ Map — произвольное вычисляемое выражение. Разные роли — разный символ, без потери однозначности.

Pattern matching — **частичный**, в отличие от List/Tuple/Record:

```dreki
match m
    %{ "a" => v } -> v   # достаточно наличия ключа "a"; остальные ключи неважны
```

Ключ в паттерне — литерал или связанная переменная; захват ключа `%{ k => v }` в MVP запрещён.

Это единственное намеренное исключение из принципа «однозначный тотальный матч»: у Map, в отличие от списка/кортежа/записи, «полной формы» не существует — открытое множество ключей это часть определения типа, а не случайность (тот же выбор в Erlang/Elixir).

### 2.8 Set ⚠ новое

Персистентное множество. Без отдельного литерала — конструктор на вариадике (см. §4.3):

```dreki
s = set(1, 2, 3)
```

Паттерн-матчинг — **точный** (не подмножество): паттерн матчит только множество ровно из перечисленных элементов. Частичный матч по подмножеству — не структурная деконструкция, а предикат «содержит ли»; «содержит подмножество» — функция `set.contains_all`, не паттерн.

Отдельный литеральный синтаксис можно добавить позже при явном спросе. **(nice to have)**

`Queue` — FIFO, Okasaki-очередь из двух списков, в stdlib, не языковая конструкция. **(nice to have)**

### 2.9 `nil` исключён ⚠ изменено

`nil` удалён целиком. Модель отсутствия значения:

- «Нет значения в домене» — `Option<T>` (`Some`/`None`).
- «Операция не удалась» — `Result<T, E>` (`Ok`/`Error`).
- «Функция не возвращает содержательного значения» — **`()`, Unit**, пустой кортеж. Не участвует в матчинге как замена `None`/`Error` — это другая категория.

Конструкторы вариантов — это тегированные данные, а не новый вид значения: `Ok(x) ≡ (:ok, x)`, 0-арный вариант — атом (`None ≡ :none`). См. §8.1.

Это закрывает главную дыру v1: `nil` был третьей, неспецифицированной категорией отсутствия. Теперь она — уже существующая конструкция (пустой кортеж), без нового имени и нового типа.

### 2.10 Записи: номинальные и анонимные

Модель — гибрид:

- `type User {...}` — **номинальная**: тег типа — часть значения.
- `{ key: value, ... }` — **структурная**, анонимная: равна по полям, без тега.
- Разные виды друг другу не равны.

```dreki
User{ id: 1 } == User{ id: 1 }     # true
User{ id: 1 } == Admin{ id: 1 }    # false — разные типы
{ id: 1 } == { id: 1 }              # true
User{ id: 1 } == { id: 1 }          # false — разные виды
```

Pattern matching: номинальный паттерн матчит только тот же номинальный тип; анонимный — только анонимные записи. Порядок веток важен. Матч — **частичный по умолчанию**: перечисленные поля обязаны присутствовать, остальные — в `..rest`. Литеральные поля записи проверяются статически на загрузке модуля (`User{ id: 1, nam: "x" }` — опечатка ловится до запуска).

⚠ Две формы `type` разведены: `type Result { Ok(T), Error(E) }` — **вариант-декларация** (порождает конструкторы-теги, §8.1); `type User { id: Int, name: Str }` — **запись-декларация** (именованные поля). Одно ключевое слово, два смысла по форме тела.

`fn greet(u: User)` не принимает ни другой номинальный тип, ни структурно похожую анонимную запись — защита от случайного смешения доменных сущностей.

Конвертация — только явная: `{ ..u }` (номинальная → анонимная), `User{ ..r }` (анонимная → номинальная).

Record update сохраняет вид: `User{ ..u, name: "Bob" }` остаётся `User`; `{ ..r, name: "Bob" }` остаётся анонимной.

Сериализация:

```dreki
json.encode(User{ id: 1 })              # {"id": 1} — тег типа не эмитится по умолчанию
json.encode({ id: 1 })                  # {"id": 1}
json.encode(User{ id: 1 }, type_tag: true)  # {"__type__": "User", "id": 1} — opt-in для внутреннего RPC
```

Type alias — структурно совместим с исходником: `type UserId = Int`. Номинальная обёртка — только через запись: `type UserId { value: Int }`.

Актёрные сообщения: с появлением кортежей — тег+данные передаём кортежем (`(:work, payload)`), а не смесью позиционного/именованного внутри `{}`. Именованные записи — когда сообщению нужна собственная предметная схема (`Work{ id: 1, retries: 3 }`).

### 2.11 Равенство — сводная таблица

| Вид                             | Равенство                 | Pattern matching      | Комментарий                                                    |
| ------------------------------- | ------------------------- | --------------------- | -------------------------------------------------------------- |
| `Int`/`Float`/`Str`/`Bytes`/`Bool`/атом | по значению               | точное                | `true`/`false` — атомы                                          |
| Функция                         | по identity               | —                     | `f == f` true; разные объекты, даже с идентичным телом — false |
| `Tuple`                         | структурно, длина+позиция | точное                | `..` запрещён                                                  |
| `List`                          | структурно, поэлементно   | точное или с `..rest` | O(n) сравнение                                                 |
| `Vector`                        | структурно, длина+позиция | точное, без `..`      | —                                                              |
| `Map`                           | по набору пар             | **частичное**         | единственное намеренное исключение                             |
| `Set`                           | по набору элементов       | точное                | не подмножество — см. §2.8                                      |
| `{...}` анонимная               | структурно, по полям      | только с анонимными   | —                                                              |
| `type X {...}` номинальная      | по тегу + полям           | только с тем же `X`   | `X{...} != Y{...}` даже при идентичных полях                   |
| `()` Unit                       | единственное значение     | `()`                  | заменяет `nil`                                                 |

### 2.12 As-паттерны ⚠ новое

`pattern = name` — деструктурировать аргумент **и** сохранить целое значение:

```dreki
fn foo((:ok, _) = full) ->
    # full — весь кортеж {:ok, _}; _ — разобранная часть
```

`=` здесь — оператор *паттерна*, а не присваивание; `name` — свежая переменная (запрет rebinding распространяется и сюда). Разрешён во всех четырёх конструктах: параметры функции, `match`, `recv`, `with`. **(should have)**

## 3. Оператор `..`: унифицированная семантика ⚠ закрывает противоречие v1

Одна идея — «остаток / развёртка» — работает по-разному в двух ролях:

**Связывание** (паттерн, деструктуризация — длина заранее неизвестна):

- Разрешён **только последним элементом, не более одного раза**.
- `[1, ..rest]` (список), `fn f(a, ..rest) -> ...` (параметры функции, §4.3).
- `Tuple` и `Vector` эту роль не поддерживают — их длина всегда известна.

**Конструирование** (построение значения — длина/содержимое уже известны):

- Разрешён **в любом количестве, в любой позиции**.

```dreki
[0, ..xs, 99]                 # список: конкатенация
{ ..user, name: "Bob" }        # запись: наложение полей, позднее — приоритетнее
{ ..a, ..b, x: 1 }             # несколько спредов подряд — валидно
%{ ..m, "c" => 3 }             # мапа: спред разрешён (кортеж — нет, арность фиксирована)
f(head, ..items, tail)         # вызов функции: развёртка списка в аргументы
```

Правило одной фразой: **связывание — `..` только в конце и один раз (неизвестная длина требует единственной точки неопределённости); конструирование — `..` где угодно и сколько угодно (длина уже известна, угадывать нечего)**.

## 4. Функции

### 4.1 Мультиклозные функции ⚠ новое

```dreki
fn classify(0) -> "zero"
fn classify(1) -> "one"
fn classify(n) -> "many"
```

- Клозы одного имени/арности идут подряд.
- Первый подходящий паттерн выигрывает (как ветки `match`).
- Guards через `when`:

```dreki
fn classify(n) when n > 0 -> "positive"
fn classify(0)             -> "zero"
fn classify(n)              -> "negative"
```

- Если ни один клоз не подошёл — автоматический `raise (:function_clause, args)` (см. §8.3).

Это заметно поднимает выразительность относительно v1, где диспетчирование по значению аргумента шло только через `match` внутри одного тела.

⚠ Дефолтных значений аргументов **нет** (`fn greet(name, greeting = "hello")` не существует). Необязательные параметры выражаются обёрточной клаузой — тем же мультиклозом, без нового механизма (принцип №2):

```dreki
fn greet(name) -> greet(name, "hello")
fn greet(name, greeting) -> ...
```

### 4.2 Лямбды ⚠ изменено

Две формы.

**Короткая** — одно выражение в строке:

```dreki
pow = x -> x**2
eligible? = x -> x > 0 and x rem 3 == 0
nums |> map(x -> x * 2)
```

Параметры: `x -> expr`, `(x, y) -> expr`, `() -> expr`. Нулевая арность в полной форме — `fn -> expr` (скобки опциональны). `?`-суффикс имени — конвенция предикатов (см. §1).

**Полная** — `fn (p) ->` + либо одно выражение в строке, либо отступ-блок. Без `end`:

```dreki
fn (x) ->
    y = x * 2
    y + 1
```

Лямбда, связанная с именем (`f = x -> expr`), — **значение-функция**; вызывается как обычная функция `f(args)` (единый синтаксис вызова, принцип №2). Отличия от именованной `fn f(...)`: не участвует в мультиклозности и паттерн-параметрах, **нерекурсивна** — имя не видно в собственном теле. Рекурсивные хелперы — только локальные `fn`-объявления (§4.5).

⚠ Голое имя лямбды — это *значение*, а не вызов: при `f = () -> 42` запись `f` передаёт значение, `f()` — вызывает.

### 4.3 Вариадические параметры и спред аргументов ⚠ новое

Тот же `..`, что у списков — параметр-остаток собирает лишние позиционные аргументы в `List`:

```dreki
fn log_all(..args) ->
    args |> list.each(log)

log_all(1, 2, 3)     # args = [1, 2, 3]
```

Комбинируется с мультиклозностью (остаток — всегда последний параметр):

```dreki
fn sum()          -> 0
fn sum(x, ..rest) -> x + sum(..rest)
```

Обратная операция — спред списка в аргументы вызова, по правилу конструирования из §3:

```dreki
nums = [1, 2, 3]
sum(..nums)          # эквивалентно sum(1, 2, 3)
```

Новой грамматики не вводится — та же семантика `..`, что уже определена для списков и записей.

### 4.4 Приоритет `**`, равенство функций

Без изменений: `-x**2 = -(x**2)`, `2**3**2 = 2**(3**2)` (правая ассоциативность). Функции — identity equality; семантическое равенство — только через явные дескрипторы (`{module, function}`, теги).

### 4.5 Локальные именованные функции ⚠ новое

Внутри тела функции, сразу после `->` и **до первого выражения** (let-стиль), можно объявлять локальные именованные функции. Мультиклозность — как на уровне модуля; взаимная рекурсия разрешена (следствие декларации-only и запрета rebinding):

```dreki
fn pow(base, exp) ->
    fn go(acc, 0) -> acc
    fn go(acc, n) -> go(acc * base, n - 1)
    go(1, exp)
```

Правила: только в начале тела, до первого выражения; имя не перекрывает имя из внешней области; вперёд-ссылки свободны. В любом другом месте объявление не допускается — иначе усложняется offside-парсер.

## 5. Операторы

### 5.1 Логические — без изменений

`and`/`or`/`not`, `not > and > or`, short-circuit обязателен, всегда возвращают `Bool`.

⚠ Побочный эффект строгости: идиома `x = value or default` не работает (`or` возвращает `Bool`, не значение). Замена — функция stdlib, без нового оператора:

```dreki
x = opt |> unwrap_or(default_value)
```

Так сохраняется принцип «один способ» и не добавляется символьный шум вида `??`/`||=`.

### 5.2 Арифметика — без изменений

`+ - * / **`, `div`, `rem` — инфиксные слова, приоритет как у `*`/`/`, левоассоциативны. `%` нет.

### 5.3 Сравнение ⚠ изменено

Операторы сравнения — стандартные: `==`, `!=`, `<`, `>`, `<=`, `>=`.

⚠ v2 использовал `=<` (Erlang-стиль), потому что `<=` был занят под отправку сообщений. В v3 отправка — функция `send(pid, msg)` (§10.3), поэтому `<=` освобождён и возвращён сравнению, а `=<` удалён. `!` не вводится; `!=` остаётся неравенством.

Тотальный порядок — term order (Erlang-тип): число < атом < кортеж < список < запись. `sort` смешанных списков не бросает, а упорядочивает по этому порядку.

Приоритет `to` — ниже арифметики, выше сравнения: `1 to n + 1` ≡ `1 to (n + 1)`; `rem`/`div` — на уровне `*`/`/`, поэтому `x rem 3 == 0` ≡ `(x rem 3) == 0`.

### 5.4 Pipe — без изменений

`x |> f(a, b)` → `f(x, a, b)` — значение подставляется **первым** аргументом, без каррирования; продолжение цепочки по ведущему `|>`. Коллекционные функции прелюдии принимают «коллекцию первым», чтобы пайплайн читался: `list |> all(eligible?)` ≡ `all(list, eligible?)`. `send` в pipe не разрешён (§10.3).

## 6. `if` — синтаксический сахар над `match` ⚠ закрывает пробел v1

`if` не существует в ядре языка. Парсер разворачивает его в `match` по булеву значению:

```dreki
if ready
    start()
else
    wait()
```

≡

```dreki
match ready
    true  -> start()
    false -> wait()
```

Без `else` — возвращает `()` (Unit):

```dreki
if ready
    start()
```

≡

```dreki
match ready
    true  -> start()
    false -> ()
```

Однострочная форма — только целиком, с обеими ветками (никаких «висячих» `if` в одну строку):

```dreki
x = if ready then start() else wait()
```

`match`, в отличие от `if`, остаётся всегда блочным (§10.5) — `if` заранее известен как ровно два случая, а произвольный `match` с одной веткой почти всегда баг.

---

## 7. `with`/`else` ⚠ расширено — несколько bind'ов подряд

v1 показывал только один bind, чего объективно мало для главной идеи `with` — последовательной композиции `Result`-цепочек:

```dreki
fn process(input) -> with
    Ok(a) <- validate(input)
    Ok(b) <- transform(a)
    Ok(c) <- save(b)
    Ok(c)
else
    Error(e) -> Error(e)
```

`<-` — bind, работает только внутри `with`. `else` покрывает все оставшиеся случаи, на одном уровне отступа с `with`.

⚠ v3: `with` работает и на `Option` (`Some`/`None`), не только на `Result`. Опущенный `else` = пропагировать несовпавшее значение как есть (Elixir-модель) — цепочка просто возвращает первый несовпавший `Error`/`None`. `with` **не** авто-raise (§8.3).

## 8. Обработка ошибок

### 8.1 Result/Option ⚠ изменено — единый механизм тегированных данных

```dreki
type Result<T, E> { Ok(T), Error(E) }
type Option<T>    { Some(T), None }
```

⚠ v3: конструкторы вариантов — **не** новый вид значения, а тегированные данные: `Ok(x) ≡ (:ok, x)`, `Some(v) ≡ (:some, v)`. 0-арный вариант — атом: `None ≡ :none`. `type Result { ... }` — объявление, порождающее конструкторы, а не отдельный тип. Одна запись канонична для сообщений — кортеж `(:ok, v)`; `Ok(v)` — сахар над ней.

`Option` — «нет значения», `Result` — «операция не удалась». Не смешивать.

### 8.2 `raise`/`trap` — без изменений по существу, примеры обновлены под кортежи

```dreki
fn get_user(id) ->
    match db.find(id)
        Some(u) -> u
        None    -> raise (:not_found, id)
```

```dreki
result = trap
    body = parse_body(req)
    user = authenticate(req)
    process(user, body)
```

`trap` создаёт границу: ловит любую ошибку внутри блока/лямбды, возвращает `Ok(v)` или `Error(e)`. Обе формы (лямбда `trap(fn -> ...)` и блочная) остаются — механическая элизия лямбды, тот же паттерн, что у именованных/анонимных функций везде в языке, а не дублирование «на вкус».

### 8.3 Автоматический `raise` при непокрытом варианте ⚠ изменено

Непокрытый `match`, `recv` или мультиклозная функция (без подходящего паттерна/клоза) бросает автоматически. **`with` — исключение: не авто-raise**, а пропагация несовпавшего значения (§7).

Имена авто-raise: `(:function_clause, args)` (мультиклозная функция), `(:case_clause, val)` (`match`), `(:recv_clause, msg)` (`recv`). Один механизм на три конструкции.

### 8.4 Решения по открытым вопросам документа об ошибках

- **`ensure`/`defer`.** Ключевое слово внутри блока `trap`, выполняется на обоих путях — не отдельный механизм, часть `trap`:

```dreki
result = trap
    file = open("data.txt")
    ensure close(file)
    process(file)
```

**(should have)**

- **Кросс-акторные ошибки.** По умолчанию ничего не видно — наблюдатель узнаёт о падении, только если явно подписался. Подписка — `watch(pid)` (§10.2) присылает `(:down, ref, reason)` обычным сообщением в `recv`. Никакого неявного проброса через границу актора.
- **Ошибки в `spawn`.** Без `link`/`watch` падение нового актора родителю не видно (как в Erlang). `spawn_linked` — падение уронит и родителя, если не поймано выше по дереву супервизии; `watch` — падение придёт сообщением `(:down, ...)`, родитель не падает.
- **`trap` внутри ветки `recv`.** Работает и является рекомендованной идиомой — не уронить актор из-за одного плохого сообщения (тот же приём, что в HTTP-хендлере, применим внутри любого `*_loop`).
- **Типы ошибок, stack trace, timeout для `trap`** — остаются открытыми, см. §15.

## 9. Модули и импорты ⚠ изменено

```dreki
module http.client
alias http.client as http
import json
```

- `import` — весь модуль под собственным именем.
- `alias ... as ...` — модуль под другим/сокращённым именем.
- Без `from x import y`: вызов всегда виден с квалификатором (`json.encode`, не голый `encode`) — не расшивает неймспейс, согласуется с «явное лучше неявного».
- `use`-инъекция макросов (как в Elixir) не вводится — метапрограммирование вне MVP.
- **Объявление модуля** — `module http.client`; по умолчанию файл = модуль (имя из пути), заголовок — для несовпадающих имён.
- **Top-level модуля — только декларации:** `fn`, `type`, `alias`, `import`, константы. Выражений на top-level нет (кроме REPL). Это решает циклические импорты (ленивый резолв функций, cycles OK) и закладывает горячую перезагрузку.
- **Entry point — `fn main()`:** рантайм стартует корневой актор, исполняющий `main`; аргументы — через `sys.args()`. «Скриптовый» режим — это REPL, отдельной точки входа нет.

### 9.1 Прелюдия

Голые имена, доступные без `import`, — минимальный фиксированный набор; всё остальное — модульное. Состав зафиксирован сейчас, чтобы не плодить коллизии имён.

- **Коллекции:** `map`, `filter`, `find`, `fold` (левый), `all`, `any`, `length` — принимают «коллекцию первым», поэтому читаются в pipe (`list |> all(eligible?)`). `all`/`any` короткозамкнуты; `none` и `reduce` не вводятся (дубли `not any` и `fold` — принцип №2).
- **Конверсии:** `to_str`, `to_int`, `to_float`.
- **Акторы/ящик:** `send`, `spawn`, `spawn_linked`, `link`, `watch`, `unwatch`, `self`, `make_ref`, `mailbox_size` (§10.6).
- **I/O:** `print`, `eprint`.
- **Эффекты:** `assert`, `raise`, `trap`.
- `not` — **оператор**, а не имя прелюдии (как `and`/`or`).

Коллизия между функцией `map` и модулем `map` (`map.put`) не возникает: модуль встречается только с квалификатором `.`, функция — в позиции вызова.

## 10. Акторы

### 10.1 Модули vs Акторы — без изменений

Модули — неймспейсы без состояния и почтового ящика, синхронные вызовы. Акторы — процессы с PID, состоянием и почтовым ящиком, асинхронные сообщения. Не смешивать: `json.encode(x)` — вызов функции, не отправка сообщения.

### 10.2 Создание и связывание ⚠ `monitor` переименован в `watch`

```dreki
pid = spawn(fn -> ...)            # создать без связи
link(pid)                         # связать существующий
pid = spawn_linked(fn -> ...)     # атомарно создать и связать
ref = watch(pid)                  # однонаправленно наблюдать, не падать вместе
unwatch(ref)                      # снять наблюдение
```

`watch(pid)` присылает `(:down, ref, reason)` обычным сообщением в `recv`, когда процесс падает. `spawn_link` как отдельное имя убран — дублирование `spawn_linked` «на вкус» (принцип №2). `spawn`+`link` по отдельности остаются для случаев, где связь не нужна сразу (окно между вызовами — осознанный риск вызывающего, не языковая проблема).

`watch(pid)` критичен для супервизоров (§11): супервизор, слинкованный с ребёнком, упал бы вместе с ним; супервизор, наблюдающий ребёнка через `watch`, получает `(:down, ...)` и решает сам.

### 10.3 Отправка сообщений ⚠ только `send(pid, msg)`

```dreki
send(worker, :hello)
send(worker, (:work, data))
```

⚠ v3: операторы `<=` и `!` не вводятся — только функция `send(pid, msg)`. Она возвращает `Result[()]`: `Error(:busy)` при переполнении ящика (HWM, принцип №8). Это упрощает всё разом: `<=` освобождён под сравнение (§5.3), `!` не вводится (`!=` — неравенство), `<-` остаётся только под `with` (§7), контекстный разбор `<=` полностью снят. Цена — `send(pid, msg)` длиннее оператора, но send в акторном языке не такой частый жест, как сравнение; компромисс в пользу однозначности. `send` в pipe не разрешён (§5.4).

### 10.4 `recv` ⚠ `recv!` удалён, рост очереди ограничен HWM

```dreki
recv
    (:value, v) -> v
    (:done)     -> :done
else msg
    log("unhandled: " + to_str(msg))
after 5000 -> :timeout
```

- `after N` — таймаут **пустого ящика**: срабатывает, только если в момент проверки очередь пуста, а не «ждать нужный ответ N мс» (следует из consume-модели). Ожидание конкретного ответа — correlation-идиома через `make_ref` (см. §10.6).
- `recv!` и модель «опасного» selective receive со stash — убраны из языка полностью. Вместо «overflow исключён» — принцип №8: рост очереди видим (`mailbox_size`) и ограничен (HWM), переполнение — контейнированное падение актора, наблюдаемое через `watch`.
- Оставлен только один синтаксис для необработанных сообщений: **`else msg`**. Второй вариант (`else pull msg`) убран — было дублирование одной семантики двумя словами ради вкуса, нарушение принципа №2.
- Однострочная форма — как в v1 (1 ветка, без `after`, без `else`):

```dreki
x = recv (:value, v) -> v
```

⚠ Уточнение: если сообщение не совпало с единственной веткой в однострочной форме — оно не молча удаляется, а логируется в debug-канал (трассировка, §14). Компромисс ради краткости идиомы «дождаться ровно одного сообщения»; нужна полная видимость — используйте блочную форму с `else`.

**Плата за отказ от selective receive.** Если актору нужно обработать сообщения не в порядке прихода (частый паттерн в Erlang — «жду ответ на конкретный запрос, остальное пока отложи»), в Dreki это не языковая фича, а прикладная идиома: актор сам складывает «неожиданные» сообщения в свой стейт и обрабатывает их позже.

```dreki
fn worker_loop(state) ->
    recv
        (:reply, id, v) when has_pending(state, id) ->
            worker_loop(resolve_pending(state, id, v))
        (:reply, id, v) ->
            worker_loop(stash(state, id, v))   # отложили сами, явно
        (:stop) -> :ok
    else msg
        log("unknown: " + to_str(msg))
        worker_loop(state)
```

Многословнее Erlang-style selective receive, но полностью убирает риск неограниченного роста «отложенных» сообщений внутри рантайма — рост виден и ограничен структурой `state`, которую пишет разработчик, а не скрытым механизмом ящика.

### 10.5 `recv` vs `match`

Без изменений по существу: `match` — чистый, не блокирует, всегда блочный; `recv` — блокирует, имеет `after`/`else`. `if` (§6) живёт по тем же принципам, что `match`, не будучи отдельной языковой сущностью.

### 10.6 Встроенные акторные примитивы

Без них correlation-идиомы не существуют; все — в прелюдии:

```dreki
send(pid, msg)        # Result[()], Error(:busy) при HWM
spawn(fn -> ...)      # новый актор, без связи
spawn_linked(fn -> ...)  # создать + связать атомарно
link(pid)             # связать с существующим
watch(pid)            # -> ref; присылает (:down, ref, reason)
unwatch(ref)
self()                # свой PID
make_ref()            # уникальная ссылка для correlation-идиом
mailbox_size()        # размер очереди (видимость роста, принцип №8)
```

Correlation-идиома «запрос/ответ»: отправитель кладёт в сообщение `make_ref()`, получатель возвращает его в ответе — отправитель матчит ответ по `ref` в своём `recv`. Это прикладная идиома поверх `recv` + стейт (как stash в §10.4), а не скрытый механизм ящика.

⚠ Формат PID закладывает **node-идентификатор уже сейчас** (зарезервированное поле): добавить его до релиза стоит ноль, после — смена формата идентичности всех акторов. Распределённость при этом не строится — только резервируется поле.

## 11. Супервизоры ⚠ закрывает блокирующий пробел v1

Минимальное ядро — `watch` (§10.2); поверх него — стандартная библиотека, не языковая конструкция (согласуется с «модули = функции, не магия»). Options передаются **анонимной записью, не kwargs** (kwargs — Should, §14):

```dreki
sup = Supervisor.start({
    strategy: :one_for_one,
    max_restarts: 3,
    within: 5000,
    children: [
        { name: :counter, start: () -> spawn_linked(() -> counter_loop(0)), restart: :permanent },
        { name: :worker,  start: () -> spawn_linked(() -> worker_loop(0)),  restart: :transient },
    ],
})
```

Под капотом `Supervisor` — обычный актор, который `watch`-ит своих детей и перезапускает их по стратегии; грамматика языка ради этого не меняется. `max_restarts`/`within` — окно перезапусков, при превышении супервизор эскалирует (падает сам).

## 12. Протоколы / Behaviors ⚠ новое

Без нового синтаксиса — запись с картой обработчиков + функция-диспетчер в stdlib:

```dreki
KVBehavior = Behavior{
    handlers: %{ :get => fn(state, key) -> ..., :put => fn(state, key, val) -> ... }
}
pid = spawn_behavior(KVBehavior, init_state)
```

Ключи — атомы (`:get`, `:put`), единообразно с тегированными данными (§8.1). Диспетч по тегу верхнего уровня; если логика ветвится тоньше — внутри самого обработчика. `Behavior.define(name, callbacks: [...])` + проверка наличия функций при `spawn_behavior`. **(should have)**

## 13. Архитектура рантайма ⚠ новое

- **Язык реализации — Go (Golang).** Референсный интерпретатор — лексер, парсер, компилятор в байткод и сама VM — пишется на Go. Выбор зафиксирован и не пересматривается в рамках v3-дизайна; на семантику языка он не влияет (принцип №10 про валидность примеров остаётся нейтральным к хосту).
  - `goroutine` и каналы ложатся на акторную модель почти один-в-один — планировщик с редукциями строится поверх них без сторонних зависимостей.
  - Один статический бинарник и кроссплатформенная сборка без внешнего рантайма — совместимо с заявленной нишей «бэкенд/веб».
  - Встроенный сборщик мусора снимает необходимость писать GC для MVP.
  - `math/big` покрывает `Int` произвольной точности из §2.1.
  - `cgo`/C-ABI — готовый путь для FFI, когда представление значений стабилизируется.
- Интерпретатор — **регистровая байткод-VM** (в духе BEAM/Lua), не walking-интерпретатор по AST и не стековая VM. Меньше инструкций на операцию, чище TCO (переиспользование кадра) и естественный учёт редукций по числу инструкций. Фрейм — как у BEAM: аргументы в регистрах, spill в стек при нехватке; замыкания — через upvalues. Регистровая модель менее читаема в байткоде, поэтому обязателен дизассемблер (`--dump-bytecode`) и `line:col` на инструкцию — часть Must (диагностика, §14).
- **Память (сема, Must-решение):** общий heap + ссылки на иммутабельные значения, не per-actor heap. Наблюдаемо эквивалентно копированию при send (значения иммутабельны, алиасинг неотличим от копии); один генеративный GC; большие структуры бесплатны. Решение действует, пока язык остаётся иммутабельным: мутация, FFI, наблюдающий алиасинг, или распределённость — триггер пересмотра; миграция к per-actor heap — возможная эволюция без смены пользовательской семантики.
- **TCO гарантирован** для самохвостовых и общих хвостовых вызовов — без этого бесконечные акторные циклы (`counter_loop(state)`) переполнили бы стек. Хвостовой вызов компилируется в переиспользование текущего кадра, а не в новый push.
- **Кооперативное планирование по «редукциям»** (по образцу BEAM): каждому актору отпускается лимит шагов VM перед принудительной передачей управления планировщику — честность между акторами без вытесняющей многопоточности и без блокировок, что и требуется акторной моделью.

## 15. Оставшиеся открытые вопросы

1. Полный набор escape-последовательностей; поведение при некорректной UTF-8 последовательности во входных данных.
2. Хранение stack trace при `raise`: часть значения ошибки или отдельный debug-канал?
3. `trap(fn, timeout: 5000)` — в MVP или только для FFI/сети позже?
4. Кросс-нодовые номинальные типы: `User`, объявленный на двух нодах, — один тип или два? Нужен ли реестр типов для распределённых акторов?
5. Совместимость версий записей при горячей перезагрузке — миграция состояния актора со старой схемы на новую.
6. Пакетный менеджер — вне языка, но формат манифеста и разрешение версий нужно определить до первого релиза stdlib.
7. Нужен ли отдельный литерал для `Set`, если `set(..items)` окажется неудобным на практике.
8. `type Color {}` без полей — номинальный маркер или алиас для Unit?
9. Паттерн в параметрах лямбды (`(:ok, v) -> expr`) — разрешён ли, или параметры лямбд только простые имена/кортеж имён.
10. Политика блокирующих операций (IO/FFI) и число потоков планировщика (M:N) — парк актора на таймере, пул для FFI.
11. stdlib `call` (фича 7A) — включать в реализацию, или request-per-actor (фича 7B) достаточно как единственная идиома.
