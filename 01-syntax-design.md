# Splink — консолидированный дизайн языка v0.2.0

Документ объединяет: исходный синтаксис, дополнение по равенству/видам записей и документ по обработке ошибок — и фиксирует решения, принятые по итогам ревью. **Заменяет все три предыдущих документа целиком.** Места, где решение v2 отличается от v1, помечены ⚠.

---

## 0. Принципы

1. Лаконичность без двусмысленности — сокращение допустимо, только если читатель угадает смысл.
2. Один способ для одной задачи.
3. Явное лучше неявного.
4. Отсутствие значения — всегда в типе: `Option`, `Result`, `()` как Unit. **`nil` в языке нет.**
5. Акторы — рантайм, модули — неймспейсы. Не смешивать.
6. Indent-driven для кода; скобки — для данных: `[]` списки, `()` кортежи, `{}` записи, `#[]` векторы, `%{}` мапы.
7. Функции сравниваются по identity; записи — гибридно, номинально или структурно (см. §2.10).
8. Overflow почтового ящика исключён **безусловно** — без запасных лазеек уровня «опасная версия».
9. `..` имеет одну идею («остаток / развёртка») во всех позициях, где применим (см. §3).
10. Примеры — валидный код, прогоняются через парсер.
11. VM гарантирует TCO для хвостовых вызовов.

---

## 1. Синтаксис блоков, отступы, комментарии

- Только пробелы, tabs запрещены. Пустые строки не закрывают блок. Отступ комментария не учитывается.
- Продолжение строки — по ведущему оператору (`|>`, `and`, `or`, `+`, `to`, `->` и т.п.).
- Скобки — для данных и вложенных выражений внутри выражения.
- Однострочная форма допустима только там, где однозначна (см. §7, §10.4).
- **Комментарии** — однострочные, `#` до конца строки. Многострочных нет.

⚠ Убрано целиком: правила многострочных лямбд из v1 (§12) — см. §4.2.

## 2. Литералы и типы данных

### 2.1 Числа

- `Int` — целое произвольной точности по умолчанию (как Python) — в динамическом языке тихое переполнение фиксированной ширины было бы отдельным классом багов.
- `Float` — IEEE754 double.
- `Decimal` — точная десятичная арифметика, stdlib, для денег. **(should have)**
- `Rational` — stdlib, не ядро. **(nice to have)**

### 2.2 Строки

- Интерполяция: `"Привет, \(name)!"` — открывается `\(`, закрывается `)`.
- Стандартные escape: `\n`, `\t`, `\\`, `\"`, `\(` для буквального `\(`.
- Строка — последовательность кодпоинтов UTF-8.
- Многострочный литерал: `"""..."""`, отступ первой закрывающей кавычки обрезается из каждой строки. **(should have)**
- `regex` — отдельный модуль stdlib, не в ядре. **(should have)**

### 2.3 Кортежи (Tuple) ⚠ новое

Фиксированной длины, гетерогенные, позиционные.

```splink
t = (1, "a", :ok)
(a, b, c) = t
```

Правила:

- `()` — пустой кортеж, он же **Unit** (замена `nil`, см. §2.9).
- `(x)` — просто группировка выражения, не 1-кортеж.
- `(x,)` — 1-кортеж, запятая обязательна (как в Python).
- `..` в паттерне кортежа **запрещён** — арность всегда фиксирована.
- Равенство — структурное: по длине и поэлементно.

Кортежи — стандартный способ передавать «тег + данные»: `(:work, payload)`, `(:ok, value)`, `(:error, reason)`. Это чинит место в v1, где `{ :work, data: [...] }` смешивал позиционный тег и именованное поле внутри одних и тех же `{}` — теперь роли разведены: `{}` только для именованных полей, `()` только для позиционных данных.

### 2.4 Списки (List) и паттерны

Persistent cons-list, без изменений по существу.

```splink
[1, 2, 3]
```

Паттерны:

```splink
[1, ..rest]        # хвост с именем
[1, 2, ..]         # хвост без имени
[1, 2, _]          # ровно 3, третий неважен
[1, 2, _, ..rest]
```

`_` — один любой элемент. `..`/`..name` — хвост, **только последним элементом, не более одного раза**. `.._` — синтаксическая ошибка. Конструирование (не паттерн) с `..` подчиняется другому правилу — см. §3.

### 2.5 Диапазоны — `to` ⚠ изменено

Слово вместо символов, по прецеденту `div`/`rem`/`and`/`or`. Убирает проблему v1 «`..` и `...` отличаются на один символ, требуют подсветки».

```splink
r = 1 to 10          # включительно с обеих сторон
nums = list(1 to 10)
```

Нисходящий диапазон — композицией, без нового слова:

```splink
(1 to 10) |> reverse()
```

`...` в языке больше не используется.

### 2.6 Vector ⚠ новое (коллекции — консультация)

Персистентный индексируемый вектор. Нужен, потому что cons-list даёт O(n) произвольный доступ, а заявленная ниша (бэкенд/веб) гарантированно требует O(1)/O(log n): JSON-массивы, пагинация, буферы.

```splink
v = #[1, 2, 3]
v[0]                  # 1; ошибка при выходе за границы
set(v, 0, 99)         # новый вектор, старый не изменён
push(v, 4)            # добавить в конец, O(1) амортизированно
length(v)
```

- Реализация: персистентная trie-структура (по образцу Clojure) — O(1) amortized append, O(log32 n) чтение/обновление. Совместимо с требованием «интерпретируемый язык», без мономорфизации.
- Отдельный литерал `#[...]`, а не переиспользование `[...]` — иначе один и тот же токен значил бы разное для List и Vector, что прямо нарушает принцип №1.
- Паттерн-матчинг — только по точной длине и поэлементно, **`..` не поддерживается**: rest-захват дорог для индексируемой структуры и плохо сочетается с идеей O(1)-доступа. Для рекурсивной обработки — используйте List.

### 2.7 Map ⚠ новое

Персистентная хэш-таблица, ключи — произвольные значения, вычисляемые в рантайме.

```splink
m = %{ "a" => 1, "b" => 2 }
m["a"]                # безопасный доступ -> Option
put(m, "c", 3)         # новый Map
```

Символ пары — `=>`, а не `:` как в записях: поле записи — идентификатор, известный при разборе; ключ Map — произвольное вычисляемое выражение. Разные роли — разный символ, без потери однозначности.

Pattern matching — **частичный**, в отличие от List/Tuple/Record:

```splink
match m
    %{ "a" => v } -> v   # достаточно наличия ключа "a"; остальные ключи неважны
```

Это единственное намеренное исключение из принципа «однозначный тотальный матч»: у Map, в отличие от списка/кортежа/записи, «полной формы» не существует — открытое множество ключей это часть определения типа, а не случайность (тот же выбор в Erlang/Elixir).

### 2.8 Set ⚠ новое

Персистентное множество. Без отдельного литерала — конструктор на вариадике (см. §4.3):

```splink
fn set(..items) -> ...
s = set(1, 2, 3)
```

Отдельный литеральный синтаксис можно добавить позже при явном спросе. **(nice to have)**

`Queue` — FIFO, Okasaki-очередь из двух списков, в stdlib, не языковая конструкция. **(nice to have)**

### 2.9 `nil` исключён ⚠ изменено

`nil` удалён целиком. Модель отсутствия значения:

- «Нет значения в домене» — `Option<T>` (`Some`/`None`).
- «Операция не удалась» — `Result<T, E>` (`Ok`/`Error`).
- «Функция не возвращает содержательного значения» — **`()`, Unit**, пустой кортеж. Не участвует в матчинге как замена `None`/`Error` — это другая категория.

Это закрывает главную дыру v1: `nil` был третьей, неспецифицированной категорией отсутствия. Теперь она — уже существующая конструкция (пустой кортеж), без нового имени и нового типа.

### 2.10 Записи: номинальные и анонимные

Модель — гибрид:

- `type User {...}` — **номинальная**: тег типа — часть значения.
- `{ key: value, ... }` — **структурная**, анонимная: равна по полям, без тега.
- Разные виды друг другу не равны.

```splink
User{ id: 1 } == User{ id: 1 }     # true
User{ id: 1 } == Admin{ id: 1 }    # false — разные типы
{ id: 1 } == { id: 1 }              # true
User{ id: 1 } == { id: 1 }          # false — разные виды
```

Pattern matching: номинальный паттерн матчит только тот же номинальный тип; анонимный — только анонимные записи. Порядок веток важен.

`fn greet(u: User)` не принимает ни другой номинальный тип, ни структурно похожую анонимную запись — защита от случайного смешения доменных сущностей.

Конвертация — только явная: `{ ..u }` (номинальная → анонимная), `User{ ..r }` (анонимная → номинальная).

Record update сохраняет вид: `User{ ..u, name: "Bob" }` остаётся `User`; `{ ..r, name: "Bob" }` остаётся анонимной.

Сериализация:

```splink
json.encode(User{ id: 1 })   # {"__type__": "User", "id": 1}
json.encode({ id: 1 })       # {"id": 1}
```

Type alias — структурно совместим с исходником: `type UserId = Int`. Номинальная обёртка — только через запись: `type UserId { value: Int }`.

Актёрные сообщения: с появлением кортежей — тег+данные передаём кортежем (`(:work, payload)`), а не смесью позиционного/именованного внутри `{}`. Именованные записи — когда сообщению нужна собственная предметная схема (`Work{ id: 1, retries: 3 }`).

### 2.11 Равенство — сводная таблица

| Вид                             | Равенство                 | Pattern matching      | Комментарий                                                    |
| ------------------------------- | ------------------------- | --------------------- | -------------------------------------------------------------- |
| `Int`/`Float`/`Str`/`Bool`/атом | по значению               | точное                | —                                                              |
| Функция                         | по identity               | —                     | `f == f` true; разные объекты, даже с идентичным телом — false |
| `Tuple`                         | структурно, длина+позиция | точное                | `..` запрещён                                                  |
| `List`                          | структурно, поэлементно   | точное или с `..rest` | O(n) сравнение                                                 |
| `Vector`                        | структурно, длина+позиция | точное, без `..`      | —                                                              |
| `Map`                           | по набору пар             | **частичное**         | единственное намеренное исключение                             |
| `Set`                           | по набору элементов       | по набору             | —                                                              |
| `{...}` анонимная               | структурно, по полям      | только с анонимными   | —                                                              |
| `type X {...}` номинальная      | по тегу + полям           | только с тем же `X`   | `X{...} != Y{...}` даже при идентичных полях                   |
| `()` Unit                       | единственное значение     | `()`                  | заменяет `nil`                                                 |

## 3. Оператор `..`: унифицированная семантика ⚠ закрывает противоречие v1

Одна идея — «остаток / развёртка» — работает по-разному в двух ролях:

**Связывание** (паттерн, деструктуризация — длина заранее неизвестна):

- Разрешён **только последним элементом, не более одного раза**.
- `[1, ..rest]` (список), `fn f(a, ..rest) -> ...` (параметры функции, §4.3).
- `Tuple` и `Vector` эту роль не поддерживают — их длина всегда известна.

**Конструирование** (построение значения — длина/содержимое уже известны):

- Разрешён **в любом количестве, в любой позиции**.

```splink
[0, ..xs, 99]                 # список: конкатенация
{ ..user, name: "Bob" }        # запись: наложение полей, позднее — приоритетнее
{ ..a, ..b, x: 1 }             # несколько спредов подряд — валидно
f(head, ..items, tail)         # вызов функции: развёртка списка в аргументы
```

Правило одной фразой: **связывание — `..` только в конце и один раз (неизвестная длина требует единственной точки неопределённости); конструирование — `..` где угодно и сколько угодно (длина уже известна, угадывать нечего)**.

## 4. Функции

### 4.1 Мультиклозные функции ⚠ новое

```splink
fn classify(0) -> "zero"
fn classify(1) -> "one"
fn classify(n) -> "many"
```

- Клозы одного имени/арности идут подряд.
- Первый подходящий паттерн выигрывает (как ветки `match`).
- Guards через `when`:

```splink
fn classify(n) when n > 0 -> "positive"
fn classify(0)             -> "zero"
fn classify(n)              -> "negative"
```

- Если ни один клоз не подошёл — автоматический `raise (:function_clause, args)` (см. §8.3).

Это заметно поднимает выразительность относительно v1, где диспетчирование по значению аргумента шло только через `match` внутри одного тела.

### 4.2 Анонимные функции — только однострочные ⚠ изменено

```splink
pow = x -> x**2
nums |> map(x -> x * 2)
```

Многострочных лямбд больше нет — весь набор правил v1 (где можно/нельзя в зависимости от переноса строки, а не от структуры AST) удалён целиком вместе с найденным противоречием. Тело больше одного выражения — выносится в именованную функцию:

```splink
fn transform(x) ->
    y = x * 2
    y + 1

result = nums |> map(transform)
```

Одновременно упрощает грамматику и делает код читаемым — логика всегда имеет имя.

### 4.3 Вариадические параметры и спред аргументов ⚠ новое

Тот же `..`, что у списков — параметр-остаток собирает лишние позиционные аргументы в `List`:

```splink
fn log_all(..args) ->
    args |> each(log)

log_all(1, 2, 3)     # args = [1, 2, 3]
```

Комбинируется с мультиклозностью (остаток — всегда последний параметр):

```splink
fn sum()          -> 0
fn sum(x, ..rest) -> x + sum(..rest)
```

Обратная операция — спред списка в аргументы вызова, по правилу конструирования из §3:

```splink
nums = [1, 2, 3]
sum(..nums)          # эквивалентно sum(1, 2, 3)
```

Новой грамматики не вводится — та же семантика `..`, что уже определена для списков и записей.

### 4.4 Приоритет `**`, равенство функций

Без изменений: `-x**2 = -(x**2)`, `2**3**2 = 2**(3**2)` (правая ассоциативность). Функции — identity equality; семантическое равенство — только через явные дескрипторы (`{module, function}`, теги).

## 5. Операторы

### 5.1 Логические — без изменений

`and`/`or`/`not`, `not > and > or`, short-circuit обязателен, всегда возвращают `Bool`.

⚠ Побочный эффект строгости: идиома `x = value or default` не работает (`or` возвращает `Bool`, не значение). Замена — функция stdlib, без нового оператора:

```splink
x = opt |> unwrap_or(default_value)
```

Так сохраняется принцип «один способ» и не добавляется символьный шум вида `??`/`||=`.

### 5.2 Арифметика — без изменений

`+ - * / **`, `div`, `rem` — инфиксные слова, приоритет как у `*`/`/`, левоассоциативны. `%` нет.

### 5.3 Сравнение ⚠ формализовано + решён конфликт с `<=` для send

v1 не фиксировал операторы сравнения явно. Теперь: `==`, `!=`, `<`, `>`, `=<`, `>=`.

Обратите внимание: **`=<`, а не `<=`**, для «меньше или равно» — как в Erlang, и по той же причине: `<=` занят под отправку сообщения (§10.3). Совпадение символа для двух разных операций было бы прямым нарушением принципа №1, а разводить по типам операндов (PID vs число) — тот самый контекстно-зависимый разбор, которого язык избегает. Erlang уже решал эту задачу — переиспользуем решение.

### 5.4 Pipe — без изменений

`x |> f(a, b)` → `f(x, a, b)`, без каррирования, продолжение цепочки по ведущему `|>`.

## 6. `if` — синтаксический сахар над `match` ⚠ закрывает пробел v1

`if` не существует в ядре языка. Парсер разворачивает его в `match` по булеву значению:

```splink
if ready
    start()
else
    wait()
```

≡

```splink
match ready
    true  -> start()
    false -> wait()
```

Без `else` — возвращает `()` (Unit):

```splink
if ready
    start()
```

≡

```splink
match ready
    true  -> start()
    false -> ()
```

Однострочная форма — только целиком, с обеими ветками (никаких «висячих» `if` в одну строку):

```splink
x = if ready then start() else wait()
```

`match`, в отличие от `if`, остаётся всегда блочным (§10.5) — `if` заранее известен как ровно два случая, а произвольный `match` с одной веткой почти всегда баг.

---

## 7. `with`/`else` ⚠ расширено — несколько bind'ов подряд

v1 показывал только один bind, чего объективно мало для главной идеи `with` — последовательной композиции `Result`-цепочек:

```splink
fn process(input) -> with
    Ok(a) <- validate(input)
    Ok(b) <- transform(a)
    Ok(c) <- save(b)
    Ok(c)
else
    Error(e) -> Error(e)
```

`<-` — bind, работает только внутри `with` (конфликт с отправкой сообщений снят конструктивно — `<-` больше нигде не встречается, см. §10.3). `else` покрывает все оставшиеся случаи, на одном уровне отступа с `with`.

## 8. Обработка ошибок

### 8.1 Result/Option — без изменений

```splink
type Result<T, E> { Ok(T), Error(E) }
type Option<T>    { Some(T), None }
```

`Option` — «нет значения», `Result` — «операция не удалась». Не смешивать.

### 8.2 `raise`/`trap` — без изменений по существу, примеры обновлены под кортежи

```splink
fn get_user(id) ->
    match db.find(id)
        Some(u) -> u
        None    -> raise (:not_found, id)
```

```splink
result = trap
    body = parse_body(req)
    user = authenticate(req)
    process(user, body)
```

`trap` создаёт границу: ловит любую ошибку внутри блока/лямбды, возвращает `Ok(v)` или `Error(e)`. Обе формы (`trap(fn -> ... end)` и блочная) остаются — это механическая элизия лямбды, тот же паттерн, что у именованных/анонимных функций везде в языке, а не дублирование «на вкус».

### 8.3 Автоматический `raise` при непокрытом варианте ⚠ распространено на мультиклозные функции

Правило v1 («непокрытый `match`/`with`/`recv` без `_`-ветки бросает автоматически») теперь явно распространяется и на мультиклозные функции (§4.1): если ни один клоз не подошёл — `raise (:function_clause, args)`. Один механизм на четыре конструкции — усиливает принцип «один способ» вместо добавления пятого отдельного правила.

### 8.4 Решения по открытым вопросам документа об ошибках

- **`ensure`/`defer`.** Ключевое слово внутри блока `trap`, выполняется на обоих путях — не отдельный механизм, часть `trap`:

```splink
result = trap
    file = open("data.txt")
    ensure close(file)
    process(file)
```

**(should have)**

- **Кросс-акторные ошибки.** По умолчанию ничего не видно — наблюдатель узнаёт о падении, только если явно подписался. Подписка — `monitor(pid)` (§10.2) присылает `(:DOWN, ref, pid, reason)` обычным сообщением в `recv`. Никакого неявного проброса через границу актора.
- **Ошибки в `spawn`.** Без `link`/`monitor` падение нового актора родителю не видно (как в Erlang). `splink` — падение уронит и родителя, если не поймано выше по дереву супервизии; `monitor` — падение придёт сообщением, родитель не падает.
- **`trap` внутри ветки `recv`.** Работает и является рекомендованной идиомой — не уронить актор из-за одного плохого сообщения (тот же приём, что в HTTP-хендлере, применим внутри любого `*_loop`).
- **Типы ошибок, stack trace, timeout для `trap`** — остаются открытыми, см. §15.

## 9. Модули и импорты ⚠ закрывает пробел v1

```splink
alias http.client as http
import json
```

- `import` — весь модуль под собственным именем.
- `alias ... as ...` — модуль под другим/сокращённым именем.
- Без `from x import y`: вызов всегда виден с квалификатором (`json.encode`, не голый `encode`) — не расшивает неймспейс, согласуется с «явное лучше неявного».
- `use`-инъекция макросов (как в Elixir) не вводится — метапрограммирование вне MVP.

## 10. Акторы

### 10.1 Модули vs Акторы — без изменений

Модули — неймспейсы без состояния и почтового ящика, синхронные вызовы. Акторы — процессы с PID, состоянием и почтовым ящиком, асинхронные сообщения. Не смешивать: `json.encode(x)` — вызов функции, не отправка сообщения.

### 10.2 Создание и связывание ⚠ убран `spawn_link`, добавлен `monitor`

```splink
pid = spawn(fn -> ... end)     # создать без связи
link(pid)                       # связать существующий
pid = splink(fn -> ... end)    # атомарно создать и связать
ref = monitor(pid)              # однонаправленно наблюдать, не падать вместе
```

`spawn_link` как отдельное имя убран — это было дублирование `splink` «на вкус», нарушение принципа №2. `splink` — единственный способ атомарно создать+связать; `spawn`+`link` по отдельности остаются для случаев, где связь не нужна сразу немедленно (окно между вызовами — тогда осознанный риск вызывающего, не языковая проблема).

`monitor(pid)` критичен для супервизоров (§11): супервизор, слинкованный с ребёнком, упал бы вместе с ним; супервизор, замониторивший ребёнка, получает сообщение и решает сам.

### 10.3 Отправка сообщений ⚠ `<=` вместо `<-`

```splink
worker <= :hello
worker <= (:work, data)
```

`<-` полностью освобождён под `with` (§7) — больше никакой контекстной эквилибристики парсера между «отправка» и «bind». Сопутствующее решение по сравнению — см. §5.3.

### 10.4 `recv` ⚠ `recv!` удалён — overflow исключён без исключений

```splink
recv
    (:value, v) -> v
    (:done)     -> :done
else msg
    log("unhandled: " + to_str(msg))
after 5000 -> :timeout
```

- `recv!` и модель «опасного» selective receive со stash — убраны из языка полностью. Гарантия «overflow исключён by design» (принцип №8) теперь верна безусловно, без пометки «кроме `recv!`» — закрывает главное противоречие v1.
- Оставлен только один синтаксис для необработанных сообщений: **`else msg`**. Второй вариант (`else pull msg`) убран — было дублирование одной семантики двумя словами ради вкуса, нарушение принципа №2.
- Однострочная форма — как в v1 (1 ветка, без `after`, без `else`):

```splink
x = recv (:value, v) -> v
```

⚠ Уточнение, которого не было в v1: если сообщение не совпало с единственной веткой в однострочной форме — оно молча удаляется из ящика, без логирования. Осознанный компромисс ради краткости идиомы «дождаться ровно одного сообщения»; нужна видимость несовпавших сообщений — используйте блочную форму с `else`.

**Плата за отказ от selective receive.** Если актору нужно обработать сообщения не в порядке прихода (частый паттерн в Erlang — «жду ответ на конкретный запрос, остальное пока отложи»), в Splink это не языковая фича, а прикладная идиома: актор сам складывает «неожиданные» сообщения в свой стейт и обрабатывает их позже.

```splink
fn worker_loop(state) ->
    recv
        (:reply, id, v) when has_pending(state, id) ->
            worker_loop(resolve_pending(state, id, v))
        (:reply, id, v) ->
            worker_loop(stash(state, id, v))   # отложили сами, явно
        (:stop) -> :ok
    else msg
        log("unknown: " + to_str(msg))
        worker_loop(state)
```

Многословнее Erlang-style selective receive, но полностью убирает риск неограниченного роста «отложенных» сообщений внутри рантайма — рост виден и ограничен структурой `state`, которую пишет разработчик, а не скрытым механизмом ящика.

### 10.5 `recv` vs `match`

Без изменений по существу: `match` — чистый, не блокирует, всегда блочный; `recv` — блокирует, имеет `after`/`else`. `if` (§6) живёт по тем же принципам, что `match`, не будучи отдельной языковой сущностью.

## 11. Супервизоры ⚠ закрывает блокирующий пробел v1

Минимальное ядро — `monitor` (§10.2); поверх него — стандартная библиотека, не языковая конструкция (согласуется с «модули = функции, не магия»):

```splink
sup = Supervisor.start(
    strategy: :one_for_one,
    children: [
        (:counter, fn -> splink(fn -> counter_loop(0) end) end, restart: :permanent),
        (:worker,  fn -> splink(fn -> worker_loop(0) end) end,  restart: :transient),
    ]
)
```

Под капотом `Supervisor` — обычный актор, который `monitor`-ит своих детей и перезапускает их по стратегии; грамматика языка ради этого не меняется.

## 12. Протоколы / Behaviors ⚠ новое

Без нового синтаксиса — запись с картой обработчиков + функция-диспетчер в stdlib:

```splink
KVBehavior = Behavior{
    handlers: %{ "get" => fn(state, key) -> ..., "put" => fn(state, key, val) -> ... }
}
pid = spawn_behavior(KVBehavior, init_state)
```

Диспетч по тегу верхнего уровня; если логика ветвится тоньше — внутри самого обработчика. **(should have)**

## 13. Архитектура рантайма ⚠ новое

- Интерпретатор — **байткод-VM**, не walking-интерпретатор по AST. Предсказуемая стоимость операций, площадка для TCO и честного планировщика.
- **TCO гарантирован** для самохвостовых и общих хвостовых вызовов — без этого бесконечные акторные циклы (`counter_loop(state)`) переполнили бы стек. Хвостовой вызов компилируется в переиспользование текущего кадра, а не в новый push.
- **Кооперативное планирование по «редукциям»** (по образцу BEAM): каждому актору отпускается лимит шагов VM перед принудительной передачей управления планировщику — честность между акторами без вытесняющей многопоточности и без блокировок, что и требуется акторной моделью.

## 15. Оставшиеся открытые вопросы

1. Полный набор escape-последовательностей; поведение при некорректной UTF-8 последовательности во входных данных.
2. `Decimal`: литеральный синтаксис (суффикс? `decimal("1.5")`?) — не решено.
3. Хранение stack trace при `raise`: часть значения ошибки или отдельный debug-канал?
4. `trap(fn, timeout: 5000)` — в MVP или только для FFI/сети позже?
5. Кросс-нодовые номинальные типы: `User`, объявленный на двух нодах, — один тип или два? Нужен ли реестр типов для распределённых акторов?
6. Совместимость версий записей при горячей перезагрузке — миграция состояния актора со старой схемы на новую.
7. Формат PID — закладывать ли node-идентификатор уже сейчас, до появления распределённости?
8. Пакетный менеджер — вне языка, но формат манифеста и разрешение версий нужно определить до первого релиза stdlib.
9. Нужен ли отдельный литерал для `Set`, если `set(..items)` окажется неудобным на практике.
10. `type Color {}` без полей — номинальный маркер или алиас для Unit?
