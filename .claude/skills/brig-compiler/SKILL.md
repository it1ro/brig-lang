# Brig — компилятор (`internal/compiler`)

Нормативный источник: `docs/02-register-based-virtual-machine.md` §3–7,
§12. Дизайн опирается на bump-аллокатор со стековой дисциплиной — НЕ
список свободных регистров (`freeRegs` сознательно не введён, см. §7).

## Инварианты аллокатора (I-1..I-4) — САМОЕ важное в этом модуле

Статус проверки: **I-1, I-3 и I-4 проверяются** автоматически
(`compileExpr` сверяет `nextReg`; `emit` — операнды и запись через A в
bound-регистр).

- **I-1.** `compileExpr` не меняет `nextReg` (стек-нейтральность):
  выделенные внутри временные регистры обязаны быть освобождены
  `releaseToMark(mark)` до выхода из функции.
- **I-2.** Аргумент `i` вызова лежит строго в `base+1+i` — это неявный
  контракт с `CALL`/`TAILCALL`; при генерации аргументов вызывать
  `fc.allocReg()` последовательно и проверять `r != base+1+i` (см.
  `compileGenericCall`, `compileGlobalCall`).
- **I-3.** После `bindLocal(r)` ни одна инструкция не пишет в `r` явным
  операндом `A`, кроме `MATCHLOCAL` (пишет неявно). Не выделять новый
  временный регистр поверх уже связанной локали. Проверяется в `emit`
  через `vm.RegUse`: если A входит в `writes` и `bound[A]`, то
  `fc.fail` с `I-3` (исключение — `MATCHLOCAL`).
- **I-4.** Любой регистр-операнд в `emit()` строго меньше `nextReg` —
  проверяется автоматически через `vm.RegUse` внутри `funcCompiler.emit`;
  если тесты падают с «reads/writes r%d >= nextReg» — это сигнал, что
  где-то регистр использован после `releaseToMark`.

**Правило работы:** каждый `compileXxx`, использующий временные регистры,
обязан начинаться с `mark := fc.nextReg` и заканчиваться
`fc.releaseToMark(mark)`. Копировать этот паттерн из соседних функций
(`compileBinary`, `compileIf`, `compileSeq`), а не изобретать заново.

## Соглашение о вызовах (§3)

- `CALL A B C`: callee в `R[A]`, аргументы в `R[A+1..A+B]`, результат в
  `R[C]`.
- `TAILCALL A B`: тот же layout без C — результат уходит через `callDst`
  вызывающего кадра, а не текущего.
- Native-функции получают **свежий слайс** аргументов (`append([]Value(nil),
  args...)`, K-5) — никогда не передавать окно регистров напрямую, иначе
  `runtime.List(args...)` будет удерживать общий backing-массив с
  регистрами кадра.

## dest / хвостовость (§7)

`dest{reg, tail}` передаётся вниз по дереву выражений. `d.tail == true`
означает «результат — значение функции, управление не возвращается»:
компилятор эмитит `TAILCALL` вместо `CALL`, финальный `RETURN` вместо
`MOVE`. Хвостовые позиции — см. таблицу в §4 дизайн-документа: последний
стейтмент тела `fn`/лямбды/локальной `fn`, обе ветки `if`, тело веток
`match`/`recv`, последний statement тела `with` и ветки `else`. Правый
операнд `and`/`or` **не хвостовой**: по design decision #41 (вариант A)
он проверяется на `Bool` после вычисления (холостой `JMPIF/JMPIFNOT acc, +0`, T-81), так что `CALL` в
`compileAndOr` правилен, а строка таблицы §4 doc 02, где он хвостовой,
правится в T-62. `fn loop(n) -> n == 0 or loop(n - 1)` растёт кадрами;
хвостовая форма — `if`. T-82 (#107) — won't-fix. **НЕ хвостовые:** RHS `let`, аргументы
вызовов, условие `if`, всё тело `trap` (включая случай без `ensure` — там
обработчик живёт в текущем кадре, замена кадра потеряла бы его).

**Не восстанавливать удалённую эвристику `isTailCall`** — хвостовость
определяется только через `dest.tail`, эвристика по паттерну инструкций
была источником багов и убрана намеренно (см. §4 changelog).

## trap / ensure (§5) — самая тонкая часть модуля

- Без `ensure`: `TRAPBEGIN dst handler` → тело в `dst` → `TRAPEND` →
  `MAKEOK dst dst`; на handler-пути — `MAKEERROR dst dst`.
- С `ensure`: используется **регистр-флаг** `fReg` (`Bool`), а не
  сравнение с атомом `:no_error` (это D-5 — сознательное исправление
  унаследованного бага, где `raise(:no_error)` в теле давало ложный
  `Ok(...)`). Ensure выполняются в обратном порядке (LIFO) относительно
  текста; каждый обёрнут собственным `TRAPBEGIN`/`TRAPEND`, поэтому
  падение одного `ensure` не мешает остальным отработать; побеждает
  **последняя** сработавшая ошибка — записывает `eReg` только сработавший
  handler.
- `TAILCALL` **никогда** не эмитируется внутри тела `trap`. Три слоя:
  тело `trap` компилируется с `val(dst)` (не хвостовой dest — структурная
  гарантия); `compileGenericCall`/`compileGlobalCall` делают
  `if d.tail && fc.trapDepth > 0 { fc.fail(...) }` (T-31 #20); `vm.Verify`
  проверяет `TAILCALL` вне `TRAPBEGIN..TRAPEND` (линейный счётчик). Если
  добавляете новую хвостовую позицию внутри тела `trap` — сначала
  проверьте, что она не входит в область активного `ensure`.
- **Ensure scope / registration (I-F5, T-37 #26):** ensure
  компилируются в области тела (до `popScope`); у каждого — свой
  Bool-флаг регистрации (`LOADK false` до тела, `LOADK true` в
  текстовой точке, `JMPIFNOT` перед исполнением). Парсер принимает
  только `ensure expr`; блочная форма и гибрид с блоком — ошибка
  парсинга (S-F5 / T-03 #3).

## Замыкания и upvalue (§7, D-4)

- `resolveUpvalue` рекурсивно поднимается по цепочке `parent`,
  регистрируя upvalue на каждом промежуточном уровне (не только в прямом
  родителе) — это D-4, настоящие вложенные замыкания. При добавлении
  новой формы, создающей область (`compileLambda`, локальные `fn`), не
  забыть прокинуть `parent` в `newFuncCompiler`.
- Захват — снимок по значению (K-7): лямбда всегда даёт `KindClosure`
  (даже с 0 захватов). Порядок разрешения имени: локаль → локальная `fn`
  (своя и все предки по цепочке `parent` → `GETGLOBAL` mangled) →
  upvalue → глобал (`compileVar`). Каждая лямбда получает уникальный
  префикс `prefix+"lambda$"+N+"$"` (`lambdaSeq`), чтобы одноимённые
  локальные `fn` в разных лямбдах одной функции не перезаписывали друг
  друга в `image.Functions` (A-F6, T-35 #24).

## Чек-лист перед коммитом правки компилятора

1. `compiler.Verify = true` уже включён в тестах пакета
   (`verify_on_test.go`) — не отключать. Сейчас на этапе `Compile` падают
   нарушения I-1 (`nextReg` в `compileExpr`), I-3 (запись в bound через A),
   I-4, `trapDepth` (TAILCALL под trap, T-31) и то, что видит `vm.Verify`
   (TAILCALL под trap, definite assignment — кроме тел веток
   `recv`/`after`, см. `brig-vm`).
2. Прогнать `make test-compiler` (узкий) и затем `go test
   ./internal/compiler/... -run TestBytecodeGolden` — если байткод
   изменился намеренно, `make update-bytecode`.
3. Прогнать полный список из `regvm_test.go` (D-1..D-5) — они защищают
   конкретные ранее найденные баги, не должны начать падать молча.
   Якорные тесты O-F2 (`TestTrapEnsureLifo`, `TestAndOr`, `TestLocalFn`,
   `TestClosure*` и др.) уже утверждают результат (T-30 #19); `runModule`
   прогоняет sema.Check после parse (T-46 #58). Новые тесты — только
   с утверждениями.
4. `TestTailRecursion` (10^6 вызовов) должен проходить быстро (секунды).
   Если тормозит — сначала проверить `--dump-bytecode`, есть ли реально
   `TAILCALL`, прежде чем оптимизировать что-то ещё.
5. При любой правке constant-pool логики (`konst`) — не убирать
   дедупликацию по `constKey` только для скаляров (Function/Decimal/Bytes
   осознанно не дедуплицируются).
