# Brig — общий контекст

Brig — язык с отступами (offside), неизменяемыми значениями, акторами и
TCO. Референсная реализация на Go: `lexer → parser → ast → sema →
compiler → vm`, без циклов зависимостей (`parser` не видит `vm`, `vm` не
видит `cmd/*`).

## Источники истины (по убыванию приоритета)

1. `docs/01-language-design.md` — единственный нормативный документ языка
   (v0.4.7). Part I — дизайн, Part II — формальная спецификация (EBNF,
   лексер, offside, диагностика), Part III — changelog.
2. `docs/02-register-based-virtual-machine.md` — дизайн регистровой VM,
   источник истины по опкодам, кадрам, TCO, trap/ensure.
3. `brig.ebnf` — исполнительная грамматика, синхронизирована с §A.
4. `docs/architecture.md` — слои, зависимости, текущий статус.
5. `STATUS.md` — рабочий чек-лист спринтов, НЕ нормативный.
6. `README.md` — обзор, наименее приоритетен.

**Правило:** если README противоречит `docs/`, а `docs/` противоречит
`docs/01-language-design.md` — верить более высокому по списку документу.
Перед любой правкой семантики языка — свериться с §0 (принципы) и
таблицей §16 (Must/Should/Nice/Не надо).

## Принципы §0 (нарушать нельзя без явного решения по дизайну)

1. Лаконичность без двусмысленности.
2. Один способ для одной задачи.
3. Явное лучше неявного.
4. `nil` в языке нет — Option/Result/Unit.
5. Акторы — рантайм, модули — неймспейсы. Не смешивать.
6. Indent-driven код, скобки — для данных.
7. Функции — identity equality; записи — гибридно.
8. Рост очереди виден (`mailbox_size`) и ограничен (HWM).
9. `..` — одна идея («остаток/развёртка») везде.
10. Примеры в докстроках — валидный код, гоняются через `check-examples`.
11. VM гарантирует TCO, кроме вызовов внутри активного `ensure`.
12. Единственное присваивание, shadowing разрешён между областями.
13. Иммутабельность — языковая гарантия.

## Структура репозитория

```
cmd/                    # brig (CLI), check-examples
internal/
  lexer/                # токены + offside
  parser/               # recursive descent → AST
  ast/                  # узлы, форматтер, Equal, visitor
  sema/                 # контекстный анализ (§F.3)
  compiler/             # AST → регистровый байткод
  vm/                   # регистровая ВМ + scheduler + прелюдия
  runtime/              # Value, Kind, Equal, Json, Serialize
  repl/                 # persistent REPL
  examples/             # A2-инструмент (check-examples)
docs/                   # спецификация, архитектура
examples/               # .brig-программы (make run-examples)
testdata/               # golden, bytecode, negative, fuzz-сиды
```

## Exit-коды CLI (`cmd/brig`)

- `0` — ok
- `1` — ошибка парсинга/sema
- `2` — runtime uncaught raise
- `3` — внутренняя ошибка / not implemented

## Что НЕ делать без явного запроса пользователя

- Не начинать новую крупную миграцию (типа Sprint 7) параллельно с другой
  большой задачей.
- Не менять AST-формы «попутно» с правкой байткода/VM.
- Не трогать `Regex` (§3.3) — отложен, ждёт решения по движку.
- Не переписывать `check-examples` целиком — 65/65 зелёный, не ломать.
- Не добавлять правила в `check-smallint` без необходимости.
- Не путать `Pos()/End()` в `ast.Node`: по факту это `(Line, Col)`, а не
  байтовые смещения (см. `sema.posOf`) — это исторический артефакт
  именования, не баг для исправления походя.

## Прежде чем предлагать план

1. Определить, какие подсистемы затрагивает задача, и подключить
   соответствующие skill-файлы (`brig-lexer`, `brig-compiler`, ...).
2. Проверить, не описано ли уже нужное поведение в §16 (Should/Nice/Не
   надо) — если да, явно сообщить пользователю статус фичи, а не
   реализовывать произвольно.
3. Для изменений семантики — сначала обновить `docs/01-language-design.md`
   (с пометкой `<!-- FIXED -->` или новым changelog-разделом по образцу
   существующих), потом код. Документ и код не должны расходиться.
