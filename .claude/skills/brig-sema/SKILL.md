# Brig — контекстный анализ (`internal/sema`)

Нормативный источник: `docs/01-language-design.md` Part II §F.3.
`sema.Check(prog)` возвращает `*Result` с `Diagnostic{Line, Col, Severity,
Message}`; `SeverityError` блокирует компиляцию, `SeverityInfo` — нет.

## Реализованные проверки (не дублировать, не удалять без согласования)

1. `trap` только как RHS `let_bind` или отдельный `expr_stmt` (§10.2) —
   иначе ошибка (`checkExpr` отвергает `TrapExpr`; вход через
   `checkExprAllowTrap` из `LetBind`/`ExprStmt`). Покрывает в том числе
   `x = 1 + trap(y)` и `if c then trap(y) else z` (I-F15, T-43 #32).
   Вложенный `trap` в теле другого `trap` допустим через `let`/`expr_stmt`
   внутри блока; идиома в ветке `recv` — блочная форма со стейтментом.
2. Pipe-запрет акторных примитивов (`send`, `spawn`, `spawn_linked`,
   `link`, `watch`, `unwatch`, `self`, `make_ref`, `mailbox_size`) как RHS
   `|>` — проверка по базовому имени до первой точки (`checkPipe`).
3. Variadic-параметр (`..name`) обязан быть последним в списке параметров
   — проверяется и для top-level `fn`, и для локальных `fn`, и для лямбд
   (`checkParams`).
4. Rebinding имени внутри одной лексической области — ошибка
   (`checker.bind`). Shadowing из вложенной области — разрешено, не
   ошибка.
5. Локальные `fn`-декларации обязаны идти в начале тела блока — если
   встречен `LocalFnDecl` после «обычного» стейтмента, это ошибка
   (`checkBlockBody`).
6. Shadowing имён прелюдии/встроенных вариантов (`Some`, `Ok`, `Error`,
   `None`, `map`, `filter`, ...) — **info**, не ошибка.

Sema обходит выражения внутри `InterpExpr` (`checkExpr`, S-F1 / T-53).
Guard'ы `recv` есть в AST (`RecvBranchArg.Guard`, S-F3 / T-02); `Walk`
их обходит. Тесты компилятора через `runModule`/`runModuleErr` прогоняют
`sema.Check` после parse (T-46 #58) — программа, которую отверг бы
`brig check`, падает и в этих хелперах.

## Модель областей видимости

`checker.scopes` — стек `map[string]binding`. Каждая новая лексическая
область (`fn`-тело, лямбда, ветка `match`/`recv`/`with`, блок `if`) должна
получать `pushScope()`/`popScope()` — если добавляете новую конструкцию с
собственной областью, не забудьте её обернуть, иначе rebinding-проверка
даст ложные срабатывания или пропуски.

Обратите внимание на асимметрию:
- `checkPatternBinding` — реально связывает идентификаторы (используется
  для `let`, параметров, `with`-байндов).
- `checkPattern` — только обходит паттерн для defensive-проверок, НЕ
  связывает имена (используется для веток `match`/`recv`/`with-else`,
  где паттерн локален для ветки и уже обёрнут в `pushScope` снаружи).

Не путать эти два метода при добавлении новой ветки анализа.

## posOf — историческая особенность

`posOf(n ast.Node)` возвращает `(n.Pos(), n.End())`, что по факту — это
`(Line, Col)`, а не байтовые смещения (из-за конструкторов AST, которые
передают `t.Line, t.Col` как `pos, end`). Не пытаться «исправить» это
в отрыве от AST-слоя — это согласованное соглашение по всему проекту.

## Чек-лист при добавлении новой проверки §F.3

1. Найти нормативную формулировку в `docs/01-language-design.md` (обычно
   в Part I рядом с описанием фичи, и продублировано в Part II §F.3 —
   таблица «Ошибки после парсинга»).
2. Решить: `SeverityError` или `SeverityInfo` — сверить с аналогичными
   существующими проверками, не изобретать новую политику произвольно.
3. Добавить проверку в `checker`, используя существующие `c.err(...)` /
   `c.info(...)` с текстом сообщения, включающим номер параграфа спеки
   (`(§X.Y)`) — это принятый в проекте стиль сообщений.
4. Добавить позитивный (`wantOK`) и негативный (`wantErr`/`wantInfo`)
   тест-кейс в `internal/sema/sema_test.go`.
5. Прогнать `go test ./internal/sema/...`.
6. Проверить, не нужно ли аналогичную проверку продублировать для
   локальных `fn`/лямбд отдельно от top-level `fn` — в текущем коде это
   частая причина «забытых» веток (см. `TestVariadicInLambda`,
   `TestVariadicInLocalFn` как образец полноты покрытия).

## Частые ошибки

- Добавить новую diagnostic-проверку, но забыть прогнать её и для
  `LambdaFull`/`LambdaShort`/`LambdaEmpty` — в `checkExpr` для лямбд
  область создаётся отдельно, легко забыть.
- Не учитывать, что `else`-имя в `recv` (`x.RecvElseName()`) связывается
  как алиас на регистр сообщения только в компиляторе (D-3); в `sema` оно
  просто биндится как обычное имя ветки — не пытаться синхронизировать
  этот механизм с компилятором, они решают разные задачи.
