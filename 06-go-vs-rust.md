# Rust вместо Go для Brig: что даёт интерпретируемая реализация

Важное уточнение: выбор host-языка (Go vs Rust) **не меняет дизайн языка** — синтаксис, семантику, акторную модель, single-binary. Меняется **рантайм**: GC, планировщик, память, таргеты, embedding. Но последствия глубокие, и для Brig они бьют ровно по тем местам, которые в дизайне ключевые.

## Преимущества Rust

### 1. Нет GC хоста — контроль над памятью

Go даёт world-class GC бесплатно, но ты им не управляешь. Rust не даёт GC вообще — ты выбираешь сам:

- **Arc + cycle collector** (Bacon–Rajan). Поскольку данные Brig иммутабельны, циклы редки — только через замыкания и ссылки на акторов. Это реалистичный путь.
- **Собственный tracing GC.** Точный, без консервативного сканирования, с tagged pointers/NaN-boxing. Rust знает layout — такой GC может быть **быстрее Go's**.
- **Арены на актора** для молодых объектов + shared heap для старых. Гибрид.

Go's GC не даёт такого контроля. В Rust ты решаешь: Arc, tracing, arena, hybrid.

### 2. Предсказуемая задержка

Go GC concurrent, но с write barriers и assist. Для edge/real-time это может быть проблемой. В Rust:

- нет GC-пауз вообще (если Arc) — ценой atomic refcount overhead;
- или GC с паузами, которые **ты контролируешь** (размер, частота, инкрементальность);
- или arena с детерминированным освобождением.

Для edge, где предсказуемость важнее throughput, это плюс.

### 3. Меньше бинарник, быстрее стартап

- Go: ~2–5 MB, startup ~1–10 ms (runtime init).
- Rust с `panic=abort`, LTO, `opt-level=z`, strip: ~1–3 MB, startup ~0.1–1 ms.

Для CLI и edge, где бинарник запускается часто, это заметно. Не радикально, но приятно.

### 4. no_std / embedded / RTOS

Go не компилируется на bare metal. Rust — да. Brig на микроконтроллере, на RTOS, на embedded Linux без glibc — всё это открывается. Для edge-ниши это **сильный** аргумент: Go здесь вообще не конкурент.

### 5. Wasm как first-class

- Rust → `wasm32-wasi`: нативный, маленький, быстрый.
- Go → wasm: большой (2–10 MB), медленный, с runtime.

Если Brig хочет работать в браузере, быть Wasm-плагином, исполняться в wasmtime/wasmer или компилировать Brig в Wasm — Rust радикально лучше. Это может стать killer-фичей: **Brig-as-Wasm**.

### 6. JIT/AOT путь

Rust: Cranelift, LLVM bindings, wasmtime. JIT для Brig — реалистичен. Go: JIT почти невозможен (runtime не позволяет), AOT — только транспиляция. Если Brig когда-нибудь захочет JIT, Rust — естественный дом.

### 7. FFI и embedding

Rust: C ABI, встраивание в C/C++/Python/Ruby — нативно. Go: CGO с overhead. Но embedding **в Go** — наоборот, Go проще. Если Brig позиционируется как «скриптинг для Go-приложений», Go выигрывает. Если как «встраиваемый язык вообще» — Rust.

### 8. Скорость интерпретатора

Rust обычно быстрее Go на интерпретаторных циклах:

- нет interface{} boxing;
- лучший контроль layout (SoA, cache-friendly);
- LLVM агрессивнее;
- можно использовать unsafe, computed goto, direct threading;
- нет GC-пауз в горячем цикле.

Реалистично: **1.5–3x** на типичных бенчмарках. Не 10x. Go-компилятор хорош.

### 9. Философское соответствие

Rust ownership + immutability ↔ Brig immutability. `Arc<T>` для shared immutable data — естественно. Borrow checker заставляет думать о lifetime данных — близко к тому, как Brig думает об иммутабельности. Концептуально Rust ближе к Brig, чем Go.

## Цена Rust

### 1. Планировщик акторов — строить самому

**Самое большое** последствие. Go: `1 актор = 1 goroutine` бесплатно. M:N, стек 2 KB, миллионы акторов, преемптивность с 1.14.

Rust: **нет** дешёвых green threads в std. Варианты:

- OS threads — дорого (~8 MB, миллионы невозможны).
- **async/await + tokio** — дёшево, M:N, work-stealing. Но async окрашивает код. Можно изолировать: VM-цикл внутри актора синхронный, `await` только на границе `recv`/`send`. Тогда tokio — это де-факто scheduler акторов. **Реалистичный путь.**
- **Собственный scheduler** (BEAM-модель, continuations, N OS threads × M акторов) — полный контроль, но месяцы-годы работы.
- **Bytecode VM с явными continuations** — акторы как состояния VM. Это и есть BEAM.

Все варианты, кроме async, — большая стройка. Go даёт это бесплатно.

### 2. GC для значений Brig — строить самому

Вторая большая стройка. Arc + cycle collector — просто, но atomic overhead. Свой tracing GC — быстро, но много работы. Арены + no collection — просто, но leak для долгоживущих. Гибрид — сложно. Go здесь выигрывает радикально.

### 3. Скорость разработки

Rust пишется медленнее. Borrow checker, lifetimes, async, unsafe-дисциплина. Для языка с REPL, компилятором, VM, stdlib, тулчейном — это годы дополнительной работы. Go пишется быстро; для MVP и итераций это критично.

### 4. Кросс-компиляция

- Go: `GOOS=linux GOARCH=arm64 go build` — из коробки.
- Rust: targets, linkers, musl, `cross`/`cargo-zigbuild`. Работает, но настройки больше.

### 5. Embedding в Go

Если Brig — Rust, встраивание в Go-приложения требует CGO + C ABI. Это противоречит «no C-ABI FFI» принципу, добавляет overhead и усложняет сборку. Если ниша — «скриптинг для Go», это серьёзный минус.

### 6. Команда и экосистема

Go-разработчиков больше, они дешевле. Rust-разработчиков меньше, дороже. Для open-source с контрибьюторами это важно.

## Ключевые архитектурные сдвиги

| Аспект         | Go                             | Rust                     |
| -------------- | ------------------------------ | ------------------------ |
| Акторы         | 1 = 1 goroutine, M:N бесплатно | tokio или свой scheduler |
| GC             | Go GC                          | Свой GC или Arc          |
| Бинарник       | 2–5 MB                         | 1–3 MB                   |
| Startup        | 1–10 ms                        | 0.1–1 ms                 |
| Embedded       | Нет                            | Да (`no_std`)            |
| Wasm           | Плохо                          | Отлично                  |
| JIT            | Нет                            | Cranelift/LLVM           |
| Embedding в C  | CGO                            | Нативно                  |
| Embedding в Go | Нативно                        | CGO                      |
| Скорость       | Хорошо                         | 1.5–3x лучше             |
| Разработка     | Быстро                         | Медленно                 |

## Гибридные варианты

1. **Ядро на Rust, embedding в Go через CGO.** Single-binary CLI на Rust, библиотека для Go через C ABI.
2. **Ядро на Go, Wasm-плагины на Rust.** Brig-на-Go, плагины компилируются в Wasm (Rust → Wasm), исполняются через wazero. Сохраняет Go-embedding и даёт Rust-плагины.
3. **Два рантайма: Go для встраивания, Rust для edge/embedded.** Один язык, две реализации. Дорого, но покрывает обе ниши.
4. **Rust + tokio для IO и акторов, свой GC.** Гибрид: tokio как scheduler, Arc + cycle collector для данных. Наиболее прагматичный Rust-путь.

## Когда что выбирать

**Go выигрывает, если:**

- Приоритет — скорость разработки и MVP.
- Ниша — embedding в Go-приложения.
- Нужны миллионы акторов дёшево.
- Wasm/embedded не критичны.
- Команда — Go-разработчики.

**Rust выигрывает, если:**

- Приоритет — производительность и контроль.
- Ниша — edge/embedded/RTOS.
- Wasm — first-class.
- JIT/AOT — в планах.
- Embedding в C/C++/Python.
- Готовность строить scheduler и GC.
- Команда — Rust-разработчики.

## Рекомендация

Для **текущего дизайна** (single-binary, edge, акторы, Go-embedding) Go — прагматичный выбор. Он даёт M:N и GC бесплатно, что для акторного языка — огромный выигрыш. Rust заставит строить и то, и другое.

Но есть **стратегический** аргумент за Rust:

- **Wasm-first** (Brig-as-Wasm-плагин, Brig-в-браузере, Brig-на-edge-Wasm) — Rust радикально лучше.
- **Embedded/bare-metal** — Rust единственный вариант.
- **JIT** в будущем — Rust естественный дом.
- **Философское соответствие** ownership + immutability — Rust ближе.

Компромисс, который я бы рассмотрел:

> **Ядро и single-binary CLI — на Rust. Embedding в Go — через CGO, как опциональный модуль. Wasm-плагины — first-class, на Rust → Wasm. Планировщик — tokio для MVP, свой BEAM-подобный на continuations для продакшена. GC — Arc + cycle collector для MVP, свой tracing GC позже.**

Это дороже, но даёт embedded, Wasm, JIT-путь, производительность, философское соответствие и single-binary — и сохраняет Go-embedding как опцию, а не как основную нишу.

**Итог:** Rust даёт контроль, производительность, embedded, Wasm и JIT-путь, но заставляет строить scheduler и GC, замедляет разработку и усложняет Go-embedding. Для MVP Go прагматичнее. Для долгосрочной стратегии с edge/embedded/Wasm — Rust сильнее.
