# 10. Пакеты и пакетный менеджер (утверждено 2026-09-27)

Пакетный менеджер — подкоманды `brig`, не отдельный бинарник (инвариант
«один файл»). Реестр/индекс — **Chandler** (рабочее имя; *ship chandler* —
поставщик снаряжения для судов).

## Утверждённые решения

| # | Решение |
|---|---|
| 1 | Пакет — **только исходники на Brig**: без Go/C и без предкомпилированного байткода. Байткод кэшируется локально |
| 2 | **URL — канонический идентификатор пакета**, живёт только в манифесте. Код импортирует имена модулей (`import Calmar.Router`), поэтому переезд репозитория = правка одной строки манифеста |
| 3 | **Vanity-адреса**: `brig.dev/calmar` отдаёт meta-тег → git-URL (как `go-import`) |
| 4 | **Подкаталоги монорепозиториев**: `github.com/org/repo/libs/json`, теги `libs/json/v1.2.0` |
| 5 | **Псевдоверсии** для нетегированных коммитов: `v0.0.0-20260927-abc123` |
| 6 | Разрешение версий — **Minimal Version Selection** |
| 7 | **Одна версия пакета на сборку**; две мажорные версии одного пакета — ошибка с объяснением от `brig why` |
| 8 | Пакет объявляет корень модулей в своём `project.brig`; **совпадение корней у разных пакетов — ошибка** разрешения. Монтирование под другим именем — после первого релиза |
| 9 | Манифест `project.brig` (Brig-литералы), lock-файл `project.lock` (Brig-литералы, отсортирован, sha256 нормализованного дерева исходников) |
| 10 | Глобальный content-addressed кэш `$XDG_CACHE_HOME/brig/pkg/<hash>`, `brig vendor` → `deps/`, флаг `--offline` |
| 11 | **Никаких install-скриптов.** Макросов нет ⇒ сборка зависимости не исполняет её код |
| 12 | **Права пакетов — как в Deno**: пакет объявляет нужные возможности (`Net`, `File`, `Proc`, `Env`, `Signal`…); I/O в Brig идёт только через порты, поэтому проверка естественна для VM. Реализация — после MVP |
| 13 | **Chandler — необязательный индекс и кэширующий прокси**: короткие имена → URL + хеш; однажды увиденная версия хранится навсегда (защита от удалённых репозиториев и перезаписанных тегов). Протокол — статический индекс поверх HTTPS; легко зеркалить |
| 14 | Короткое имя (`brig add calmar`) — только удобство в момент добавления: **в манифест всегда пишется канонический URL** |
| 15 | Офлайн-снапшота пакетов в `brig` **нет**: первое добавление требует сети; офлайн закрывают кэш и `vendor` |
| 16 | Позже: публичный журнал хешей (как Go sumdb) и подписи (sigstore) |

## Команды

| Команда | Что делает |
|---|---|
| `brig add URL[@версия]` | добавить зависимость в `project.brig`, обновить lock |
| `brig remove URL` | убрать зависимость |
| `brig fetch` | скачать всё по lock-файлу в кэш (CI, первый клон) |
| `brig update [URL]` | поднять версии (явно, MVS сам ничего не поднимает) |
| `brig vendor` | скопировать зависимости в `deps/` |
| `brig why URL\|Модуль` | почему пакет/модуль в сборке, кто требует какую версию |
| `brig install URL[@версия]` | собрать пакет-утилиту в один исполняемый файл в `~/.local/bin` |
| `brig uninstall NAME`, `brig install --list` | управление установленными утилитами |
| `brig publish` | (с появлением Chandler) проверить пакет и отправить в индекс |

Формы адреса:

```text
brig add github.com/vendor/library            # последний semver-тег
brig add github.com/vendor/library@v1.4.0     # конкретная версия
brig add github.com/vendor/library@main       # ветка/коммит → псевдоверсия
brig add github.com/org/monorepo/libs/json    # подкаталог монорепо
brig add brig.dev/calmar                      # vanity-адрес
brig add calmar                               # позже: короткое имя через Chandler
```

## `calmar new` — глобальная команда фреймворка (утверждено)

Ничто не мешает: это прямое следствие `brig install` и «приложение = один файл».

```text
$ brig install brig.dev/calmar        # один раз; кладёт ~/.local/bin/calmar
$ calmar new lookout                  # скаффолд проекта
$ cd lookout && calmar server         # dev-сервер с перезапуском и страницей ошибок
$ calmar gen resource Monitor name:str url:str interval_ms:int
$ calmar routes
$ calmar db migrate
```

**Единственная реальная проблема — рассинхрон версий.** Глобальный
`calmar` (например, 0.3) и Calmar, зафиксированный в lock-файле проекта
(например, 0.2), — разные версии. Если `calmar gen` из 0.3 сгенерирует код
для проекта на 0.2, код не соберётся. Так же и с рантаймом: `calmar`
собран с одной версией `brig`, а проекту может требоваться другая.

**Решение — `calmar` как лаунчер (приём Rails binstubs / npx / Gradle wrapper):**

| Где запущен | Что делает |
|---|---|
| вне проекта | исполняет свою встроенную версию: `calmar new` (генерирует проект под свою версию и пишет её в манифест) |
| внутри проекта (найден `project.brig` с зависимостью Calmar) | делегирует `brig` из PATH с версией Calmar **из lock-файла проекта** (`brig fetch` при необходимости); команды берутся из `pub fn commands()` пакета |
| внутри проекта без Calmar в зависимостях | ошибка с подсказкой `brig add brig.dev/calmar` |

Так у пользователя одна форма вызова — `calmar …` — а версии всегда
согласованы с проектом. Механизм общий: любой пакет-утилита может
экспортировать `commands()` и стать лаунчером (миграции БД, генераторы
клиентов OpenAPI и т.д.).

Что нужно от `brig`:
1. `brig install` (утверждено).
2. Конвенция `pub fn commands()` в пакете и API для лаунчера:
   `Toolchain.project_root()`, `Toolchain.locked_version(url)`,
   `Toolchain.exec(args)` — стабильный контракт между `brig` и утилитами.
3. Правило поиска проекта: вверх по каталогам до `project.brig`.
