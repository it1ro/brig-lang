# 19. Производительность как метрика (утверждено 2026-09-27)

Brig — интерпретатор; «достаточно ли он быстр для веба» — первый вопрос
скептиков. Без набора бенчмарков нечем подтвердить оптимизации, заметить
регрессии и закрыть решения, отложенные «до замеров»: модель heap (11),
изменяемая VM-таблица (B3), N:M (R10).

## Решения

| Вопрос | Решение |
|---|---|
| Набор | **три уровня**: микро — опкоды VM, вызовы и TCO, паттерны, `send`/`recv`, `await`, native-вызовы; макро — HTTP hello, JSON, запросы к SQLite, рендер шаблона, SSE (сценарии TechEmpower); память — замеры Z1–Z6 из 11, включая `--copy-on-send` |
| Регрессии | микро — в каждом PR в `main`: `benchstat` против базы, статистически значимая регрессия > 5 % — красный статус; макро и память — ночью на выделенном раннере, история сохраняется |
| Цели | **относительно соседей + абсолютные полы**. На одном железе, I/O-сценарии: не хуже Rails, ≥ 50 % Phoenix. Полы: RSS hello-сервера ≤ 64 МБ, старт ≤ 20 мс, p99 пауз GC ≤ 10 мс, бинарник ≤ 25 МБ |
| Публичность | публичный дашборд с историей; участие в TechEmpower — после web-MVP |

## Что где живёт

| Что | Где |
|---|---|
| микро-бенчмарки VM | `internal/vm/*_bench_test.go` (Go `testing.B`), цель `make bench` |
| макро-сценарии | каталог `bench/` в репозитории: приложения на Brig + нагрузочный клиент (Go), цель `make bench-macro` |
| сравнение с соседями | те же сценарии на Rails и Phoenix в `bench/peers/`, прогон на том же раннере |
| история и дашборд | результаты ночных прогонов — JSON в отдельной ветке или хранилище; статическая страница с графиками |

## Как это закрывает отложенные решения

| Решение | Какой замер решает |
|---|---|
| модель heap (11) | Z3 (паузы GC под нагрузкой), Z4 (`--copy-on-send`), Z6 (ARM) |
| изменяемая VM-таблица (B3) | макро-сценарий «горячий кэш» на шардированных акторах |
| N:M (R10) | макро-сценарии при насыщении одного ядра |
| тяжёлые native в пуле (R15) | латентность соседних запросов во время входа с argon2 |
