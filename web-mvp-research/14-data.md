# 14. Доступ к данным: data mapper в духе Ecto (утверждено 2026-09-27)

## Решение

- **Подход — data mapper в духе Ecto** (путь rom.rb по духу, без его
  многоисточниковости). ActiveRecord отвергнут: он противоречит
  иммутабельности (§0.13), требует скрытого I/O при чтении поля (ленивые
  связи) и неявных колбэков (§0.3).
- **Размещение — отдельный пакет после MVP** (рабочее имя `Query`), не
  внутри Calmar: им пользуются Whelk, скрипты и генераторы Calmar.
- **MVP** — как есть: `Sql` из stdlib, SQL-строки с параметрами,
  `Sql.to_record` (06, демо `repo.brig`).

## Принципы

| Принцип | Как выражается |
|---|---|
| Запрос — **неизменяемое значение** | строится функциями через pipe, компонуется (фильтры из формы, пагинация, скоупы — обычные функции `Query -> Query`) |
| I/O — **только в `Repo`** | выполнение запроса — актор-пул через порты и `await(ref)` (02/R12); построение запроса чистое |
| Результат — **номинальные записи** | маппинг по `Type.fields` (03/L11), контракты проверены на границе (09) |
| Связи — **только явный `preload`** | ленивой загрузки нет ⇒ N+1 невозможен по построению |
| Незагруженная связь — **вариант, не `nil`** | `checks: Assoc<List<Check>>` = `NotLoaded` \| `Loaded(list)`; паттерн-матчинг заставляет обработать |
| Запись — **через changeset** | `Monitor.changeset(params) \|> Repo.insert()` → `Result`; правила — `validate/1` (09) |
| Запасной выход — **SQL** | `Query.sql("… ? …", [params])`; миграции остаются SQL-модулями |

## Как выглядит (без макросов и перегрузки операторов)

Ecto строит условия макросами (`where: m.status == ^s`). В Brig их нет,
поэтому **условие — запись**, где форма значения задаёт оператор
(утверждено 2026-09-27):

| Значение поля | SQL |
|---|---|
| литерал | `=` |
| `List` | `IN` |
| `Range` (`5_000 to 60_000`) | `BETWEEN` |
| `Q.lt(x)`, `Q.gt(x)`, `Q.lte(x)`, `Q.gte(x)`, `Q.like(s)`, `Q.not(v)` | `<`, `>`, `<=`, `>=`, `LIKE`, `NOT …` |

```brig
alias Query as Q

pub fn failing(since) ->
    Monitor
        |> Q.from()
        |> Q.where({ status: :down, last_checked_at: Q.lt(since) })
        |> Q.order_by([(:desc, :last_checked_at)])
        |> Q.preload(:checks, Check |> Q.from() |> Q.limit(10))
        |> Repo.all()

# Скоуп — обычная функция Query -> Query
pub fn active(q) -> q |> Q.where({ interval_ms: Q.lte(60_000) })
```

Имена полей сверяются с `Type.fields` при построении запроса (опечатка —
сразу, а не в SQL); значения всегда уходят параметрами. `OR` и сравнение
двух полей — `Q.any([cond, …])` и `Q.sql(…)`; если этого окажется мало —
кандидат в язык `quote`-лямбды (03/L23).

Связи объявляются данными в модуле типа (конвенция «модуль типа», 03/L6):

```brig
pub fn relations() ->
    %{ :checks => Rel.has_many(Check, :monitor_id) }
```

Несколько шагов в одной транзакции — `with` внутри
`Repo.transaction(fn -> …)` или пайплайн шагов-данных (аналог `Ecto.Multi`).

## Чего не делаем

- Многоисточниковость rom.rb (HTTP, YAML как «relations») — главный источник
  его сложности; для HTTP есть свой клиент.
- Ленивые связи, identity map, колбэки жизненного цикла.
- Собственный язык запросов поверх строк (как HQL/JPQL).

## Что потребуется

| Что | Где |
|---|---|
| компилятор запроса в SQL на адаптер (SQLite, Postgres) | пакет `Query` |
| `Assoc<T>` = `NotLoaded` \| `Loaded(T)` | пакет `Query` (вариантный тип) |
| `Type.fields`, `Type.schema` | 03/L11 |
| `validate/1`, `Check`, `Changeset` | 09 |
| `Repo` как актор-пул с `await(ref)` | `Sql` из stdlib + 02/R12 |

## Открытое

- Имя пакета: рабочее `Query`; в резерве морских имён подходит, например,
  *Hold* (трюм — где хранится груз). Решить при старте работ.
- Вводить ли в язык `quote`-лямбды (03/L23) — решить при проектировании
  пакета по реальным запросам.
