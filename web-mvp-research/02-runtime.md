# 02. Рантайм: что должна уметь VM

Всё здесь — **механизмы**. Политика (HTTP, супервизор, пулы) — Brig-код.
Уровни: **M** = Must для web-MVP, **S** = Should, **N** = Nice.

## Текущее состояние (факты)

- Планировщик: один кооперативный run-loop (`internal/vm/scheduler.go`),
  таймеры `recv … after` (`nextDeadline`/`wakeExpired`), `Spawn/Send/Watch/Unwatch`.
- I/O: только `print`/`eprint`/`log`. Ни fs, ни сети, ни времени.
- Нет примитива завершения чужого актора; `link` ≡ `watch`.
- Когда все акторы ждут — прогон завершается; внешних источников событий нет.

## R1. Внешние события в планировщике — M

**Сценарий:** любой сокет, файл, подпроцесс, сигнал ОС.
**Требование:** run-loop получает события из потокобезопасной inject-очереди.
Go-сторона I/O — goroutine на ресурс (использует netpoller Go), которая
по готовности кладёт сообщение в очередь → оно доставляется владельцу.
Когда ready-очередь пуста, run-loop блокируется на
`select { таймер | inject | сигнал ОС }`, а не завершается.

**Следствия для спеки:**
- Детекция «все заблокированы → выход» меняется: выход только когда `main`
  завершился и нет живых портов (или явный `Sys.halt`).
- Новая гарантия G5: «события порта доставляются владельцу в порядке их
  возникновения на ресурсе; относительно сообщений других акторов порядок
  не гарантирован». §15.4 — I/O вводится как второй (после wall-clock)
  источник недетерминизма.
- Native-вызовы не блокируют: никакой прелюдийной функции, которая ждёт ОС.
  Всё ждущее = «попросить порт» + `recv`.

## R2. Порты — M

**Сценарий:** TCP-сервер, HTTP-клиент, чтение файла потоком, subprocess.
**Модель:** порт — opaque-значение нового вида `Port` (как `Pid`/`Ref`:
identity-равенство, место в term order после `Ref`, не сериализуется).
У порта ровно один **владелец** (актор). Смерть владельца → порт закрыт.
Смерть порта (ошибка ОС) → владелец получает сообщение.

**Backpressure — только pull (active-once):**

```brig
Tcp.request(sock)                 # взвести: "пришли одну порцию"
recv
    (:tcp, s, data) when s == sock -> ...
    (:tcp_closed, s) when s == sock -> ...
    (:tcp_error, s, reason) when s == sock -> ...
after 30_000 -> :idle_timeout
```

Почему только pull: push-режим упирается в HWM (порт не может получить
`Error(:busy)` и подождать), а pull делает очередь видимой и ограниченной
(§0.8) без новых механизмов. Один режим — §0.2.

**Владение:** `Tcp.accept` возвращает пассивный сокет; `Port.give(sock, pid)`
передаёт владение; события начинаются только после `request` нового
владельца → гонки «данные пришли не тому» нет.

**Запись:** `Tcp.send(sock, iodata)` — синхронно кладёт в буфер порта и
возвращает `Ok(())` / `Error(:busy)` при переполнении буфера записи
(та же семантика, что `send` при HWM) / `Error(:closed)`. `iodata` =
`Bytes | Str | List<iodata>` — ответы собираются без конкатенаций.

**HTTP-порты (решение B2): транспорт — Go `net/http`, семантика — Brig.**
`HttpServer` принимает соединения, TLS, HTTP/1.1 и HTTP/2 в горутинах Go
(вне run-loop, на других ядрах) и присылает владельцу
`(:http_request, req_port, head)` на каждый запрос. `req_port` — порт
запроса: Go-горутина владеет `ResponseWriter` и исполняет команды Brig
(`read_body` в pull-режиме, `send_head`, `write(iodata)`, `flush`,
`finish`). Отключение клиента (отмена контекста) → `(:http_closed,
req_port)`. Обязательно: лимит одновременных запросов на стороне Go
(сверх — `503` без участия Brig), безопасные таймауты по умолчанию
(`ReadHeaderTimeout`, `IdleTimeout`, `MaxHeaderBytes`, лимит тела),
нормализация поведения Go (заголовки, `100-continue`, `HEAD`) в `Conn`.
`HttpClient` — `net/http.Client` (HTTP/2, пул, прокси, TLS); вызов =
команда порту + `await(ref)` (R12). Порт запроса — интерфейс: `net/http`
— одна реализация, in-memory — другая (тесты, симуляция). WebSocket —
HTTP/1.1 upgrade. HTTP/3 — отложен.

Уточнение принципа для спеки: *сложные протоколы с проверенной
Go-реализацией (TLS, HTTP/1.1, HTTP/2, HPACK) допускаются в Go-native
stdlib, если наружу отдают только порты и сообщения; VM о них не знает.*

Порты web-MVP: `Tcp` (listen/accept/connect/request/send/close/shutdown),
`Tls` (обёртка над `Tcp`, Go `crypto/tls`), `File` (open/read-chunk/write),
`Proc` (subprocess: stdin/stdout/stderr как порты, exit-статус сообщением),
`Signal` (SIGTERM/SIGINT/SIGHUP → сообщение подписанному актору). Позже:
`Udp`, `Serial`, `Gpio` (embedded).

## R3. Сигналы актору: `exit(pid, reason)` — M

**Сценарий:** супервизор гасит детей при shutdown/`:one_for_all`;
актор запроса завершается по дедлайну; graceful shutdown всего дерева.
**Семантика (утверждено, Q-exit):** асинхронно; жертва завершается в ближайшей
точке редукции/ожидания; `ensure` жертвы **выполняются** (закрытие ресурсов);
наблюдатели получают `(:down, ref, reason)`. `exit(pid, :kill)` —
без `ensure`, для зависших. Причина — любое значение. `exit` не
перехватывается `trap`; мягкая остановка — сообщение `(:shutdown, deadline)`,
которое актор обрабатывает сам, `exit` — следующий шаг после дедлайна.
Без этого супервизор на Brig невозможен (см. обсуждение ядро vs библиотека).

## R4. Атомарный spawn + watch — M

`spawn_watched(fn) -> (pid, ref)`. В однопоточном run-loop гонки нет, но при
N:M появится; фиксируем контракт сейчас, чтобы не менять API потом.

## R5. Реестр имён — M

**Сценарий:** `Repo`, `PubSub`, `Endpoint` должны находиться без протаскивания
PID через все вызовы; перезапущенный супервизором актор получает новый PID.
**Требование:** `register(name, pid)`, `whereis(name) -> Option<Pid>`,
авто-снятие при смерти. Имя — **любой терм** (`:repo`, `(:checker, 42)`).
Это механизм VM (гонки при перерегистрации и снятие при `:down` должны быть
атомарны). `send` по имени **нет** — только явный `whereis` (Q-reg).

## R6. Таймеры — M

`recv … after` — таймаут **пустого ящика**, он сбрасывается каждым
сообщением. Периодическая работа (health-check каждые 30 с) при потоке
других сообщений на `after` не строится. Нужны:
`Timer.send_after(ms, pid, msg) -> Ref` и `Timer.cancel(ref)`. Реализуются на
той же куче таймеров, что `after` (G4 распространяется).

## R7. Время — M

`Time.monotonic_ms()` (окна рестартов, дедлайны, метрики),
`Time.now()` → UTC-инстант (заголовок `Date`, логи, `created_at`).
Сам тип даты/времени — см. 03/04.

## R8. Лимиты и изоляция — M (уточнено в [11](11-memory.md))

- Бюджет «хода» актора (редукции и байты между двумя `recv`) в child spec;
  превышение → `exit(pid, :resource_limit)`, дальше решает супервизор.
- Счётчики на актор (`Actor.info`), `GOMEMLIMIT` + актор-сторож.
- При встраивании — лимиты на экземпляр рантайма, не на актор.
- Модель heap (общий vs на актора) — по замерам до 1.0.
- Учёт native-вызовов в редукциях (уже T-58) — большие операции над `Bytes`
  не должны надолго занимать run-loop.

## R9. Детерминированный режим и симуляционное тестирование — S (стратегическая цель, B4)

Фейковые часы (`Time`/`Timer`/`after` от виртуального времени) и
in-memory транспорт (порт запроса и `Tcp` без сокетов) → интеграционные
тесты без сети и `sleep`, воспроизводимые. Поверх — `brig test --simulate
--seed N`: подключаемая политика планировщика (случайные, но
воспроизводимые чередования), инъекция сбоев в порты (задержка, обрыв,
отказ), падения акторов; упавший прогон воспроизводится тем же seed.

Требования-инварианты:
- **весь** недетерминизм идёт через VM: время, случайные числа
  (`Crypto.random_bytes` детерминирован в режиме симуляции), I/O;
- однопоточный детерминированный режим (`schedulers=1`) сохраняется
  **навсегда**, в том числе после N:M.

## R10. N:M — N (после MVP)

Один run-loop = одно ядро. Для веб-MVP приемлемо (Node живёт так же);
при переходе к N:M гарантии G1–G5 сохраняются. Не блокирует фреймворк,
если API R2–R5 спроектированы без допущения однопоточности.

## R11. Встраивание (Go-хост) — S

Стабильный Go-API (`pkg/brig`, 05): `brig.New(brig.Options{…})`,
`rt.Compile(name, src)`, `rt.Call(mod, fn, args…)`, регистрация host-функций
и host-портов; лимиты на экземпляр — 11/M4.
Нужно и для embedded-ниши, и для тестов самого фреймворка.

## R12. Ожидание ответа по ref, не трогая остальной ящик — M (главная находка)

**Проблема.** Selective receive запрещён (§16), `recv` берёт сообщения по
порядку. Значит, **любая библиотечная функция, которая внутри делает
`recv`** (`Http.Client.get`, `Server.call`, `Sql.query`, `Tcp.recv`),
вызванная из актора со своим протоколом, съест его чужие сообщения
(`:tick`, `(:call, …)`, события PubSub) или упадёт на них. Идиома «сложи
неожиданное в стейт» (§12.4) тут не работает: библиотека не знает стейта
вызывающего. В demo это чекер: пока идёт HTTP-запрос, в ящик приходит
`:tick`. Без решения синхронный клиент невозможен, и весь stdlib
придётся писать в стиле «верни управление в мой цикл», т.е. колбэками.

**Решение (Q-await): `await(ref, timeout)` — ref-слоты.** Сообщение, отправленное
как `reply(pid, ref, value)` (или событие порта, взведённого с ref), попадает
не в общий ящик, а в слот этого ref; `await` ждёт только его. Это O(1),
без сканирования очереди и без паттернов → не selective receive в смысле
§16 (нет скрытой очереди, нет O(n) сканов). Ref-слот живёт до `await` или
таймаута; поздний ответ отбрасывается. Ящик и HWM не затрагиваются.
Это ровно то, что в Erlang оптимизируется как «receive по свежему ref».

Следствие: `Server.call`, `Http.Client`, `Sql` синхронны для вызывающего и
не ломают его протокол; `recv` остаётся для собственных сообщений актора.
`Server.call` передаёт серверу `from = (pid, ref)`, и `Server.reply(from, v)`
≡ `reply(pid, ref, v)`. Внести в §12/§16 — задача `edit-spec`.

## R13. Именованные неизменяемые значения — S

`Config.get(:checks)`, скомпилированный роутер, секреты: читаются из
любого актора, пишутся один раз на старте (или редко). Сейчас пришлось бы
держать актор-хранилище и делать `call` на каждое чтение.
**Решение (B3):** `Global.put(name, value)` / `Global.get(name) -> Option`
(аналог `persistent_term`): значение иммутабельно, shared heap делает
чтение бесплатным. Это не мутабельное состояние языка — меняется только
привязка имени, как у реестра R5.

**Кэши с частой записью (B3):** аналога ETS нет. Сессии, rate limiting,
горячие кэши — библиотека на Brig из шардированных акторов
(`Cache.start({ shards: 16 })`, ключ → шард по хешу); `Global` — для
редко меняющегося. Изменяемая VM-таблица рассматривается только по
данным бенчмарков и через DD (противоречит §0.13).

## R14. VM без ОС-зависимостей — M (B6)

Всё ОС-специфичное (сокеты, файлы, сигналы, процессы) — только в
реализациях портов. Ядро VM компилируется под `js/wasm` без правок:
песочница в браузере (S, вскоре после релиза языка), WASI-приложения (N).

## R15. Тяжёлые native-операции — вне run-loop — M (18)

Native-вызовы редукций не тратят (K-4), а run-loop один. Операция на
десятки миллисекунд CPU (argon2id при входе, bcrypt, хеш большого файла,
сжатие, разбор большого JSON) замораживает **все** акторы. Такие функции
stdlib исполняются в пуле Go-воркеров: вызывающий актор отдаёт задачу и
ждёт через `await(ref)` (R12), остальные акторы работают. Критерий «тяжёлая»
— документируется у функции (и/или порог по размеру входа). Связано с T-58
(учёт native-вызовов в редукциях).
