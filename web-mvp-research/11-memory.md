# 11. Память и изоляция (B7)

## Вводные (опрос 2026-09-27)

| Вопрос | Ответ |
|---|---|
| Сценарий | **веб первым, embedding не закрывать** — только обратимые решения |
| Общий heap vs heap на актора | **отложить до замеров** |
| Превышен лимит ресурсов | **убить (`exit(pid, :resource_limit)`), дальше решает супервизор** |
| Чужой код в процессе | **лимиты на экземпляр рантайма** при встраивании; многоарендность серверов — процессами |

## Исходная реальность

1. **VM написана на Go и живёт на Go GC.** Heap на актора в смысле BEAM
   (свой GC на каждый актор, копирование при `send`) означает **собственный
   аллокатор и сборщик мусора внутри Go** — по объёму это отдельный
   проект, сравнимый со всей текущей VM. Это главный практический аргумент
   за «отложить».
2. **При общем heap точный лимит памяти на актора невозможен**: одно
   неизменяемое значение может разделяться многими акторами, «владельца» у
   него нет. Возможны только счётчики аллокаций и оценки.
3. **Go GC конкурентный** — паузы обычно доли миллисекунды, цена —
   CPU-оверхед и рост RSS при высокой скорости аллокаций. Для веба это
   приемлемо; для слабых embedded-устройств — вопрос замеров.
4. **HWM уже ограничивает ящики** (§0.8) — самый частый источник
   неограниченного роста памяти в акторных системах закрыт.

## Что делаем сейчас (не зависит от выбора модели heap)

### M1. Бюджет «хода» актора — M

**Ход** — работа актора между двумя `recv` (обработка одного сообщения).
Бюджет задаётся в child spec супервизора:

```text
{ id: …, start: …, restart: :transient,
  limits: { turn_reductions: 5_000_000, turn_alloc_bytes: 64_000_000 } }
```

- VM считает редукции и выделенные байты с начала хода; сбрасывает на `recv`.
- Превышение → `exit(pid, :resource_limit)` с деталями
  `(:resource_limit, (:turn_alloc_bytes, used, limit))`; дальше обычная
  политика рестартов (ответ опроса).
- Почему «ход», а не «всё время жизни»: долгоживущий актор законно
  аллоцирует гигабайты за сутки; ненормален **один** ход, который не
  заканчивается (бесконечный цикл, взрыв данных). Бюджет хода ловит именно
  это и не мешает нормальным акторам.
- Дефолты: без лимитов для обычных акторов; Calmar/Whelk ставят разумный
  бюджет актору запроса (плюс дедлайн запроса по wall-clock через `exit`).

### M2. Счётчики на актор — M

`Actor.info(pid)` → `{ reductions, alloc_bytes_total, alloc_rate, mailbox,
state_size_estimate }`. Видно в observer, метриках, логах падений.
`state_size_estimate` — периодический сэмпл обхода состояния с лимитом
стоимости обхода; при общем heap это **верхняя оценка** (разделяемые
значения считаются у каждого).

### M3. Процесс целиком — M

- `GOMEMLIMIT` из флага/конфига (`--memory-limit 256MiB`);
- актор-сторож в stdlib: при приближении к лимиту логирует топ акторов
  по `alloc_rate` и, если включено, завершает самых прожорливых
  (`exit(pid, :memory_pressure)`) — решение снова за супервизорами.

### M4. Экземпляры рантайма при встраивании — S

При встраивании в Go-хост изолируем **экземпляры `brig.Runtime`**, а не
акторы (ответ опроса):

- у каждого экземпляра свой run-loop и свои счётчики;
- `rt.Call(fn, args, brig.Limits{Reductions, AllocBytes, Timeout})` и
  лимиты на экземпляр целиком;
- превышение → экземпляр останавливается, все его акторы завершаются,
  ссылки отпускаются → Go GC освобождает память;
- условие чистоты: **значения не утекают между экземплярами** — хост
  получает сконвертированные значения или непрозрачные хэндлы, а не
  внутренние указатели.

Ограничение, которое надо честно написать в документации: это **мягкая**
изоляция. Быстро аллоцирующий экземпляр давит на общий Go GC, пока его не
остановят по счётчику. Жёсткие гарантии — только отдельный процесс.

## Что сохраняем обратимым (чтобы heap на актора остался возможным)

Решение отложено, значит нельзя закладывать в язык то, что сделает его
невозможным потом:

| Инвариант | Почему | Статус |
|---|---|---|
| **Семантика `send` — значение, а не ссылка**: копирование или разделение ненаблюдаемы | при копировании программа не должна измениться | следует из иммутабельности (§0.13); зафиксировать в §12.3 явно |
| **Спека не обещает O(1) `send`** | иначе переход сломает ожидания производительности | зафиксировать в §15.4 (производительность не гарантируется) |
| **Identity функций — не адрес в памяти** | функции сравниваются по identity (§0.7); после копирования замыкания identity должна сохраниться | ввести стабильный id замыкания в VM |
| **`Global` и реестр — отдельная область** | при heap на актора им нужна общая неизменяемая область (как `persistent_term` в BEAM) | держать их API без обещаний про разделение памяти |
| **Большие `Bytes` — отдельный вид хранения** | при копировании нужны refc-бинарники вне heap (как в Erlang) | `Bytes` уже отдельный вид; не смешивать с общим представлением |
| **Хост-API не отдаёт внутренние указатели** | нужно и для M4, и для будущей смены heap | правило для `pkg/brig` (R11) |

## План замеров (что решит вопрос heap)

| # | Замер | Зачем |
|---|---|---|
| Z1 | RSS пустого `brig` и hello-сервера | бюджет embedded |
| Z2 | память на простаивающего актора (100k акторов) | WebSocket/SSE-нагрузка, embedded |
| Z3 | p50/p99 паузы и CPU-доля GC под веб-нагрузкой при heap 0.5 / 2 / 8 ГБ | нужен ли свой GC вообще |
| Z4 | пропускная способность `send` для маленьких и больших сообщений **с экспериментальным флагом `--copy-on-send`** (глубокое копирование при отправке) | цена BEAM-семантики без переписывания GC |
| Z5 | утечка в одном акторе: время до обнаружения и завершения по M1–M3 | достаточно ли мягкой изоляции |
| Z6 | те же Z1–Z3 на ARM-плате с 256–512 МБ | embedded-ниша |

**Триггеры пересмотра** (в пользу heap на актора или гибрида):

- p99 пауз GC на целевой нагрузке мешает SLO (ориентир > 10 мс), и
  настройкой `GOGC`/`GOMEMLIMIT` это не лечится;
- embedded-сценарий требует жёсткого лимита на компонент, а M1–M3 его не
  дают (Z5/Z6);
- при переходе к N:M конкуренция за общий GC становится узким местом;
- Z4 показывает, что копирование дешевле ожидаемого на типичных
  сообщениях — тогда цена изоляции ниже, чем кажется.

Если ни один триггер не сработал к 1.0 — общий heap становится
окончательным решением, а §15.1 перестаёт быть «временным».

## Итог

- **Сейчас:** M1 (бюджет хода + `exit` по превышению), M2 (счётчики),
  M3 (`GOMEMLIMIT` + сторож) — всё это в рамках общего heap.
- **Для встраивания:** M4 — лимиты на экземпляр рантайма.
- **Обратимость:** шесть инвариантов выше фиксируются в спеке и VM.
- **Решение о модели heap:** по замерам Z1–Z6 и триггерам, до 1.0.
