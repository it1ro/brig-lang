# 13. Brig для микросервисов

## Вердикт

По форме поставки и модели исполнения Brig подходит микросервисам хорошо,
местами лучше мейнстрима. Сильнее всего — **I/O-bound сервисы**:
внутренние API, шлюзы, воркеры очередей, webhooks, edge-сервисы,
sidecar-агенты. Слабее — CPU-bound нагрузка и сервисы, которым нужен
богатый готовый SDK (облачные API, Kafka-тяжёлые пайплайны), пока нет
пакетов.

## Сильные стороны

| Свойство | Что даёт микросервису |
|---|---|
| один статический файл | образ `FROM scratch` на 15–20 МБ, нет рантайма и уязвимых базовых слоёв, быстрый pull при автоскейлинге |
| старт за миллисекунды | быстрый rolling deploy, scale-to-zero |
| один run-loop = одно ядро | в Kubernetes под на 1 vCPU — норма; масштаб репликами. HTTP-транспорт в Go (B2) и так разбирает протокол и TLS на других ядрах |
| акторы + супервизия | ретраи, circuit breaker, пулы, консьюмеры — обычные акторы; упал консьюмер — перезапуск, сервис жив |
| graceful shutdown = `recv` сигнала | SIGTERM от оркестратора обрабатывается явно; drain запросов (C6) |
| `Result` вместо исключений | сетевые ошибки видны в коде |
| батарейки | HTTP/1.1 + HTTP/2, JSON, TLS, авто-HTTPS, логи, конфиг из env — 12-factor без зависимостей |
| контракты (09) | `decode_as` на границе, экспорт OpenAPI/JSON Schema, дифф схемы в CI |

**«Микросервисы внутри процесса».** Акторы — изолированные компоненты,
общающиеся только сообщениями. Разумный путь: модульный монолит на Calmar
→ вынос компонента в отдельный сервис, когда это действительно нужно;
граница по сообщениям уже есть.

## Риски и ответы

| Риск | Ответ |
|---|---|
| **Дрейф контрактов** без статических типов | решено гибридом code-first (09): типы Brig — истина, проверка на границе, экспорт схем, импорт чужих OpenAPI/protobuf |
| **Экосистема клиентов**: пакеты только на Brig (10/#1) — каждый протокол пишется заново | первая волна — Postgres (D2); затем NATS и Redis (текстовые протоколы, дёшево), S3 и OpenTelemetry (поверх `HttpClient`); gRPC и Kafka — дорого, позже |
| **CPU-bound нагрузка** — интерпретатор проиграет Go/JVM | позиционирование: I/O-bound; тяжёлые вычисления — отдельный сервис на другом языке |

## Что нужно сверх web-MVP

| Что | Уровень | Заметка |
|---|---|---|
| health/readiness-эндпоинты | M | `/healthz`; readiness — из состояния дерева супервизии |
| метрики Prometheus | M | `Metrics` (04) поднять из S в M для микросервисного профиля |
| OpenTelemetry-трейсинг | M | у акторов нет thread-local ⇒ **контекст трейса передаётся явно**: поле `trace` в `Conn`, в сообщениях — конвенция записи `{ trace: ctx, … }` или хелпер `Trace.send(pid, msg)`; поддержка в `Http`, `Server.call`, `Sql` без шума в пользовательском коде |
| HTTP-клиент с ретраями, таймаутами, circuit breaker | M | актор-пул над `HttpClient` (B2) + `await(ref)` (R12) |
| NATS-клиент | S | самый дешёвый брокер |
| импорт OpenAPI/protobuf | S | 09 |
| gRPC | N→S | HTTP/2 уже даёт Go-транспорт (B2); остаются protobuf-кодек и генерация |
| прозрачные удалённые акторы между нодами | не делать в MVP | node-поле в PID зарезервировано, но между сервисами — явный HTTP или брокер: сеть не прячем |

## Решения (2026-09-27)

- **Контекст трейса — явно:** поле `trace` в `Conn`; в сообщениях —
  конвенция и хелперы; `Http`, `Server.call`, `Sql` пробрасывают контекст
  сами. VM не меняется, всё видно в коде (§0.3).
- **`calmar new --api`** — шаблон для сервисов без HTML: без шаблонов,
  сессий и CSRF, с БД, миграциями, контрактами и экспортом OpenAPI.
  Whelk — для совсем маленьких сервисов в одном файле.
