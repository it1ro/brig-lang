# Разбор вариантов (обоснование)

## Q-await. Как библиотеке ждать ответа, не съедая чужие сообщения (02/R12)

| Вариант | + | − |
|---|---|---|
| A. Ничего не менять; все клиенты асинхронные, ответ приходит в `recv` вызывающего | язык не трогаем | колбэк-стиль в каждом клиенте, `Server.call` невозможен, фреймворк некрасивый |
| B. Вернуть selective receive (`recv` пропускает несовпавшие) | привычно по Erlang | противоречит §16, скрытая очередь, O(n) сканы, теряется видимость HWM |
| **C. `await(ref, timeout)` + ref-слоты** | O(1), ящик не трогается, синхронные клиенты, узкий механизм | новый примитив VM; правка §12/§16 через DD |
| D. Каждый синхронный вызов — во временном акторе-посреднике | без новых примитивов | посредник сам ждёт ответ через `recv` → проблема та же для вызывающего |

**Решение: C.** (как рекомендовано)

## Q-mod. Модули и типы как значения (03/L5)

| Вариант | + | − |
|---|---|---|
| **A. `UPPER_IDENT`-путь → значение `Module`/`Type`, операции `Module.apply`, `Type.fields`** | нужно уже для MFA в §13.1; роутер, Repo, «модуль типа» | новый вид значения (term order, сериализация как имя) |

| Вариант | + | − |
|---|---|---|

## Q-fw. Вшивать ли фреймворк в бинарник — решено: отдельный пакет (2026-09-27)

**Вводная от автора:** пакетный менеджер нужен в любом случае — без него
язык не выживет. Значит, главный довод за вшивание («нет пакетов — нет
способа доставить фреймворк») отпадает. Остаются только **офлайн-первый
запуск** и **целостность «из коробки»**.

| Вариант | + | − |
|---|---|---|
| A. Calmar вшит в `brig` как stdlib | `brig new web` офлайн; одна версия — нет матрицы совместимости | фреймворк релизится только с языком; баг в роутере ждёт релиза языка; stdlib распухает; у пакетов появляется «привилегированный» сосед — плохой сигнал экосистеме |
| B. Calmar — обычный пакет | независимые релизы; dogfooding пакетного менеджера с первого дня; конкурирующие фреймворки на равных | первый `brig new web` требует сети; матрица «версия brig × версия Calmar» |
| **C. Обычный пакет + предзаполненный кэш в `brig`** | Calmar — полноценный пакет (версии, lock, обновления через `brig deps update`), но `brig` везёт снапшот нескольких «благословлённых» пакетов (Calmar, Postgres-драйвер) как запись в кэше; `brig new web` офлайн | размер бинарника +~1 МБ (исходники/байткод); нужно правило, какие пакеты получают место в снапшоте |
| D. Отдельный бинарник `harbor` | чистое разделение | нарушает «один файл», второй инструмент |

**Предварительная рекомендация была C; итог — B**: Calmar — обычный пакет, без офлайн-снапшота в `brig`. Граница stdlib проходит по
принципу «механизмы и протоколы» (`Http`, `Sql`, `Supervisor`, `PubSub`,
`Log`, `Config`) — стабильно, медленно меняется. «Мнения» (роутер,
контроллеры, шаблоны, генераторы, соглашения каталогов) — пакет
Calmar. Снапшот в бинарнике — удобство первого запуска, а не особый
статус: он перекрывается любой версией из lock-файла.

**Подвопросы (закрыты: команды — задачи `tasks/` и лаунчер `calmar` (16), компилятор шаблонов — в `brig`):**
1. Критерий попадания в снапшот (официальные пакеты организации? лимит размера?).
2. Генераторы (`brig new web`, `brig gen resource`) — это код Calmar. Как
   `brig` их вызывает (итог: задачи в `tasks/` пакета, 16; было: `Calmar.Cli.commands()`), а
   `brig <cmd>` ищет команды в зависимостях проекта (как `mix` tasks)?
3. Шаблоны `.html.bt`: компилятор шаблонов — в тулчейне (общий формат для
   всех фреймворков) или в Calmar (плагин тулчейна)? Предложение: формат и
   компилятор — в `brig` (иначе нужны плагины компилятора), хелперы — в Calmar.

## Q-reg. Реестр имён (02/R5)

- Ключ: только атом или любой терм? **Любой терм** (demo: `(:checker, id)`), как `Registry` в Elixir.
- `send(name, msg)` по имени? **Нет**: `whereis(name)` → `Option<Pid>` явно (§0.3); отсутствие получателя видно в коде.

## Q-exit. Семантика `exit(pid, reason)` (02/R3)

- Выполняются ли `ensure` жертвы? **Да** для любого reason, кроме `:kill`.
- Можно ли перехватить `exit` через `trap`? **Нет** — иначе супервизор не
  сможет гарантировать остановку. Для graceful — отдельное сообщение
  `(:shutdown, deadline)`, которое актор обрабатывает сам; `exit` —
  следующий шаг после дедлайна.
