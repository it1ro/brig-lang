# Part I: Language Design

## 0. Principles

1. **Лаконичность без двусмысленности** — сокращение допустимо, только если читатель угадает смысл.
2. **Один способ для одной задачи.**
3. **Явное лучше неявного.**
4. **Отсутствие значения — всегда в типе:** `Option`, `Result`, `()` как Unit. **`nil` в языке нет.**
5. **Акторы — рантайм, модули — неймспейсы.** Не смешивать.
6. **Indent-driven для кода; скобки — для данных:** `[]` списки, `()` кортежи, `{}` записи, `%[...]` векторы, `%{...}` мапы. Offside-блоки активны и внутри бракетных литералов.
7. **Функции сравниваются по identity**; записи — гибридно, номинально или структурно.
8. **Рост очереди видим** (`mailbox_size`) и ограничен (HWM, по умолчанию 10 000, настраивается при `spawn`). Переполнение — `Error(:busy)` у отправителя и событие `[:vm, :mailbox, :hwm]`; ящик получателя не растёт сверх порога. Скрытых stash-механизмов уровня языка нет.
9. **`..` имеет одну идею** («остаток / развёртка») во всех позициях, где применим.
10. **Примеры — валидный код**, прогоняются через парсер, сгенерированный из Part II.
11. **VM гарантирует TCO** для хвостовых вызовов, в том числе внутри `trap` с `ensure`: кадр заменяется, а невыполненные `ensure` хранятся компактной записью в куче (O(1) кадров, O(n) памяти на n уровней `ensure`, `docs/02-register-based-virtual-machine.md` §5.1).
12. **Единственное присваивание:** имя связывается один раз в **лексической области**. Rebinding внутри области запрещён. Вложенная область может затенять имя внешней (shadowing). В REPL и в script-файле каждая top-level инструкция — новая top-level область (§11.3, §11.4).
13. **Иммутабельность — языковая гарантия.** Все значения неизменяемы; «изменяющие» операции коллекций (`Vec.set`, `Map.put`) возвращают новое значение. Мутация — только через замену состояния актора.

## 1. Lexical Structure

### 1.1 Пробелы и комментарии

- В отступах разрешены **только пробелы**. Табуляция в отступах — ошибка лексера.
- Пустые строки и строки, содержащие только комментарии, не влияют на offside.
- Комментарии — однострочные, `#` до конца строки. Отступ комментария не учитывается.
- `##` синтаксически — тот же однострочный комментарий: лексер не выделяет его отдельно и не строит из него AST-узел. Это текстовое соглашение для doc-комментариев (§11.7), которое использует `brig test` для доктестов (§11.6).

### 1.2 Идентификаторы

```text
LOWER_IDENT ::=
    [a-z] [a-zA-Z0-9_]* ["?"]
  | "_" [a-z] [a-zA-Z0-9_]* ["?"]

UPPER_IDENT ::= [A-Z] [a-zA-Z0-9_]*

WILDCARD    ::= "_"
```

**Допустимые:** `x`, `foo`, `ready?`, `done?`, `true?`, `_msg`, `_unused`.

**Недопустимые:** `_1`, `_Foo`, `x?y`, `_`.

Правила:

- `_` — только wildcard, не идентификатор.
- `_msg`, `_unused` — **именованный wildcard**: лексически это `LOWER_IDENT`, в паттерне и параметре совпадает с чем угодно, как `_`, но **не связывается**. Имя только документирует, что игнорируется. Обращение к `_name` в теле — ошибка контекстного анализа (§F.3).
- `?` допускается только как **последний** символ идентификатора.
- `x?y` — ошибка лексера.
- Ключевые слова без финального `?` не являются `LOWER_IDENT`.
- `done?`, `true?`, `if?` — допустимые `LOWER_IDENT`.

### 1.3 Ключевые слова

```text
fn match cond recv with else if then after when alias import module type ensure
trap and or not div rem to true false as pub quote
```

`raise`, `assert` — функции прелюдии, не keywords.

- `pub` — видимость функции модуля (§11.2).
- `quote` — **зарезервировано**: продукций в грамматике нет, семантика будет задана отдельным решением (research 21, RFC-0001). Как имя `quote` использовать нельзя; атом `:quote` допустим (§1.4).

Реализация резерва в лексере — T-132.

### 1.4 Атомы

```text
ATOM ::= ":" atom_body
```

где `atom_body`:

- начинается с `[a-z]`;
- может совпадать с ключевым словом;
- может заканчиваться `?`;
- не может начинаться с `_`;
- не может быть `UPPER_IDENT`.

**Допустимые:** `:ok`, `:none`, `:not_found`, `:if`, `:and`, `:true`, `:false`, `:ready?`, `:done?`.

**Недопустимые:** `:_`, `:_foo`, `:Foo`.

### 1.5 Поведение `:`

| Ситуация                     | Токенизация                           |
| ---------------------------- | ------------------------------------- |
| `:ok`                        | `ATOM(:ok)`                           |
| `:if`                        | `ATOM(:if)`                           |
| `a:b` (после идентификатора) | `LOWER_IDENT(a) COLON LOWER_IDENT(b)` |
| `{a:b}`                      | record field                          |
| `::`                         | `COLON COLON`                         |
| `:_foo`                      | `COLON` + обработка `_foo`            |
| `:Foo`                       | `COLON UPPER_IDENT(Foo)`              |

Правило: если предыдущий токен — `LOWER_IDENT`, `UPPER_IDENT`, `)`, `]`, `}`, то `:` всегда эмитируется как `COLON`. Иначе, если следующий символ `[a-z]`, читается `ATOM`.

### 1.6 Зарезервированные слова и особые токены

- Одиночный `%` без `[` или `{` — ошибка лексера.
- `..` — один токен, не два `.`.
- `%[` и `%{` — один токен каждый.
- `?` не является оператором.
- `;` в языке отсутствует.

## 2. Offside and Blocks

### 2.1 Общие правила

- Только пробелы в отступах; табуляция запрещена.
- Пустые строки не закрывают блок.
- Отступ комментария не учитывается.
- **Offside внутри бракетных литералов.** Внутри `(...)`, `[...]`, `{...}`, `%[...]`, `%{...}` переносы строк разрешены без оператора-продолжения. Элементы разделяются **запятой или переносом строки**; висячая запятая перед закрывающей скобкой разрешена.

### 2.2 Продолжение строк

Продолжение строки — по ведущему оператору, **закрытый список**:

```text
|> and or * / ** div rem to == != < > <= >= .. <>
```

Оператор-продолжение обязан быть первым токеном строки; отступ строки-продолжения — строго больше отступа первой строки стейтмента. `<>` — конкатенация строк (§7.3a). `<-` из списка убран: его позиция полностью фиксирована грамматикой `with`.

`+` и `-` в списке **нет**: строка, которая начинается с `-` (или `+`), — новый стейтмент, `-y` — унарный минус. Длинную сумму переносят внутри скобок, оператором в конце строки (§D.5):

```brig
fn f(x) ->
    y = x
    -y

fn total(a, b, c) ->
    (a +
        b -
        c)
```

### 2.3 Скобки и вызовы

- **Пробел перед `(` незначим.** `f (a, b)` ≡ `f(a, b)` — вызов с двумя позиционными аргументами.
- Скобки после идентификатора (или после `.name`, `[...]`) — **всегда** список аргументов вызова.
- Чтобы передать кортеж одним аргументом — **двойные скобки**: `f((a, b))`.
- Пробел внутри и снаружи `(`, `[`, `{` декоративен.

### 2.4 Якоря offside-блоков

Для **всех** блочных конструкций — `fn`, `match`, `recv`, `with`, `if`, `trap` — единое правило, вне скобок и внутри них (§2.5):

```text
base_indent = stmt_indent — отступ первой строки логического стейтмента,
              содержащего блочную конструкцию
```

Тело блока — на отступе строго больше `base_indent`. Колонка токена-открывателя (`trap`, `fn`, `match`, …) в строке роли не играет.

Отдельного правила для `trap` **нет**: `ensure` — это `trap_item` внутри `INDENT`-блока `trap` (см. §10.3 и грамматику в A), а не клауза после `DEDENT`. Все `trap_item` (включая `ensure`) находятся на отступе, строго большем, чем `base_indent`.

Пример:

```brig module
fn main() ->
    result = trap
        f1 = open("a.txt")
        ensure close(f1)
        f2 = open("b.txt")
        ensure close(f2)
        process(f1, f2)
    result

# хелперы примера
fn open(path) -> path
fn close(_f) -> ()
fn process(a, b) -> (a, b)
```

Здесь `base_indent` — 4 (отступ строки `result = trap`), тело и ensure-клаузы — на отступе 8 > 4. То, что `trap` стоит в колонке 14, не важно.

### 2.5 Offside внутри скобок

Если внутри `%{...}`, `[...]`, `(...)` встречается один из блоков (`fn`, `match`, `recv`, `with`, `trap`, `if`), лексер открывает **изолированный offside-мини-блок** с собственным стеком отступов и `paren_depth`. Якорь мини-блока — по §2.4: `stmt_indent` стейтмента, внутри которого стоят скобки, а не колонка открывателя. После завершения блока внешний скобочный контекст восстанавливается.

```brig
fn main() ->
    ys = Enum.map([1, 2], fn (x) ->
        y = x * 2
        y + 1)
    ys
```

Здесь `base_indent` мини-блока — 4 (строка `ys = Enum.map(…`), тело лямбды — на отступе 8.

## 3. Values and Literals

### 3.1 Числа

- `Int` — целое произвольной точности.
- `Float` — IEEE754 double.
- `Decimal` — точная десятичная арифметика, `dec"1.50"` (**Should**, feature-flagged).
- `Rational` — stdlib (**Nice to have**).

**Лексические правила:**

- `0x`/`0b`/`0o` — только `Int`.
- `_` разрешён **только между цифрами**: `1_000_000`. Не в начале, не в конце, не рядом с `x`/`b`/`o` или `.`.
- `1e9`, `1.5e-3`, `1E+9` — `Float`.
- `1.5` — `Float`. `1.` и `.5` — ошибка лексера.
- `-1`, `+1` — унарные операторы над `1`, не часть литерала.
- `dec"..."` — `Decimal`. Тело — десятичный литерал, `_` разрешён.

**Валидные формы:** `1_000_000`, `0xFF`, `0b1010`, `1e9`, `1.5`, `dec"1_000.5"`, `dec"-1.5"`, `dec"+1"`, `dec"1.50"`.

**Невалидные:** `1__0`, `1_`, `_1`, `1e`, `1.`, `.5`, `0x` (без цифр), `dec"1e9"`, `dec".5"`, `dec"1."`, `dec"1__0"`.

### 3.2 Строки (`Str`) и `Bytes`

- **`Str`** — UTF-8 строка, всегда валидная.
- **`Bytes`** — `b"\x89PNG"`, последовательность байтов.
- **Интерполяция:** `"Привет, \(name)!"` — только в `Str`.
- **Escape:** `\n`, `\t`, `\r`, `\0`, `\\`, `\"`, `\(`, `\u{H...H}`. Полный список — в [C. Escape Sequences](#c-escape-sequences-and-utf-8).
- **Сигилы:** `b"..."`, `dec"..."`, `rx"..."`. Пользовательских сигилов нет.

**Интерполяция `\(...)` (MVP ограничения):**

- Границы: от `\(` до соответствующей `)` с учётом вложенности скобок и вложенных строк.
- Внутри `\(...)` разрешены любые выражения, **кроме блочных offside-конструкций** (`if`/`match`/`recv`/`with`/`trap` с телом-блоком, блочные лямбды). Однострочный `if … then … else …` — выражение, он разрешён (§C.2).
- Физический перенос строки внутри `\(...)` запрещён: лексер сообщает `unclosed interpolation` (§C.2). Выражение интерполяции пишется в одной строке; длинное — выносится в именованное значение до строки.
- `NEWLINE`/`INDENT`/`DEDENT` внутри интерполяции не эмитируются.
- Незакрытая интерполяция — ошибка лексера.

Недопустимо — перенос строки внутри `\(...)`:

```brig invalid "unclosed interpolation"
x = "sum: \(1 +
2)"
```

Допустимо — однострочный `if`:

```brig
fn label(ready) -> "value: \(if ready then 1 else 0)"
```

Недопустимо в MVP — блочный `if`:

```text
x = "value: \(if ready
    1
else
    0)"
```

### 3.3 `Regex`

- `rx"..."` — regex-литерал (**Should**, feature-flagged).
- Escape: `\"`, `\\`, другие `\X` сохраняются как `\X`.
- Интерполяции нет.
- Лексер не валидирует синтаксис regex.

### 3.4 Unit, Bool, Atom

- **`()`** — Unit, единственное значение типа Unit.
- **`Bool`** — `true`, `false`.
- **`Atom`** — интернированные атомы, например `:ok`, `:ready?`.

### 3.5 Многострочные строки

`"""..."""` — многострочный `Str` (**Must**, research 03/L9). Формальные правила — §C.7.

- После открывающих `"""` до конца строки — только пробелы; содержимое начинается со следующей строки.
- Закрывающие `"""` стоят первыми непробельными символами своей строки. Их отступ — **общий отступ литерала**: он снимается со всех строк содержимого (как в Swift). Строка содержимого с меньшим отступом — ошибка лексера.
- Перевод строки сразу после открывающих и перед закрывающими `"""` в значение не входит; строки содержимого соединяются через `\n`.
- Пустые строки и строки из одних пробелов допустимы при любом отступе и дают пустую строку значения.
- Интерполяция `\(expr)` и escape — как в обычном `Str` (§3.2); `"` внутри не экранируется. Интерполяция не переходит границу строки содержимого.
- `#` внутри литерала — текст, не комментарий; строки содержимого не участвуют в offside.
- После закрывающих `"""` строка продолжается как обычно: `[q, """` … `""", x]`.

```brig module
module Sql

fn find_user(table) ->
    """
    SELECT id, name
      FROM \(table)
     WHERE id = $1
    """
```

Значение: `"SELECT id, name\n  FROM users\n WHERE id = $1"` при `table == "users"`. Для SQL подставляются параметры, а не интерполяция — интерполяция в примере показывает только правило лексера.

Многострочных `b"..."`, `rx"..."`, `dec"..."` и raw-строк нет.

## 4. Collections

### 4.1 Кортежи (`Tuple`)

```brig
t = (1, "a", :ok)
(a, b, c) = t
```

- `()` — Unit.
- `(x)` — группировка.
- `(x,)` — 1-кортеж.
- `(x, y)` — 2-кортеж.
- `..` в кортеже запрещён.
- Равенство — структурное.
- `(a, b, c) = t` — связывание с паттерном (§5.1); кортеж другой длины — `(:badmatch, t)`.

### 4.2 Списки (`List`)

```brig
[1, 2, 3]
```

Паттерны: `[1, ..rest]`, `[1, 2, ..]`, `[1, 2, _]`, `[1, 2, _, ..rest]`. `..`/`..name` — только последним, не более одного раза.

`[1, 2, ..]` в позиции **выражения** — запрещено: `..` без операнда допустим только в паттерне.

```brig invalid "expected expression, got ]"
fn main() ->
    xs = [1, 2, ..]
```

**Представление и сложность (DD #397).** `List` — неизменяемый односвязный список (cons-ячейки), длина хранится в ячейке. Хвост разделяется между значениями: `[x, ..xs]` не копирует `xs`. Гарантия — асимптотика (O-оценки); константы спека не обещает. Здесь и в §4.4–§4.6 `n` — число элементов коллекции.

| Операция                                   | Сложность              | Примечание                                              |
| ------------------------------------------ | ---------------------- | ------------------------------------------------------- |
| `len(xs)`                                  | O(1)                   | длина в ячейке                                          |
| `[x, ..xs]` — добавление в голову          | O(1)                   | `xs` разделяется                                        |
| разбор `[h, ..t]`                          | O(1)                   | `t` — тот же хвост, без копирования                     |
| разбор `[a, b, c]` из `k` элементов        | O(k)                   | длина сверяется за O(1)                                 |
| индекс `xs[i]`                             | O(i), в худшем O(n)    | для индексного доступа — `Vector` (§4.4)                |
| `[..a, ..b]`, `[..a, x]`                   | O(len(a))              | все спреды, кроме последнего, копируются; последний разделяется |
| `list(range)` (§4.3)                       | O(n)                   | материализация                                          |

### 4.3 `Range`

```brig
r = 1 to 10
nums = list(1 to 10)
```

- **Встроенное иммутабельное значение первого класса.** Представляется как `Range{ start: Int, end: Int }`.
- **Равенство** — структурное (`1 to 10 == 1 to 10`).
- **Term order** — сразу после `Bool`, перед атомами.
- **Паттерны** — в MVP не поддерживаются.
- `list(range)` материализует. `list(1 to 1)` → `[1]`.
- Убывающий литеральный range (`1 to 0`, `5 to 1`) — **ошибка парсинга**. При вычисляемых границах — runtime `raise((:range_error, (start, end)))`.
- `...` не используется.

### 4.4 `Vector`

```brig
v = %[1, 2, 3]
v[0]
Vec.set(v, 0, 99)
Vec.push(v, 4)
len(v)
```

- Персистентный 32-арный trie (Clojure-style): `push` — O(1) amortized, чтение и `set` — O(log₃₂ n); `len` — O(1). Значения разделяют неизменённые ветви trie: `Vec.push`/`Vec.set` не копируют вектор целиком.
- Литерал — `%[...]`.
- Паттерн-матчинг — только по точной длине; `..` не поддерживается.
- `v[0]` вне границ — `raise((:index_out_of_bounds, (idx, len)))`.
- Модуль называется `Vec` — осознанное исключение из правила «модули не сокращаются».

| Операция                                   | Сложность              | Примечание                                              |
| ------------------------------------------ | ---------------------- | ------------------------------------------------------- |
| `len(v)`                                   | O(1)                   |                                                         |
| `v[i]`, `Vec.get(v, i)`                    | O(log₃₂ n)             |                                                         |
| `Vec.set(v, i, x)`                         | O(log₃₂ n)             | путь от корня копируется, остальное разделяется         |
| `Vec.push(v, x)`                           | O(1) amortized         |                                                         |
| разбор `%[a, b, c]` из `k` элементов       | O(k log₃₂ n)           | длина сверяется за O(1)                                 |
| `%[..a, ..b]`, `%[..a, x]`                 | O(число развёрнутых элементов) | каждый развёрнутый элемент добавляется как `push` |

### 4.5 `Map`

```brig
m = %{ "a" => 1, "b" => 2 }
m["a"]                 # Option
Map.put(m, "c", 3)
m2 = %{ ..m, "c" => 3 }
```

- **Pattern matching — частичный по ключам.** Захват ключа `%{ k => v }` в MVP запрещён. `..` в паттернах Map **запрещён в MVP**.
- `%{ "a" => a }` матчится, если ключ `"a"` есть; остальные ключи игнорируются.
- Отсутствующий ключ в паттерне означает, что пара не требуется для совпадения.
- `m["a"]` возвращает `Option`.

`Map` — персистентная хеш-структура HAMT (hash array mapped trie, ветвление 32): ключи сравниваются по равенству §4.8, неизменённые ветви разделяются между значениями.

| Операция                                   | Сложность              | Примечание                                              |
| ------------------------------------------ | ---------------------- | ------------------------------------------------------- |
| `len(m)`                                   | O(1)                   |                                                         |
| `m[k]`, `Map.get(m, k)`, `Map.get_or`      | O(log₃₂ n)             |                                                         |
| `Map.put(m, k, v)`                         | O(log₃₂ n)             |                                                         |
| `Map.remove(m, k)`                         | O(log₃₂ n)             |                                                         |
| `Map.keys(m)`                              | O(n)                   |                                                         |
| разбор `%{ k1 => p1, .. }` из `k` ключей   | O(k log₃₂ n)           | частичный: лишние ключи не читаются                     |
| `%{ ..m, k => v }`                         | O(log₃₂ n) на каждую добавленную пару | первый спред — основа без копирования; каждая следующая пара и пара следующих спредов — как `Map.put` |

### 4.6 `Set`

```brig
s = set(1, 2, 3)
```

Паттерн-матчинг — точный. `Queue` — FIFO, Okasaki, stdlib (**Nice to have**).

`Set` — тот же HAMT, что и `Map`, без значений (§4.5).

| Операция                                   | Сложность              | Примечание                                              |
| ------------------------------------------ | ---------------------- | ------------------------------------------------------- |
| `set(..xs)` из `n` элементов               | O(n log₃₂ n)           | повторы отбрасываются                                   |
| `len(s)`                                   | O(1)                   |                                                         |
| членство, добавление, удаление элемента    | O(log₃₂ n)             | оценка для операций модуля `Set`, когда они появятся в API; сегодня API — только конструктор `set` |

### 4.7 Записи: номинальные и анонимные

- `type User {...}` — номинальная.
- `{ key: value, ... }` — структурная (анонимная).
- Разные виды друг другу не равны.

**Различие между конструктором варианта и литералом записи:**

- `Red` (без `{`) — значение-конструктор варианта (без полей).
- `Red{...}` — литерал **номинальной записи** типа `Red` (форма `type Red { ... }` как запись).
- Тип из другого модуля — `Accounts.User{...}` или короткое имя по правилу §11.1.

**Доступ к полю** — `rec.field`, для номинальных и анонимных записей одинаково. Отсутствующее поле — авто-raise `(:no_field, (name, rec))` (§10.4); `Option` на каждый доступ не возвращается. Необязательное поле хранит `Option` как значение: `email: Option<Str>`, чтение — `u.email`.

```brig module
module Accounts

type User { id: Int, name: Str, email: Option<Str> }

fn greeting(u) -> "Hello, \(u.name)"
```

**Record update сохраняет вид.** Литерал без имени типа, в котором есть спред, получает вид **первого спреда**: `{ ..u, name: "b" }` при `u = User{...}` — снова `User`, при анонимной `u` — анонимная запись. Поле, которого нет в типе номинальной записи, — авто-raise `(:no_field, (name, rec))`, где `rec` — запись первого спреда. Анонимная запись принимает любые поля.

```brig module
module Accounts

type User { id: Int, name: Str }

fn rename(u, name) -> { ..u, name: name }               # User остаётся User

fn tagged(u) -> { ..Record.to_anon(u), kind: :user }   # анонимная: новое поле допустимо
```

**Конвертация вида — только явная:**

- `User{ ..r }` — в номинальную запись типа `User`;
- `Record.to_anon(r)` — в анонимную запись с теми же полями; для анонимной `r` возвращает `r`. Не запись — `(:type_error, (:to_anon, v))`.

Реализация — T-142.

<!-- Известное ограничение (не заведена задача): форматтер теряет inline-комментарии и может отличаться пробелами вокруг `{` для именованных записей. До фикса помечен как text. -->

Сериализация:

```text
Json.encode(User{ id: 1 })                       # {"id": 1}
Json.encode(User{ id: 1 }, { type_tag: true })   # {"__type__": "User", "id": 1}
```

#### JSON: маппинг и ошибки

`Json.encode(v) -> Str` и `Json.decode(s) -> Result<V, (:json, reason)>`.

| Значение Brig | JSON | `decode` возвращает |
| --- | --- | --- |
| `None` | `null` | `None` |
| `Some(v)` | кодируется как `v` | `v` (не `Some(v)`) |
| `()` | `null` | `None` |
| `Bool` | `true`/`false` | `Bool` |
| `Int` | число | `Int` |
| `Float` | число с `.` или `e`; `NaN`, `Inf`, `-Inf` — не кодируются | `Float` |
| `Decimal` | строка `dec"…"` | `Str` |
| `Str` | строка | `Str` |
| атом | строка `":имя"` | `Str` |
| `Bytes` | `{"$bytes": "<base64>"}` | `Bytes` |
| `List`, `Vector`, `Set`, кортеж | массив | `List` |
| `Map` со `Str`/`Atom` ключами | объект | `Map` со `Str`-ключами |
| запись | объект по полям; с `{ type_tag: true }` номинальная получает `"__type__"` | `Map` |
| пользовательский вариант | `{"tag": "Имя", "args": [...]}` | `Map` |
| `Ok`, `Error`, `Pid`, `Ref`, `Port`, функция, `Range` | не кодируются | — |

Ключи `Map`, начинающиеся с `$`, кодируются с лишним `$`, чтобы не совпасть с маркером `Bytes`; `decode` снимает его. Целое число без `.` и экспоненты разбирается в `Int` любой величины, остальные — в `Float`.

`Json.decode` не бросает: ошибка — `Error((:json, reason))`.

| `reason` | Когда |
| --- | --- |
| `:syntax` | не JSON |
| `(:number, s)` | число `s` не представимо в `Float` (`1e999`) |
| `:depth_limit` | вложенность больше 64 |
| `:trailing_data` | после первого значения есть непробельный текст |
| `:invalid_utf8` | входная `Str` не UTF-8 |

`Json.encode` на значении без маппинга бросает `raise((:json, (:unsupported, v)))`, где `v` — само непредставимое значение (для ключа `Map` — ключ), и `raise((:json, :depth_limit))` при вложенности больше 64. Паттерн `Error((:json, _))` и `trap`-паттерн `(:json, _)` ловят все ошибки модуля.

```brig
fn json_roundtrip() ->
    assert(Json.decode("nope") == Error((:json, :syntax)))
    assert(Json.decode("null") == Ok(None))
    assert(Json.decode(Json.encode(%{ "a" => [1, 2.5, None] })) == Ok(%{ "a" => [1, 2.5, None] }))
    assert(Json.encode(Some(1)) == "1")
    r = trap(Json.encode(Ok(2)))
    assert(r == Error((:json, (:unsupported, Ok(2)))))
```

### 4.8 Равенство — сводная таблица

| Вид                        | Равенство               | Pattern matching        | Комментарий                      |
| -------------------------- | ----------------------- | ----------------------- | -------------------------------- |
| `Int`/`Float`              | численно, точно (смешение) | точное, по виду      | `1 == 1.0` true; паттерн `1` не матчит `1.0`; ключи `Map`/`Set`: `1` и `1.0` — один ключ |
| `Decimal`                  | точно                   | точное, по виду         | `Decimal` vs `Float` — `:type_error` в `==`/`<`; в паттернах и ключах `Map`/`Set` — разные значения |

| `Str`                      | по кодпоинтам           | точное                  | —                                |
| `Tuple`                    | структурно              | точное                  | `..` запрещён                    |

| `Vector`                   | структурно              | точное, без `..`        | —                                |

| `Set`                      | по набору элементов     | точное                  | —                                |

| `type X {...}` номинальная | по тегу + полям         | только с тем же `X`     | `X{...} != Y{...}`               |

| `Function`                 | по identity             | —                       | нестабильно между запусками; функция модуля `M.f` — по полному имени и арности (§7.6) |

## 5. Spread Operator `..`

### 5.1 Связывание (паттерн)

**Связывание `pattern = expr`.** Левая часть `=` — любой паттерн (§9), не только имя. Значение правой части сопоставляется с паттерном; при совпадении имена паттерна связываются в текущей лексической области (§6.6). Имя, повторённое в одном паттерне, — повторное связывание в одной области, ошибка контекстного анализа (§F.3).

Несовпадение — авто-raise `(:badmatch, v)`, где `v` — значение правой части (§10.4). Ошибка ловится `trap`, как любой авто-raise. Неопровержимые паттерны (`x`, `_`, `(a, b)` для пары, `{ json: j }` для анонимной записи с полем `json`) — частный случай того же правила. Это идиома «let it crash»: когда другой исход — ошибка программы, `Ok(v) = f()` короче `match` с веткой `raise`.

```brig module
module Config

fn port(opts) ->
    Some(p) = opts.port          # None → raise((:badmatch, None))
    p

fn swap(pair) ->
    (a, b) = pair                # не пара → raise((:badmatch, pair))
    (b, a)
```

`<-` в `with` — другая форма: несовпадение там не бросает, а передаётся дальше (§8.2).

**Спред в паттерне:**

- Только последним элементом, не более одного раза.
- Только в `List`-паттернах: `[1, ..rest]`.
- В `Map`-паттернах и record-паттернах **запрещён в MVP**. Частичность Map/record выражается отсутствием ключей/полей в паттерне.
- `Tuple`/`Vector` эту роль не поддерживают.

### 5.2 Конструирование (построение значения)

- В любом количестве, в любой позиции.
- В позиции **аргумента вызова** форма `..` требует выражения: `f(..xs)` корректен, `f(..)` — ошибка парсинга.

```text
[0, ..xs, 99]
{ ..user, name: "Bob" }
{ ..a, ..b, x: 1 }
%{ ..m, "c" => 3 }
f(head, ..items, tail)
```

**Правило:** **связывание — `..` только в конце и один раз; конструирование — `..` где угодно и сколько угодно.**

В записи и `Map` при повторе ключа побеждает правый: `{ ..a, ..b }` берёт поля `b` поверх `a`, `{ ..a, x: 1 }` — `x` поверх `a`. Так передаются опции функции — анонимная запись последним аргументом со спредом дефолтов; kwargs в языке нет (§16).

```brig module
module Server

fn defaults() -> { port: 4000, max_body: 8_000_000 }

fn listen(opts) ->
    o = { ..defaults(), ..opts }
    o.port
```

### 5.3 Порядок операций при вызове со спредом

1. **Спред:** список разворачивается в позиционные аргументы.
2. **Диспетчизация клоза:** первый совпавший клоз выигрывает.
3. **Авто-raise:** если ни один не совпал — `(:function_clause, args)` на финальном списке аргументов.

Спред данных внутри спреда аргументов (`f(..[0, ..xs, 99])`) обрабатывается рекурсивно.

### 5.4 `..` и pipe

`..` в аргументах вызова разрешён, в том числе в pipe RHS: `xs |> f(..ys)` → `f(xs, ..ys)`.

## 6. Functions

### 6.1 Мультиклозные функции

```brig
fn classify(0) -> "zero"
fn classify(1) -> "one"
fn classify(n) -> "many"
```

Guards через `when`:

```brig
fn classify(n) when n > 0 -> "positive"
fn classify(0)             -> "zero"
fn classify(n)             -> "negative"
```

Ни один клоз не подошёл — авто-raise `(:function_clause, args)`.

**Область `when`-guards.** Разрешён:

- В мультиклозных `fn` (модуль и локальные).
- В ветках `recv`.
- **Не разрешён** в `match`, `with`/`else`, и в лямбдах.

Guard — подмножество выражений без побочных эффектов. Если вычисление guard бросает, исходная ошибка пробрасывается как есть: guard не считается ложным, следующий клоз не пробуется, отдельного имени ошибки нет. Guard, вернувший не-`Bool`, — ловимый `raise((:type_error, (:expected_bool, v)))`, как условие `if` (§7.2).

```brig
fn safe(x) when 10 div x > 1 -> :big
fn safe(_)                   -> :small

fn main() -> trap(safe(0))   # Error((:division_by_zero, ())), а не :small
```

### 6.2 Лямбды

**Короткая (стрелка — одна строка):**

```text
pow = x -> x**2
nums |> Enum.map(x -> x * 2)
```

Короткая лямбда **всегда однострочная**: тело — одно выражение. Параметров может быть несколько — имена в скобках через запятую:

```text
Enum.fold(xs, 0, (acc, x) -> acc + x)
```

`(a, b) -> …` отличается от кортежа `(a, b)` по `->` после `)` — тем же приёмом, что и пустая лямбда `() ->`.

**Пустая (канон):**

```text
thunk = () -> spawn_linked(() -> counter_loop(0))
```

**Полная (`fn` — блок):**

```brig
fn (x) ->
    y = x * 2
    y + 1
```

При нуле параметров скобки в полной форме не нужны — канон `fn ->`:

```text
fn ->
    y = compute()
    y + 1
```

`fn () ->` остаётся валидным; форматтер переписывает его в `fn ->`. Для одного параметра `fn x ->` без скобок **не** вводится (§0.2, один способ): `fn (x) ->`, `fn (a, b) ->`, `fn ((:ok, v)) ->`.

**Паттерны в параметрах лямбды (Should, §16).** В полной лямбде: `fn ((:ok, v)) -> ...`. В короткой лямбде параметры — только `lower_ident` (`x -> ...`, `(a, b) -> ...`).

**Границы короткой лямбды.** Тело короткой лямбды `x -> expr` заканчивается на ближайшем токене, который не может быть частью выражения на этом уровне приоритета: `,`, `)`, `]`, `}`, `NEWLINE`. Внутри скобок — до `,` или закрывающей скобки. Вне скобок — до `NEWLINE`. Блочного тела у стрелки нет — для блока нужна полная форма `fn`.

**Блочная лямбда в аргументе вызова.** Полная лямбда с блочным телом допустима прямо в аргументах вызова; блок отсчитывается от отступа стейтмента (§2.4, §D.6):

```brig
fn run(f) -> f(20)

fn main() ->
    run(fn (x) ->
        y = x * 2
        y + 1
    )
```

Лямбда, связанная с именем, — значение-функция. **Взаимная рекурсия замыканий запрещена** — для неё только локальные `fn`.

### 6.3 Вариадические параметры и спред аргументов

```brig module
module Variadic
fn count(..args) -> len(args)

fn sum()          -> 0
fn sum(x, ..rest) -> x + sum(..rest)

fn main() ->
    nums = [1, 2, 3]
    (count(1, 2, 3), sum(..nums))
```

`..args` собирается в `List`. `..rest` разворачивается из `List`.

### 6.4 Приоритет `**`, равенство функций

`-x**2 = -(x**2)`, `2**3**2 = 2**(3**2)`. Функции — identity equality.

### 6.5 Локальные именованные функции

```brig
fn pow(base, exp) ->
    fn go(acc, 0) -> acc
    fn go(acc, n) -> go(acc * base, n - 1)
    go(1, exp)
```

Только в начале тела; вперёд-ссылки свободны (взаимная рекурсия разрешена).

### 6.6 Лексическое связывание и shadowing

> **Правило.** Имя связывается один раз в **лексической области**. Внутри одной области повторное связывание того же имени — ошибка контекстного анализа. **Вложенная область** может затенять имя внешней: новое связывание видно от точки связывания до конца вложенной области; внешнее связывание после этого не видно. Затенение — не ошибка, но компилятор **выдаёт info-диагностику** при затенении имени прелюдии.

Пример-контроль:

```brig
fn main() ->
    x = 1
    f = fn (x) -> x + 1        # параметр x затеняет внешний — OK
    g = fn () ->
        x = 2                   # локальный x затеняет внешний — OK
        x + 1
    (f, g)
```

**REPL-замыкания — лексический снимок.** Замыкание захватывает связывание своей инструкции. Позднее `x = 10` в следующей инструкции не влияет на ранее созданное замыкание.

## 7. Operators

### 7.1 Таблица приоритетов

| Уровень | Операторы                   | Ассоциативность | Комментарий              |
| ------: | --------------------------- | --------------- | ------------------------ |
|       2 | `or`                        | left            | самый слабый из бинарных |
|       3 | `and`                       | left            |                          |
|       4 | `==` `!=` `<` `>` `<=` `>=` | non-assoc       | цепочки запрещены        |
|       5 | `\|>`                       | left            |                          |
|       6 | `<>`                        | right           | конкатенация строк       |
|       7 | `to`                        | non-assoc       |                          |
|       8 | `+` `-`                     | left            |                          |
|       9 | `*` `/` `div` `rem`         | left            |                          |
|      10 | унарный `-`, `not`          | prefix          | слабее `**`, сильнее `*` |
|      11 | `**`                        | right           | сильнее унарного `-`     |
|      12 | постфиксные `.`, `()`, `[]` | left            |                          |

**Не в таблице:** `=`, `:`, `->`, `..`, `as`, `=>`. `=` — стейтмент. `->` — lowest precedence, right-assoc, тело до конца выражения/блока. `..` и `as` — не операторы, а маркеры паттернов/спредов. `=>` — только в `map_literal`.

**Свойства:**

- `|>` (5) выше сравнений (4): `a |> f == c` → `(a |> f) == c`.
- `<>` (6) выше `|>` (5): `"a" <> b |> f` → `("a" <> b) |> f`.
- `to` (7) выше `<>` (6): `1 to 10 |> list` → `(1 to 10) |> list` (не затрагивается `<>`, но сохраняет порядок относительно `|>`).
- `<>` — право-ассоциативен и допускает цепочки: `"a" <> "b" <> c` → `"a" <> ("b" <> c)`.
- Сравнения и `to` — non-assoc: `a == b == c` и `1 to 2 to 3` — **ошибка парсинга**.
- **Больший номер уровня связывает сильнее.**

### 7.2 Логические

`and`/`or`/`not`, `not > and > or`, short-circuit, всегда `Bool`.

Операнды `and`/`or`/`not` и условие `if` обязаны быть `Bool` (строгий `Bool`, без truthiness, §16). Не-`Bool` — ловимый `raise((:type_error, (:expected_bool, v)))`. Правый операнд `and`/`or` проверяется после вычисления и не является хвостовой позицией; хвостовая форма — `if c then true else f(..)`.

### 7.3 Арифметика

`+ - * / **`, `div`, `rem`. `%` нет.

**Правила (Must для VM):**

- `Str + Str` не определён: `"a" + "b"` — ловимый `raise((:type_error, (:add, ("a", "b"))))`. Склейка строк — оператор `<>` (§7.3a) или интерполяция: `"\(a)\(b)"` (§0.2).
- `List + List` не определён: `[1, 2] + [3]` — ловимый `raise((:type_error, (:add, ([1, 2], [3]))))`. Склейка списков — спред: `[..a, ..b]` (§5.2).
- `/` всегда возвращает `Float`.
- Деление на ноль — `raise((:division_by_zero, ()))`.
- `div` — целочисленное деление к нулю; деление на ноль — `raise((:division_by_zero, ()))`.
- `rem` — знак результата следует за делимым (`-7 rem 3 == -1`, `7 rem -3 == 1`).
- Переполнение `Int` — не происходит (произвольная точность).
- `v[i]` вне границ — `raise((:index_out_of_bounds, (i, len)))`. То же для `Bytes`/`Str` (индексация по кодпоинту для `Str`, по байту для `Bytes`).

### 7.3a Конкатенация строк (`<>`)

`<>` — бинарный оператор конкатенации `Str`, право-ассоциативный, приоритет между `|>` и `to` (§7.1). Не-`Str` операнд — ловимый `raise((:type_error, (:concat, (a, b))))`.

```brig
"Hello, " <> "World"          # "Hello, World"
"a" <> "b" <> "c"             # "abc" (право-ассоциативно)
```

`<>` также работает как паттерн для деструктуризации префикса строки (Elixir-style), и в связывании `pattern = expr`, и в параметрах функции:

```brig
fn greet("Hello, " <> name) -> name
fn greet(_) -> "?"

"Hello, " <> name = "Hello, World"   # name = "World"
greet("Hello, World")                # "World"
```

**Правило (§0.2).** `<>` — склейка строк, интерполяция `"\(x)"` — подстановка значения в строку; оба способа остаются, каждый для своего случая. `+` для `Str` не определён (§7.3).

**Ограничение (как в Elixir):** слева от `<>` в паттерне обязан быть строковый литерал — `x <> rest` не парсится (`'<>' пattern requires a string literal on its left-hand side`). Последовательные литералы складываются: `"a" <> "b" <> rest` эквивалентно `"ab" <> rest`. Несовпадение префикса в связывании — обычный `(:badmatch, v)` (§5.1); в мультиклозной функции — просто следующая клоза (первое совпадение побеждает, порядок клоз важен, как в Elixir).

### 7.4 Сравнение и term order

`==`, `!=`, `<`, `>`, `<=`, `>=`.

**`<` тотален, `==` структурен.**

**Числа.** `Int`/`Float` — один домен. `Decimal`:

- `Decimal × Decimal` — точно.
- `Decimal × Int` — по значению.
- `Decimal × Float` — ошибка (`:type_error`, ловимая `trap`) в `==`/`!=`/`<`/`>`/`<=`/`>=` (для `==`/`!=` — только пара верхнего уровня; вложенная в контейнер — `false`); в паттернах и ключах `Map`/`Set` `Decimal` и `Float` — разные значения, без ошибки.

`Int × Float` сравнивается точно (без потери точности выше 2^53), `NaN != NaN`.

**Term order:**

1. число (`Int`/`Float`/`Decimal`, кроме пары `Decimal`↔`Float`)
2. `Bool` — `false < true`
3. `Range` — по `(start, end)` лексикографически
4. атом — лексикографически по имени атома (включая финальный `?`)
5. `Bytes` — по байтам
6. `Str` — по кодпоинтам
7. кортеж (`()` — наименьший)
8. `Vector` — лексикографически: первое различие решает, при равном префиксе короче — меньше
9. `List` — лексикографически, как `Vector`
10. `Map` — размер, затем по отсортированным парам
11. `Set` — размер, затем по отсортированным элементам
12. номинальная запись и пользовательский вариант — по имени типа, затем у записи по полям, у варианта по порядку тега в декларации, затем по полям (пример: `Red < Green` для `type Color { Red, Green }`)
13. встроенные варианты `Ok`/`Error`/`Some`/`None` — по тегу, затем по полям (порядок тегов: `None < Some`, `Ok < Error`)
14. анонимная запись — по полям
15. `Function` — по identity
16. `Pid`, `Ref` — по identity
17. `Port` — по identity (§12.12)

```brig module
module Colors

type Color { Red, Green }

fn compare() -> Red < Green
```

`List` и `Vector` сравниваются лексикографически, как `Str` (а не по длине, как кортеж): `[1, 1] < [2]`, `[1] < [1, 0]`, `[] < [0]`, `%[1, 1] < %[2]`.

```brig
Enum.sort([[1, 1], [2], [0, 0, 0]])  # => [[0, 0, 0], [1, 1], [2]]
```

`sort` смешанных списков бросает только при `Decimal` + `Float`.

### 7.5 Pipe

`x |> f(a, b)` → `f(x, a, b)` — значение подставляется первым аргументом.

**Первый аргумент — субъект.** У функций прелюдии и stdlib первым идёт значение, которое протекает через pipe: коллекция у `Enum.*` (`Enum.map(xs, f)`, `Enum.fold(xs, acc, f)`), мапа у `Map.*`, вектор у `Vec.*`(§11.5). Поэтому `xs |> Enum.map(f) |> Enum.filter(p)` работает без исключений. Новые функции stdlib следуют тому же правилу. Акторные примитивы под правило не подпадают: в pipe они запрещены.

**Запрет акторных примитивов в pipe — статическая проверка парсера + контекстного анализа.** В качестве правой части `|>` запрещены **все** акторные примитивы прелюдии: `send`, `spawn`, `spawn_linked`, `spawn_watched`, `link`, `watch`, `unwatch`, `exit`, `self`, `make_ref`, `mailbox_size`, `register`, `unregister`, `whereis`, `reply`, `await` (§12.6).

В MVP проверка выполняется по имени `pipe_name` без точки. Полная проверка с алиасами — в семантическом анализе.

Разрешённые формы RHS: `f`, `f(a)`, `M.f(a)`.

### 7.6 Точка: поле, функция модуля, имя из модуля

Постфиксная `.` (уровень 11) разбирается по левой части:

| Форма | Смысл |
| --- | --- |
| `expr.field` | поле записи (§4.7); отсутствующее — `(:no_field, (name, rec))` |
| `M.f(args)` | вызов функции `f` модуля `M` |
| `M.f` | **значение-функция** `f` модуля `M`, без вызова |
| `M.Ctor`, `M.Ctor(x)`, `M.Type{...}` | конструктор варианта или тип записи из модуля `M` (§11.1) |

`M` — имя модуля, видимое в файле (§11.1): встроенный модуль, импортированный модуль (полное имя или последний сегмент) или имя из `alias`.

**Ссылка на функцию модуля как значение.** `M.f` без вызова даёт значение-функцию, как имя собственной `fn` модуля: `f = Json.encode`, `Enum.map(xs, Util.g)`. Identity — полное имя модуля, имя функции и арность, а не адрес: две ссылки `Util.g` равны (`Util.g == Util.g` → `true`). Правила видимости те же, что для вызова: ссылка на приватную функцию другого модуля — ошибка компиляции (§11.2).

```brig module
module Main

fn main() ->
    encode = Json.encode
    Enum.map([[1], [2]], encode)
```

Имя модуля без `.name` в позиции выражения значением не является: модули и типы как значения — вне v0.5.0. Реализация — T-144.

## 8. Control Flow

### 8.1 `if` — синтаксический сахар над `match`

```text
if ready
    start()
else
    wait()
```

≡

```text
match ready
    true  -> start()
    false -> wait()
```

Без `else` — `()`:

```text
if ready
    start()
# ≡ match ready
#     true  -> start()
#     false -> ()
```

Однострочная форма — только целиком, с обеими ветками:

```text
x = if ready then start() else wait()
```

`else` — на том же отступе, что стейтмент с `if` (якорь — `stmt_indent`, как в §2.4). `match` всегда блочный.

### 8.2 `with`/`else`

```brig module
fn process(input) ->
    with
        Ok(a) <- validate(input)
        Ok(b) <- transform(a)
        Ok(c) <- save(b)
        Ok(c)
    else
        Error(e) -> Error(e)

# хелперы примера
fn validate(x) -> Ok(x)
fn transform(x) -> Ok(x)
fn save(x) -> Ok(x)
```

Binds только в начале; тело — с первого statement без `<-`.

Тело обязательно: `with` из одних binds — ошибка. Bind после первого statement тела — ошибка парсинга, а не молчаливое переупорядочивание. Для промежуточного шага цепочки пишется bind с неопровержимым паттерном: `y <- f(a)` вместо `y = f(a)`, а для побочного эффекта — `_ <- log(a)`:

```brig module
fn process(x) ->
    with
        Ok(a) <- validate(x)
        _     <- print(a)
        y     <- transform(a)
        Ok(y)
    else
        Error(e) -> Error(e)

# хелперы примера
fn validate(x) -> Ok(x)
fn transform(x) -> x
```

`else` — на уровне отступа `with`. Ветки `else` проверяются по порядку; первая совпавшая выигрывает.

**Семантика `else`:**

1. Отсутствует — пропагация: цепочка возвращает первое несовпавшее значение. Не авто-raise.
2. Присутствует, значение совпало — ветка выполняется.
3. Присутствует, не совпало — авто-raise `(:case_clause, val)`.

`with` работает и на `Option`.

**Эргономическая ловушка (отсутствие `else`).** Типы documentation-only, поэтому `with` без `else` не проверяет форму несовпавшего значения — любое значение «пролетает» наружу. Осознанный выбор в духе Elixir.

### 8.3 `match`

```text
match expr
    pattern1 -> result1
    pattern2 -> result2
```

`match` всегда блочный. Guards в `match` не разрешены: условие по значению — `cond` (§8.4) в теле ветки или `fn` с guard (§6.1).

### 8.4 `cond`

Многоветочное условие — выражение `cond`. `else if` в языке нет.

```brig
fn sign(n) ->
    cond
        n < 0 -> :neg
        n == 0 -> :zero
        true -> :pos

fn label(n) ->
    s = cond
        n > 100 ->
            print("big")
            "big"
        true -> "small"
    s
```

- Ветка — `условие -> тело`; тело однострочное или блоком, как у ветки `match`. Условие — выражение без лямбды на верхнем уровне (`or_expr`, как у guard).
- Условия проверяются сверху вниз; значение `cond` — тело первой ветки с истинным условием.
- Каждое условие — строгий `Bool`, как у `if` (§8.1): не-`Bool` → `:type_error`.
- Ни одно условие не истинно → авто-raise `(:cond_clause, ())` (§10.4).
- `cond` всегда блочный. Последняя ветка не `true ->` — info `brig check`.
- `cond` — сахар: парсер разворачивает его во вложенные `if`, форматтер печатает как `cond`.

```text
cond
    a -> x
    b -> y
# ≡ if a then x else (if b then y else raise((:cond_clause, ())))
```

## 9. Patterns

### 9.1 Общие правила

```text
pattern ::= pattern_atom [ "as" lower_ident ]
pattern_atom ::=
    WILDCARD
  | LOWER_IDENT
  | literal
  | constructor_pattern
  | tuple_pattern
  | list_pattern
  | map_pattern
  | record_pattern
  | "(" pattern ")"
```

### 9.2 As-паттерны

`pattern as name` — деструктурировать аргумент **и** сохранить целое значение:

```brig
fn foo((:ok, _) as full) -> full
```

Разрешён в параметрах `fn`, `match`, `recv`, `with`.

### 9.3 Конструкторы

```brig module
module Ctors
type User { id: Int }

fn unwrap_or(Some(x), _) -> x
fn unwrap_or(None, d) -> d

fn check(Ok(v)) -> v
fn check(Error(e)) -> e

fn user_id(User{ id: 1 }) -> :one
fn user_id(_) -> :other
```

### 9.4 Кортежные и списочные паттерны

Паттерны `..`/`..name` допустимы только в конце списка и не более одного раза:

```brig module
module Patterns

```

### 9.5 Map-паттерны

```text
%{ "a" => a }
```

Частичный по ключам. Захват ключа (`%{ k => v }` где `k` — переменная) **запрещён в MVP**. `..` в map-паттернах **запрещён в MVP**.

Частичный по полям. `..` в record-паттернах **запрещён в MVP**.

- `Range` не поддерживается в паттернах.

## 10. Error Handling

### 10.1 `Option` и `Result`

**`nil` исключён.** Нет значения — `Option<T>`. Ошибка — `Result<T, E>`. Нет содержательного значения — `()`.

**`Option` и `Result` — встроенные алгебраические варианты, а не прозрачные тюплы/атомы.**

- `Ok(1) != (:ok, 1)`.
- `None != :none`.
- `Some(1) != (:some, 1)`.
- Равенство — по тегу и полям (как у номинальных вариантов).
- Паттерны — только `Ok(x)`, `Error(e)`, `Some(v)`, `None`.

**Конструкторы:**

- Конструктор **без аргументов** — **значение**: `None`, `Red`, `Green`.
- Конструктор **с аргументами** — **функция**: `Some`, `Ok`, `Error`.
- Конструктор можно передавать как функцию: `Enum.map(xs, Some)`.

### 10.2 `raise`/`trap`

```brig module
fn get_user(id) ->
    match find_user(id)
        Some(u) -> u
        None    -> raise((:not_found, id))

# хелперы примера
fn find_user(_id) -> None
```

**Двойные скобки:** `raise` принимает ровно один аргумент; кортеж `(:not_found, id)` передаётся как один аргумент.

**`trap` — самостоятельная форма, не сахар над `trap(fn -> ...)`.**

**Семантика `trap(expr)` — синтаксический сахар.** Однострочная форма `trap(expr)` — сокращение для блочной формы с единственным `trap_item` — стейтментом `expr`. Это чисто синтаксический сахар, не вызов функции.

**Возвращаемое значение `trap`.** `trap` возвращает `Result<T, E>`:

- Успешное завершение тела со значением `v` → `Ok(v)`.
- Исключение в теле (raise) → `Error(e)`.
- `ensure`-клаузы выполняются LIFO при любом выходе.
- Ошибка в `ensure` замещает исходную (последняя побеждает).

**Позиция `trap`.** `trap` разрешён только как RHS `let_bind` или как отдельный `expr_stmt`. Запрещён в позиции аргумента вызова (`f(trap ...)`) и в позиции элемента литерала (`[trap ...]`, `{key: trap ...}`, `%{k => trap ...}`). **Запрет — контекстный (семантический), не грамматический.**

### 10.3 `ensure`/`defer`

**`ensure` — это `trap_item` внутри `INDENT`-блока `trap`, на том же уровне отступа, что и обычные стейтменты тела `trap`.** Это не клауза после `DEDENT`. `ensure` может появляться между стейтментами тела и обрамляться ими.

Две формы — `ensure <expr>` (одна строка) и `ensure` + под-блок (задел на будущее; в MVP не требуется). Несколько `ensure` допустимы в произвольном порядке; **runtime выполняет их LIFO**.

Пример с двумя `ensure`, перемежающимися с кодом:

```brig module
fn main() ->
    result = trap
        f1 = open("a.txt")
        ensure close(f1)
        f2 = open("b.txt")
        ensure close(f2)
        process(f1, f2)
    result

# хелперы примера
fn open(path) -> path
fn close(_f) -> ()
fn process(a, b) -> (a, b)
```

Порядок выполнения при выходе: `close(f2)`, затем `close(f1)`.

**`ensure` и TCO.** TCO гарантирован и внутри `trap` с `ensure` (принцип #11). Кадр хвостового вызова заменяется, а код `ensure` выполняется после возврата из вызова: невыполненные `ensure` хранятся компактной записью в куче. Глубина стека не растёт, память растёт O(n) на n уровней `ensure`. Схема и условия хвостовой позиции — `docs/02-register-based-virtual-machine.md` §5.1.

**Область активного `ensure`.** От точки регистрации первого `ensure` до выхода из `trap`. Включает сами `ensure`-клаузы.

### 10.4 Автоматический `raise`

Непокрытый `match`, `recv`, мультиклозная функция или несовпавшее связывание `pattern = expr` бросает автоматически. `with` без `else` — исключение (пропагация); `with` с неполным `else` — авто-raise `(:case_clause, val)`.

**Имена авто-raise:**

- `(:function_clause, args)`
- `(:case_clause, val)`
- `(:recv_clause, msg)`
- `(:cond_clause, ())` — ни одно условие `cond` не истинно (§8.4).
- `(:assertion_failed, ())`
- `(:type_error, (op, val))`
- `(:division_by_zero, ())`
- `(:index_out_of_bounds, (idx, len))`
- `(:range_error, (start, end))`
- `(:invalid_utf8, b)`
- `(:no_field, (name, rec))` — чтение отсутствующего поля записи `rec.name`; то же — поле, которого нет в типе, при record update номинальной записи `rec` (§4.7); `name` — атом.
- `(:badmatch, val)` — несовпадение паттерна в связывании `pattern = expr`; `val` — значение правой части (§5.1).

Ошибка внутри `when`-guard отдельного имени не имеет: пробрасывается исходная ошибка (§6.1).

**Причина завершения от VM — не авто-raise.** При превышении бюджета хода VM завершает актор через `exit(pid, (:resource_limit, (kind, used, limit)))` (§12.10): `kind` — `:turn_reductions` или `:turn_alloc_bytes`. Как любой `exit`, это не `raise`: `trap` его не ловит, причина видна только наблюдателям в `(:down, ref, reason)`.

### 10.5 Кросс-акторные ошибки

Наблюдатель узнаёт о падении только через `watch(pid)` (или `spawn_watched`, §12.7).

**Завершение чужого актора** — только `exit(pid, reason)` (§12.7): асинхронно, `trap` жертвы его не ловит, `ensure` выполняются (кроме `:kill`).

**Ошибки в `spawn`.** Без `watch` падение родителю не видно (`link` — связь, не наблюдение, §12.2).

**`trap` внутри ветки `recv`** — рекомендованная идиома.

## 11. Modules and Imports

### 11.1 Синтаксис

```brig module
module Http.Client
alias Http.Client as Http
import Json
```

- Именование модулей — PascalCase. `Vec` — осознанное исключение.
- `import` — весь модуль под собственным именем: `import Lookout.Repo` делает модуль доступным и как `Lookout.Repo`, и по последнему сегменту — `Repo`.
- `alias ... as ...` — под другим именем: `alias Http.Client as Http` — модуль доступен как `Http` (и под полным именем).
- Два локальных имени модуля в одном файле не совпадают: `import A.Client` и `import B.Client` — ошибка компиляции; развести — через `alias`.
- Встроенные модули (`Json`, `Vec`, `Map`, `Enum`, `Sys`, …) доступны без `import`; `import` и `alias` для них допустимы.
- Пользовательский модуль доступен в файле только после `import` или `alias`.
- Без `from x import y`.
- `use`-инъекция макросов не вводится.
- Объявление модуля — `module Http.Client`; по умолчанию файл = модуль.

**Правило путь-файла → имя модуля.** Относительный путь от корня без `.brig`; каждый сегмент → PascalCase. `json.brig` → `Json`; `http/client.brig` → `Http.Client`. Корень — каталог входного файла программы. Явный `module ...` задаёт имя модуля: у входного файла — любое (обычно `Main`), у импортируемого файла оно обязано совпадать с именем, по которому файл найден, иначе — ошибка компиляции.

**Загрузка модулей.** Программа — входной файл и все модули, достижимые из него через `import` и `alias`. Имя разрешается по порядку: встроенный модуль, затем файл по правилу путь → имя (`import Http.Client` → `http/client.brig`). Модуль, которого нет ни там, ни там, — ошибка компиляции с `line:col` директивы (§E):

```text
error: main.brig:3:1: module Util not found
```

Каждый модуль загружается один раз, сколько бы файлов его ни импортировали. Пути поиска, пакеты и кэш байткода — вне v0.5.0.

**Циклы импорта разрешены.** Модуль состоит только из деклараций (§11.2) и не имеет кода инициализации, поэтому порядок загрузки не наблюдаем: `A` импортирует `B`, а `B` — `A`, и это корректная программа. Ошибка — только отсутствующий модуль.

**Имена из других модулей.** Тип, тип записи и конструктор варианта другого модуля квалифицируются его локальным именем: `Accounts.User{ id: 1 }`, `Shapes.Circle(r)`, аннотация `u: Accounts.User`, паттерн `Accounts.User{ name: n }`. Имена своего модуля пишутся без квалификации.

**Тип = последний сегмент модуля.** Если модуль `….X` объявляет тип `X` (имя типа совпадает с последним сегментом модуля), после `import` или `alias` этого модуля имя `X` в литерале записи, паттерне и аннотации означает тип `X`, а в `X.f(...)` — модуль:

```text
# accounts/user.brig
module Accounts.User

type User { id: Int, name: Str }

pub fn new(name) -> User{ id: 0, name: name }

# main.brig
module Main

import Accounts.User

fn main() ->
    u = User.new("Ada")          # функция модуля Accounts.User
    match u
        User{ name: n } -> n     # тип Accounts.User.User
```

Полная форма `Accounts.User.User{...}` остаётся допустимой. Пример — два файла, поэтому `text`: `check-examples` проверяет блоки по одному. Грамматика — `ModuleName` в `record_literal`, `record_pattern`, `constructor_pattern`, `type_primary` (§A.1). Реализация — T-135 (загрузка), T-137 (компиляция нескольких модулей).

### 11.2 Top-level ограничения

**Top-level модуля — только декларации:** `module`, `import`, `alias`, `type`, `fn` и `pub fn`. Top-level `let` и выражения **запрещены** в режиме `module`.

**Порядок деклараций свободный** после `module`:

```brig module
module Http.Client
alias Http.Client as Http
import Json
```

**Entry point — `fn main()` в модуле `Main`.**

**Видимость функций.** Функция модуля по умолчанию **приватна**: вызвать её или сослаться на неё как на значение (§7.6) можно только внутри её модуля. `pub fn` экспортирует функцию. У мультиклозной функции `pub` стоит перед каждым клозом; клозы одной функции с `pub` и без — ошибка контекстного анализа (§F.3). Локальная `fn` (§6.5) `pub` не имеет — ошибка парсинга.

```brig module
module Temperature

pub fn to_fahrenheit(c) -> scale(c) + 32

fn scale(c) -> c * 9 / 5
```

Вызов или ссылка на приватную функцию другого модуля — ошибка компиляции:

```text
error: main.brig:6:5: scale/1 is private to Temperature
```

- Без `pub` вызываются функции, которые вызывает тулчейн, а не код: `main` модуля `Main` и тестовые функции `brig test` (T-149).
- Типы, конструкторы вариантов и поля записей всегда публичны.
- В сессии REPL не-`pub` функции модулей, загруженных из файлов пользователя, видны из вводов (§11.4, «Загрузка»).

Реализация — T-143, она же переводит на `pub fn` существующие примеры и программы.

### 11.3 Режимы парсинга

Один парсер, флаг `mode: module | repl | script`.

- `module` — файл, который начинается с `module`, и любой файл, найденный через `import`/`alias` (§11.1), даже без строки `module`. Top-level — только декларации (§11.2); `let`/`expr` — ошибка парсинга.
- `repl` — порция ввода REPL (§11.4). Инструкции — `repl_input` (`brig.ebnf`): `import`, `alias`, связывания, локальные `fn` и выражения.
- `script` — файл без `module`, запущенный напрямую или загруженный в сессию REPL. Инструкции — те же, что у ввода REPL (`script` в `brig.ebnf`); `type` и `pub fn` в нём — ошибка парсинга, им место в модуле.

**Режим `script`** (research Q-script, вариант B). Top-level инструкции исполняются по порядку, сверху вниз, так же, как исполнялись бы вводы REPL с тем же текстом:

- каждая top-level инструкция — своя лексическая область (§11.4): повторное связывание имени на верхнем уровне — shadowing, замыкания захватывают связывание своей инструкции;
- имя видно только инструкциям ниже своего связывания: вызвать `fn`, объявленную ниже, нельзя;
- `fn main()` в script-файле — обычная локальная функция, автоматически не вызывается. Если script объявляет `fn main()` и нигде не ссылается на `main`, `brig check` печатает info (exit code не меняется, §E.3): `info: <file>:<line>:<col>: script defines fn main() but never calls it; add module Main to run it`;
- пустые строки блок не закрывают (§2.1): это файл, правило пустой строки из §11.4 к нему не относится;
- непойманный `raise` останавливает скрипт на этой инструкции, инструкции ниже не исполняются;
- первая строка `#!…` — обычный комментарий (§1.1), поэтому script-файл можно запускать через shebang.

```brig repl
> xs = [3, 1, 2]
> total = Enum.fold(xs, 0, (acc, x) -> acc + x)
> total
6
```

Тот же текст без `>` и без строки ответа — script-файл: три инструкции, исполненные по порядку. Script-файл нельзя импортировать: `import` находит файл как модуль (§11.1), и top-level `let`/`expr` в нём — ошибка парсинга режима `module`.

`brig check` выбирает режим по тому же правилу, что и запуск файла: файл без `module` проверяется как script (разбор и контекстный анализ инструкций по порядку), но не исполняется.

Исключения путь→модуль: `Prelude`, `Main`, `Vec`, builtins — фиксированный список.

### 11.4 REPL

Каждая top-level инструкция ввода REPL — **новая top-level лексическая область**. Имена из предыдущих инструкций видны. Повторное связывание того же имени — shadowing между областями, не rebinding (принцип #12 соблюдён). Внутри одной инструкции rebinding по-прежнему запрещён.

**Лексический снимок для замыканий.** Замыкание захватывает связывание своей инструкции. Поздний `x = 10` в следующей инструкции не влияет на ранее созданное замыкание.

```brig repl
> x = 5
> f = () -> x
> x = 10        # shadowing: новая область
> f()
5              # лексический снимок: f видит старый x
> x + 1
11
```

**Ввод.** Порция ввода — текст, который REPL исполняет целиком; в ней одна или несколько top-level инструкций (`repl_input`), каждая — своя область, исполняются по порядку. Ввод продолжается следующей строкой, пока:

1. открыта скобка (`(`, `[`, `{`, `%[`, `%{`), строковый литерал (`"…"`, `b"…"`, `rx"…"`, `dec"…"`) или интерполяция `\(`;
2. строка кончается так, что по грамматике дальше ждётся `INDENT`-блок: блочная конструкция (§2.4) без тела на этой строке — `fn f(x) ->`, `match v`, `recv`, `trap`, `with …`, `else` и т.п.;
3. открыт `INDENT`-блок из п. 2: строки тела продолжают ввод.

Открытые блоки закрывает **пустая строка**: в REPL она завершает порцию, если скобки и литералы закрыты (в файле пустые строки блок не закрывают, §2.1). Строка-продолжение по ведущему оператору (§2.2) присоединяется к вводу только внутри открытого блока — после завершённой порции REPL не ждёт следующей строки. Строка без блока, со всеми закрытыми скобками, завершает порцию сразу.

```text
brig[1]> fn fact(n) ->
   ...>     match n
   ...>         0 -> 1
   ...>         _ -> n * fact(n - 1)
   ...>
brig[1]> fact(5)
120
brig[2]> v(1) + 1
121
```

Пример — `text`: `check-examples` исполняет каждую строку `>` REPL-блока как отдельный ввод (§G.5), продолжений строк он не знает. Вид приглашений здесь условный.

**Процесс.** Все вводы сессии исполняет один долгоживущий актор сессии:

- `self()` возвращает один и тот же `Pid` во всех вводах; ящик сессии общий для всех вводов, сообщения в нём копятся между вводами;
- акторы, заспавненные из ввода, работают и между вводами, пока REPL ждёт следующей порции; `recv` во вводе получает их сообщения;
- прерывание ввода (Ctrl-C) снимает текущее вычисление, но не актор сессии: привязки, ящик и заспавненные акторы сохраняются. Прерывание — не `raise`: `trap` его не ловит; выполнение `ensure`-областей прерванного ввода не гарантируется;
- непойманный `raise` завершает ввод ошибкой, но не сессию. Привязки предыдущих вводов и инструкций этого ввода, исполненных до `raise`, сохраняются;
- `watch` на актор сессии — по §12: `:down` приходит в ящик сессии и разбирается следующим `recv`, текущий ввод он не обрывает, сессия остаётся жива. `link(pid)` из сессии делает её владельцем `pid` (§12.2): смерть такого актора сессии ничего не шлёт и ввод не прерывает.

**Загрузка.** Кроме вводов, в сессию загружаются файлы пользователя — при запуске консоли или хелпером `load/1`:

- модуль из файла пользователя виден в сессии целиком, **включая не-`pub` функции** (исключение из §11.2): консоль — инструмент исследования своего кода;
- модули зависимостей (пакеты, встроенные модули) — только `pub`, как в §11.2;
- script-файл (§11.3) исполняется как последовательность вводов; его привязки остаются в сессии;
- ошибка загрузки (ошибка компиляции модуля, `raise` в script-файле) не отменяет привязки и модули, загруженные до неё; сессия продолжает работу.

**Хелперы.** Консольные команды — функции встроенного модуля **`Repl`**, а не отдельный синтаксис (`:help` — валидный атом). Модуль `Repl` существует только в сессии REPL: в ней он доступен без `import`, а в режиме `repl` его функции видны ещё и голыми именами, как прелюдия (§11.5). В файлах режимов `module` и `script` голых имён хелперов нет; файл, исполняемый вне сессии, модуль `Repl` не видит.

| Имя | Арность | Аргументы | Результат |
| --- | --- | --- | --- |
| `h` | 1 | `(f)` — функция-значение `M.f`/`f` (§7.6) или имя модуля `M` | `()`; печатает сигнатуры всех арностей и doc-комментарий `##` (§11.6); для модуля — его документацию и список `pub`-функций |
| `i` | 1 | `(v)` | `()`; печатает вид значения, размер; для записи — тип и поля; для `Pid` — жив ли актор и размер ящика |
| `v` | 0..1 | `()` или `(n)`, `n`: `Int` | значение ввода с номером `n`; `v()` — последнего пронумерованного; номера нет — `raise((:no_value, n))` |
| `bindings` | 0 | `()` | `Map` `Str` → значение: видимые привязки сессии |
| `reset` | 0 | `()` | `()`; снимает все привязки сессии; актор сессии, ящик, заспавненные акторы и загруженные модули остаются |
| `load` | 1 | `(path)`, `path`: `Str` | `()`; загружает модуль или script-файл в сессию (см. «Загрузка»); ошибка — `raise((:load_error, (path, msg)))` |
| `flush` | 0 | `()` | `List` сообщений ящика сессии; печатает их и снимает из ящика |
| `time` | 1 | `(f)`, `f()` | `(us, r)`: `us` — время вызова `f()` в микросекундах (`Int`), `r` — его результат |
| `dis` | 1 | `(f)` — функция-значение | `()`; печатает байткод функции |
| `recompile` | 0 | `()` | `()`; перекомпилирует загруженные модули пользователя, семантика — T-208 |
| `tree` | 0 | `()` | `()`; печатает дерево живых акторов: корни — акторы без супервизора, дети супервизора — по `Supervisor.which_children` (§13.1, T-223); у узла pid, `name`, `status` и размер ящика из `Actor.info` (§12.13) |
| `info` | 1 | `(pid)`, `pid`: `Pid` | `()`; печатает `Actor.info(pid)` целиком; мёртвый — строка о том, что актор не жив; `pid` не `Pid` — `(:type_error, (:info, pid))` |
| `top` | 1 | `(n)`, `n`: `Int` ≥ 1 | `()`; печатает `n` живых акторов с наибольшим `reductions` по убыванию, со счётчиками `Actor.info`; иначе `(:type_error, (:top, n))` |
| `observe` | 0 | `()` | `()`; полноэкранный вид на TTY — дерево, ящики, счётчики и лента последних `[:vm, :actor, :crash]` и `[:vm, :actor, :down]`, пока пользователь не выйдет; без TTY — один кадр тем же видом; если observe уже открыт (`Error(:already_exists)` у его подписки) — печать «observe уже открыт» и `()` |

- **Нумерация.** Ввод, значение которого не `()`, получает очередной номер `n`; приглашение `brig[n]>` показывает номер, который получит следующий такой ввод. Значение ввода — значение его последней инструкции; у связывания `pattern = expr` это значение `expr`, у локальной `fn`, `import` и `alias` — `()`. Вводы со значением `()` и вводы, завершённые ошибкой, номер не получают. `v(n)` — значение ввода `n`, `v()` — значение последнего пронумерованного ввода.
- **Затенение.** Связывание во вводе с именем хелпера затеняет его по правилам затенения прелюдии (§11.5): info-диагностика, хелпер остаётся доступен как `Repl.h`. Так же хелпер затеняет функция загруженного кода, видимая вводу голым именем: `fn` script-файла (она — связывание сессии) и `fn` модуля файла в доктесте (§11.6). Функции модуля, загруженного в сессию `-i`, видны только по имени модуля (`M.v`) и с хелперами не пересекаются.
- **Хелперы observer** (`tree`, `info`, `top`, `observe`) — такие же функции `Repl`, не синтаксис. Они читают только `Actor.list` и `Actor.info` (§12.13) и ничего не останавливают: акторы, заспавненные из вводов и загруженного приложения (`brig -i .`), продолжают работать, пока хелпер печатает, так что снимок racy (§15.2). `observe` дополнительно показывает ленту последних `[:vm, :actor, :crash]` и `[:vm, :actor, :down]` (§12.14); занятый id этой подписки — «observe уже открыт» и `()`. Подключение к чужому процессу (`brig observe` по сокету) — горизонт.
- **Хелперы фреймворка.** Фреймворк добавляет свои хелперы (`routes()`, `app()` у Calmar) — функциями своего модуля, которые он регистрирует в сессии кодом, исполненным до первого ввода. Зарегистрированные функции видны голыми именами так же, как функции `Repl`. API регистрации — T-206.

Имена и арности фиксированы этой таблицей. Вид печати (формат, цвета, ширина) — тулчейн, не язык.

### 11.5 Прелюдия

Голые имена без `import`. Порядок аргументов — субъект первым (§7.5). Колонка «Авто-raise» перечисляет ошибки самой функции; ошибка внутри колбэка пробрасывается как есть.

| Имя | Арность | Аргументы | Результат | Авто-raise |
| --- | --- | --- | --- | --- |
| `len` | 1 | `(v)` | `Int`: элементы `List`/`Vector`/`Set`/`Tuple`, пары `Map`, кодпоинты `Str`, байты `Bytes` | `(:type_error, (:len, v))` |

#### Модуль `Enum`

`Enum` (DD T-257) — функции над перечислимыми коллекциями: `List`, `Vector`, `Range`, `Set`, `Map`. Встроенный модуль, доступен без `import`; субъект — первый аргумент (§7.5). Элемент `Map` — пара `(k, v)`. Порядок обхода `List`, `Vector`, `Range` — порядок элементов, `Set` и `Map` — term order элементов и ключей (§7.4), как у печати. Результат — `List`, кроме колонки «Результат» с другим видом. Каждая функция обходит коллекцию один раз; колбэк вызывается по порядку обхода, `find`, `all?`, `any?` останавливаются на первом решающем элементе. Пользовательских перечислимых типов и ленивых последовательностей нет.

Общие авто-raise: субъект не из пяти видов — `(:type_error, ((:enum, :f), v))`, `f` — имя функции; убывающий `Range` с вычисленными границами — `(:range_error, (start, end))`, как у `list` (§4.3); предикат вернул не `Bool` — `(:type_error, (:expected_bool, r))`, как условие `if` (§8.1); ошибка внутри колбэка пробрасывается как есть. Сравнение в `sort`, `sort_by`, `min`, `max` — оператор `<` (§7.4): несравнимые элементы и `Decimal`↔`Float` — `(:type_error, (:compare, (a, b)))`.

| Имя | Арность | Аргументы | Результат | Авто-raise |
| --- | --- | --- | --- | --- |
| `Server.call` | 3 | `(pid, req, timeout)`, `timeout` — мс | `Ok(v)` — сервер ответил; `Error(:timeout)` — ответа нет, в том числе сервер мёртв; `Error(:busy)` — ящик полон (§12.2) | — |
| `Server.reply` | 2 | `(from, v)`, `from` — пара `(pid, ref)` | `()`; поздний или повторный ответ отбрасывается | `(:type_error, (:reply, from))` — `from` не `(Pid, Ref)` |

#### Модуль `Supervisor`

Супервизор (§13.1): актор, который запускает детей, наблюдает за ними через `watch` и перезапускает по `restart`.

| Имя | Арность | Аргументы | Результат | Авто-raise |
| --- | --- | --- | --- | --- |
| `Supervisor.start` | 1 | `(spec)`, `spec`: `{ strategy, max_restarts, within, children }` | `Pid` супервизора, когда все `start` детей вернулись | `(:start_failed, (name, reason))` — `start` ребёнка упал или вернул не `Pid`; `(:start_failed, :timeout)`; `(:type_error, (:start, v))` — `strategy` не `:one_for_one`, `restart` не `:permanent`/`:transient` |
| `Supervisor.stop` | 3 | `(sup, reason, opts)`, `opts`: `{ timeout }` | `Ok(())`; `Error(:timeout)` — остановка не подтверждена | — |
| `Supervisor.which_children` | 1 | `(sup)` | `List` из `(id, pid, restart)` в порядке старта | `(:type_error, (:which_children, sup))` — `sup` не `Pid`; `(:timeout, (:which_children, sup))` |

Больше `max_restarts` перезапусков за `within` мс — супервизор гасит остальных детей и падает с `(:max_restarts, (name, reason))`.

#### Модуль `Behavior`

Актор с поведением `Behavior{ handlers: %{...} }` (§13.2).

| Имя | Арность | Аргументы | Результат | Авто-raise |
| --- | --- | --- | --- | --- |
| `Behavior.spawn` | 2 | `(b, init_state)` | `Pid` актора; голое имя — `spawn_behavior` (§13.2) | `(:type_error, (:spawn_behavior, v))` — `b` не `Behavior` или `handlers` не `Map` |

Ошибки самого актора (в нём, не у вызывающего): тега нет в `handlers` — `(:no_handler, tag)`; аргументов больше трёх — `(:bad_arity, tag)`; колбэк вернул не пару — `(:badmatch, v)`.

### 11.6 Тест-фреймворк: `Test.*` и `brig test`

`Test.*` — не голые имена (в отличие от §11.5), а имена модуля `Test`, доступные без `import`, как встроенный модуль.

| Имя | Арность | Аргументы | Результат | Авто-raise |
| --- | --- | --- | --- | --- |
| `Test.describe` | 1 | `(name)` | `()`; задаёт текущую группу для последующих `Test.it` до следующего `Test.describe` | `(:type_error, (:test_describe_name, name))` — `name` не `Str` |
| `Test.it` | 2 | `(name, thunk)`, `thunk()` | `()`; регистрирует тест в реестре | `(:type_error, (:test_it_name, name))`; `(:type_error, (:test_it_thunk, thunk))` — `thunk` не функция |
| `Test.run` | 0 | `()` | `Int` — число упавших тестов | — |
| `Test.assert_eq` | 2 | `(a, b)` | `()` | `(:assert_eq_failed, (a, b))` — `a` и `b` не равны (§4.8) |
| `Test.assert_ne` | 2 | `(a, b)` | `()` | `(:assert_ne_failed, (a, b))` — `a` и `b` равны |
| `Test.assert` | 1 | `(x)` | `()` | `(:assertion_failed, ())` — `x == false`; `(:type_error, (:assert_expected_bool, x))` — `x` не `Bool` |
| `Test.fail` | 1 | `(msg)` | не возвращает | `(:assert_fail, msg)` |

`Test.run()` прогоняет все тесты, зарегистрированные `Test.it` с момента последнего `Test.run()` (реестр очищается после прогона), в порядке регистрации; падение одного теста не прерывает остальные. На каждый тест — строка `ok <группа> > <имя>` или `FAIL <группа> > <имя>` (без группы — просто `<имя>`), в конце — сводка `N passed, M failed`.

```brig repl
> Test.it("2 + 2", () -> Test.assert_eq(2 + 2, 4))
> Test.run()
0
```

**`brig test [path]`.** Подкоманда CLI (`cmd/brig`), не часть языка. Под `path` (файл или каталог; по умолчанию `.`) каждый файл с именем `*_test.brig` — тестовый файл: его top-level `fn test_*()` без параметров — тесты; каждый прогоняется на свежей ВМ, тесты, зарегистрированные вызовами `Test.it` внутри него, прогоняются следом на той же ВМ. `path`, который не файл и не каталог, — ошибка. Файлы обходятся в лексикографическом порядке путей.

Кроме тестовых функций, в каждом `.brig`-файле под `path` (тестовом или нет, если в нём есть `##`) исполняются доктесты (ниже). Сводка `N passed, M failed` печатается в stdout по всем файлам. Exit-код: `0` — все тесты и доктесты прошли и все затронутые файлы скомпилировались; `1` — упал тест, доктест, файл не скомпилировался или `path` не существует. `BRIG_VERIFY=1` включает `compiler.Verify`, как и у остальных подкоманд `brig`.

**Доктесты.** Doc-комментарий — одна или несколько подряд идущих строк `##` (после отступа), не считая `###`; префикс `##` и один пробел за ним снимаются, дальше текст доктеста трактуется построчно, как в этой спеке. Fenced-блоки ```` ```brig repl ```` внутри doc-комментария `brig test` исполняет как REPL-блоки спеки (§G.5, режим `repl`): строки `>` — ввод одной REPL-сессии, строка без `>` сразу после — ожидаемый ответ, сравнение — через `==`. Ввод и ответ видят модуль файла так же, как его собственный код: функции (в том числе не-`pub`), типы записей и конструкторы вариантов — голыми именами, импортированные им модули — как в файле; функция модуля с именем хелпера `Repl` затеняет хелпер (§11.4 «Затенение»). Ответ вычисляется на отдельной ВМ с тем же модулем, но без привязок ввода: `## > parse("1.2.3")` и ответ `## Ok(Version{ major: 1, minor: 2, patch: 3, pre: [] })` сравниваются через `==`, а имя, связанное во вводе, в ответе не видно. REPL-блоки самой спеки (§G.5) модуля не имеют и считают ответ на чистой сессии. Провал доктеста указывает строку исходника `.brig`-файла. Fenced-блоки с другими метками внутри `##` не исполняются.

```text
## Складывает два числа.
##
## ```brig repl
## > add(2, 3)
## 5
## ```
fn add(a, b) ->
    a + b
```

**Не входит в этот объём:** `Test.isolated` (отдельный экземпляр рантайма на тест), параллельный запуск тестов и файлов, `brig doc` (рендер `##` в отдельную документацию) — горизонт.

### 11.7 Doc-комментарии `##`

Документация кода — doc-комментарии `##` (research 03/L24, 22; **Should**, §16). Атрибутов `@doc` и других `@`-форм в языке нет.

- **Форма.** Doc-комментарий — одна или несколько подряд идущих строк, которые после отступа начинаются с `##` (строка `###…` — обычный комментарий). Префикс `##` и один пробел за ним снимаются; остаток — Markdown.
- **Место.** Doc-комментарий стоит перед объявлением, которое документирует, — `module`, `type` или клозом функции (`pub fn`/`fn`); между ними допустимы только пустые строки. Документация модуля — перед `module`, функции — перед её первым клозом. Публичное API модуля — `module`, `type` и `pub fn` — документируется; у приватных функций `##` допустим.
- **Лексер и парсер.** Для лексера `##` — обычный комментарий (§1.1): doc-комментарий не меняет offside, токены и семантику программы. Программа, в которой все `##` заменены на `#`, ведёт себя так же.
- **Доктесты.** Fenced-блок ```` ```brig repl ```` внутри doc-комментария — доктест: строки `>` — ввод, в котором видны функции модуля файла, следующая строка без `>` — ожидаемое значение, сравнение через `==`; `raise` ожидается строкой `raise <значение>`. Доктесты исполняет `brig test` (§11.6); блоки с другой меткой не исполняются.
- **Где видно.** Команда `h` консоли печатает doc-комментарий функции или модуля (§11.4).

```brig module
## Температурные шкалы.
module Temperature

## Переводит градусы Цельсия в Фаренгейт.
##
## ```brig repl
## > to_fahrenheit(100)
## 212
## ```
pub fn to_fahrenheit(c) -> c * 9 / 5 + 32
```

**Горизонт** (не входит в Should): `brig doc` — статический сайт из `##` и аннотаций; предупреждение `brig check` о `pub fn` без `##`; требование документации в `brig publish`; проверка ссылок `[M.f]`; сохранение `##` в AST и метаданных байткода.

## 12. Actors

### 12.1 Модули vs Акторы

Модули — неймспейсы без состояния. Акторы — процессы с PID, состоянием и ящиком.

### 12.2 Создание и связывание

```brig module
fn main() ->
    pid1 = spawn(() -> counter_loop(0))
    link(pid1)
    pid2 = spawn_linked(() -> counter_loop(0))
    ref = watch(pid2)
    unwatch(ref)
    (pid1, pid2)

# хелперы примера
fn counter_loop(n) -> n
```

`watch(pid)` присылает `(:down, ref, reason)` в `recv`.

**Семантика `link`/`spawn_linked` — связь владелец → ребёнок:**

- `link(pid)` делает **вызывающего владельцем** `pid`; результат — `()`, ref не выдаётся. `pid` не `Pid` — `(:type_error, (:link, pid))`. `pid` мёртв или никогда не существовал — ничего (как `send`); `link(self())` — ничего.
- `spawn_linked(fn)` ≡ `spawn(fn)` + `link` ребёнка со стороны создателя, атомарно.
- **Смерть владельца по любой причине** (нормальный возврат, падение, `exit`, в том числе `:kill` и `:resource_limit`) делает каждому его ребёнку `exit(child, (:linked_exit, reason))`, где `reason` — причина смерти владельца. Это `exit`, а не `raise` (§12.7): `trap` ребёнка его не ловит, `ensure` ребёнка выполняются (причина не `:kill`, даже когда владельца убили), наблюдатели ребёнка получают `(:down, ref, (:linked_exit, reason))`. Внуки уходят по той же цепочке, причина вкладывается на каждом шаге.
- Связь **однонаправленная**: смерть ребёнка владельцу ничего не шлёт и его не завершает. Наблюдение за ребёнком — только `watch`/`spawn_watched`; `link` — не синоним `watch` и в `watchers`/`watching` (§12.13) не виден.
- Автоматической эскалации **ошибок** через границы акторов нет: передаётся `exit`, а не значение `raise` (§16).
- У ребёнка может быть несколько владельцев (`spawn_linked` плюс `link` из другого актора): его завершает смерть любого из них. Снятия связи нет — `unwatch` относится только к `watch`.
- `:down` доставляется в **начало очереди** с приоритетом, временно превышая HWM.
- `send` возвращает `Error(:busy)`, когда размер пользовательской очереди ≥ HWM. HWM по умолчанию — **10 000** сообщений; порог на актора задаёт поле лимитов `spawn` `mailbox_hwm` (§12.10).
- Отказ по HWM не молчит: получатель считает отказы в счётчике `dropped` (`Actor.info`, §12.10), VM излучает `[:vm, :mailbox, :hwm]` (§12.14). Ящик получателя сверх порога не растёт, сам получатель жив.
- `mailbox_size()` возвращает размер пользовательской очереди.
- `spawn_watched(fn)` ≡ `spawn(fn)` + `watch` атомарно, возвращает `(pid, ref)` (§12.7). У `spawn`, `spawn_linked`, `spawn_watched` есть форма со вторым аргументом — бюджет хода (§12.10).

**Поведение системных сообщений при HWM наблюдателя:**

- Пользовательские сообщения действуют по HWM: `send` возвращает `Error(:busy)`.
- `:down` доставляется всегда, с приоритетом, временно превышая HWM.
- При аномальном переполнении контрольных сообщений — падение `(:system_mailbox_overflow, count)`.

### 12.3 Отправка сообщений

```text
fn main() ->
    send(worker, :hello)
    send(worker, (:work, data))
```

`send` возвращает `Result<(), Atom>`: `Ok(())` при успехе, `Error(:busy)` при переполнении. Арность `Result` — два параметра.

`send` к мёртвому процессу — `Ok(())`, сообщение теряется (как в Erlang). `mailbox_size(pid)` возвращает `Int`, для мёртвого процесса — `0`.

`Error(:busy)` — ящик получателя полон (HWM, по умолчанию 10 000, на актора — `mailbox_hwm` при `spawn`, §12.10): сообщение не принято, получатель жив и продолжает работу. Отказ виден получателю как `dropped` в `Actor.info` и наблюдателю как событие `[:vm, :mailbox, :hwm]` (§12.14). Блокирующего `send` нет: отправитель сам решает, повторить, отбросить или упасть.

### 12.4 `recv`

```brig
recv
    (:value, v) -> v
    (:done)     -> :done
else msg
    log("unhandled: \(msg)")
after 5000 -> :timeout
```

**Offside `else`/`after` формализован.**

> `else` и `after` — клаузы `recv` на **том же отступе, что сам `recv`**. Обе опциональны. Если обе присутствуют — порядок фиксирован: сначала `else`, затем `after`. `after` без `else` разрешён. `else` без `after` разрешён. Более одного `after` — ошибка. Более одного `else` — ошибка.

**`else` — только блочная форма** (`else name` + INDENT…DEDENT), без `->`. **`after` — как тело ветки:** `after expr -> expr` или `after expr ->` и блок INDENT…DEDENT.

Ключевое отличие от v0.4.2: `else`/`after` находятся **вне** блока `INDENT...DEDENT` веток — то есть на уровне отступа `recv`, что соответствует прозе и примеру.

**Границы однострочной формы.** `recv` в однострочной форме заканчивается на `NEWLINE`. В блочной — на `DEDENT`. То же для `match`, `with`, `trap`.

`after N` — таймаут пустого ящика, `N` — миллисекунды. Это не периодика: `after` срабатывает, только когда ящик пуст `N` мс, и каждое сообщение отодвигает его. Для «через `N` мс, что бы ни происходило» и для периодических тиков — `Timer` (§12.11).

`recv!` и stash-механизмы убраны. Оставлен один синтаксис необработанных: `else msg`.

Однострочная форма:

```brig
x = recv (:value, v) -> v
```

**`else` в `recv` требует `lower_ident`.** `else _ ->` не поддерживается. Для игнорирования сообщения — `else msg` с `msg` в теле (или `_msg`, если имя не нужно).

**Плата за отказ от selective receive.** Прикладная идиома — актор складывает «неожиданные» сообщения в стейт:

```brig module
fn worker_loop(state) ->
    recv
        (:reply, id, v) when has_pending(state, id) ->
            worker_loop(resolve_pending(state, id, v))
        (:reply, id, v) ->
            worker_loop(stash(state, id, v))
        (:stop) -> :ok
    else msg
        log("unknown: \(msg)")
        worker_loop(state)

# хелперы примера
fn has_pending(_state, _id) -> false
fn resolve_pending(state, _id, _v) -> state
fn stash(state, _id, _v) -> state
```

### 12.5 `recv` vs `match`

`match` — чистый, не блокирует, всегда блочный; `recv` — блокирует, имеет `after`/`else`.

### 12.7 `exit` и `spawn_watched`

```brig
fn idle() ->
    recv
        _msg -> idle()

fn main() ->
    (pid, ref) = spawn_watched(() -> idle())
    exit(pid, :shutdown)
    recv
        (:down, r, reason) when r == ref -> reason
```

**`exit(pid, reason)`** завершает актор `pid` с причиной `reason` (любое значение).

- **Асинхронно.** `exit` возвращается сразу, результат — `Ok(())`, в том числе для мёртвого или несуществующего `pid` (как `send`, §12.3). Вид результата `Result<(), Atom>` оставлен под ошибки будущей распределённости.
- **Когда жертва завершается.** В ближайшей точке редукции (K-4 в docs/02) или ожидания: исполняющийся актор — на ближайшей редукции, в том числе вытесненный (он снимается с очереди готовых, не дожидаясь своего кванта); актор, ждущий в `recv` или `await`, будится и завершается, не получив сообщения. Сигнал `exit` не проходит через ящик: не виден `recv` и `mailbox_size` и не учитывается в HWM.
- **`ensure` жертвы выполняются** (LIFO, от внутреннего `trap` к внешнему, §10.3) для любой причины, кроме `:kill`: так закрываются ресурсы. `exit(pid, :kill)` завершает без `ensure` — для зависших акторов.
- **`trap` не перехватывает `exit`.** Кадры `trap` пропускаются, тело не продолжается ни в одном из них; перехват сделал бы остановку супервизором негарантированной. Ошибка внутри `ensure` при таком завершении причину не меняет, оставшиеся `ensure` выполняются.
- **Повторный `exit`** актору, который уже завершается, игнорируется, кроме `exit(pid, :kill)`: он прерывает оставшиеся `ensure`. Причина остаётся первой.
- **Наблюдатели** получают `(:down, ref, reason)` с той же `reason`, `:kill` — как есть. Вместе со смертью снимаются имена реестра (§12.8) и слоты ответов (§12.9).
- **Дети умершего** (`link`, `spawn_linked`, §12.2) получают `exit(child, (:linked_exit, reason))` в той же редукции, что и наблюдатели — `:down`. Причина `(:linked_exit, reason)` — не `:kill`, поэтому `ensure` ребёнка выполняются, даже когда владельца убили `:kill`.
- **`exit(self(), reason)`** — то же для себя, но синхронно: актор завершается сразу, как `raise`, который не ловит ни один `trap`; `ensure` выполняются.

Мягкая остановка — не механизм VM, а соглашение: сообщение `(:shutdown, deadline)`, которое актор обрабатывает сам; `exit` — следующий шаг после дедлайна. Политика — `Supervisor` (§13.1).

**`spawn_watched(f) -> (Pid, Ref)`** ≡ `spawn(f)` + `watch(pid)` со стороны родителя, **атомарно**: нет состояния, в котором ребёнок уже исполняется, а наблюдение ещё не взведено. Ребёнок, упавший на первой редукции, всё равно даёт `(:down, ref, reason)`. В однопоточном run-loop гонки нет и так; контракт фиксирован, чтобы не менять API при переходе к N:M (§15.2).

### 12.8 Реестр имён

```brig
fn checker_loop(id) ->
    recv
        :check -> checker_loop(id)

fn main() ->
    pid = spawn(() -> checker_loop(42))
    register((:checker, 42), pid)
    match whereis((:checker, 42))
        Some(p) -> send(p, :check)
        None    -> Error(:not_running)
```

Реестр — механизм VM, общий для всех акторов: актор находится по имени без протаскивания PID через все вызовы, перезапущенный актор регистрируется под тем же именем с новым PID.

- **`register(name, pid) -> Result<(), Atom>`.** Имя — любое значение, сравнивается по правилам ключей `Map` (§4.8): `:repo`, `(:checker, 42)`. `Ok(())` — имя связано с `pid`. Имя уже связано (с любым PID, в том числе с тем же) → `Error(:already_registered)`. `pid` мёртв → `Error(:not_alive)`. У одного PID может быть несколько имён. Регистрировать может любой актор, не только сам `pid`. `pid` не `Pid` → `(:type_error, (:register, pid))`.
- **`unregister(name) -> ()`** снимает связь, если она есть; идемпотентно.
- **`whereis(name) -> Option<Pid>`**: `Some(pid)` или `None`.
- **Снятие при смерти атомарно с `:down`.** Имена актора снимаются в тот же момент, когда его наблюдателям ставится `:down`; актор, получивший `:down`, и любой `whereis` после смерти видят `None`.
- **`send` по имени нет.** Только явный `whereis` (§0.3): отсутствие получателя видно в коде как `None`.

### 12.9 `await` и `reply`: ответ по ref мимо ящика

Библиотечная функция, которая внутри ждёт ответ через `recv` (`Server.call`, клиент HTTP, SQL), съела бы чужие сообщения вызывающего актора — его `:tick`, его протокол. Идиома «сложить неожиданное в стейт» (§12.4) тут не работает: библиотека не знает стейта вызывающего. Для этого — ref-слоты:

```brig
fn get(server, key) ->
    ref = make_ref()
    send(server, (:get, key, (self(), ref)))
    await(ref, 5000)

fn server_loop(store) ->
    recv
        (:get, key, (from, ref)) ->
            reply(from, ref, Map.get(store, key))
            server_loop(store)

fn main() ->
    server = spawn(() -> server_loop(%{:a => 1}))
    get(server, :a)
```

- **Слот.** Каждый `make_ref()` открывает слот ответа у актора, который его создал (владелец). Слот пуст → заполнен (первым `reply`) → закрыт (после `await`).
- **`reply(pid, ref, value) -> ()`.** Если `pid` жив, `ref` создан `pid` и его слот пуст — `value` кладётся в слот, ждущий `await` будится. Иначе ответ молча отбрасывается: `pid` мёртв, `ref` создан не им, слот уже заполнен (побеждает первый ответ) или закрыт (поздний ответ). Ответ **не попадает в ящик**: не виден `recv` и `mailbox_size`, не учитывается в HWM, `Error(:busy)` не бывает. `pid` не `Pid` или `ref` не `Ref` → `:type_error`.
- **`await(ref, timeout) -> Result<V, Atom>`.** Слот заполнен → `Ok(value)` сразу. Иначе актор ждёт ответа не дольше `timeout` миллисекунд, затем `Error(:timeout)`. В обоих случаях слот закрывается: поздний ответ отбрасывается, повторный `await` того же ref сразу даёт `Error(:timeout)`. `timeout` — `Int` ≥ 0, бесконечного ожидания нет (для него — `recv`); иначе `(:type_error, (:await, timeout))`. `ref`, созданный не этим актором (в том числе ref из `watch`), → `(:type_error, (:await, ref))`.
- **Ящик не трогается.** Пока актор ждёт в `await`, сообщения и `:down` копятся в ящике по обычным правилам и берутся следующим `recv`. `await` — точка ожидания: `exit` его прерывает (§12.7).
- **Это не selective receive** (§16): нет паттернов, нет сканирования очереди и скрытой очереди несовпавших — слот адресуется ref за O(1), ящик и HWM не затрагиваются. Ожидание нескольких ref сразу не поддерживается.

`Server.call` (Wave 13) передаёт серверу `from = (pid, ref)`; `Server.reply(from, v)` ≡ `reply(pid, ref, v)`.

### 12.10 Бюджет хода и `Actor.info`

**Ход** — работа актора между двумя сообщениями: от старта (или от взятия сообщения `recv`, или от срабатывания `after`) до следующего такого события. Бюджет ловит один ход, который не заканчивается (бесконечный цикл, взрыв данных), и не мешает долгоживущему актору, который за всё время законно тратит много.

```brig
fn spin(n) -> spin(n + 1)

fn main() ->
    (_pid, ref) = spawn_watched(() -> spin(0), { turn_reductions: 5_000_000 })
    recv
        (:down, r, (:resource_limit, (kind, used, limit))) when r == ref ->
            (kind, used, limit)
        (:down, _r, reason) -> reason
```

- **Где задаётся.** Вторым аргументом `spawn`, `spawn_linked`, `spawn_watched` — анонимная запись с полями `turn_reductions`, `turn_alloc_bytes` и `mailbox_hwm` (`Int` > 0). Поля необязательны, нет поля — нет лимита (у `mailbox_hwm` — порог по умолчанию, 10 000); без второго аргумента лимитов нет. Другое поле или значение — `(:type_error, (:spawn, limits))`. Дети лимиты не наследуют. Child spec супервизора (Wave 13) передаёт лимиты сюда.
- **`mailbox_hwm`** — порог ящика этого актора (§12.2), а не лимит хода: превышение не завершает актора, а отвечает отправителю `Error(:busy)`.
- **Счёт.** Редукции — по K-4 (docs/02), включая колбэки прелюдии (G3). Выделенные байты — оценка реализации: точность не гарантируется, гарантируется монотонность в пределах хода. Счётчики хода обнуляются, когда `recv` берёт сообщение или срабатывает `after`; `await` ход не завершает.
- **Превышение** → VM делает `exit(pid, (:resource_limit, (kind, used, limit)))`, `kind` — `:turn_reductions` или `:turn_alloc_bytes`, `used` ≥ `limit`. Дальше — по §12.7: `ensure` выполняются (уже вне бюджета; для зависшего `ensure` — `exit(pid, :kill)`), наблюдатели получают `:down` с этой причиной, решение — за супервизором.
- **`Actor.info(pid) -> Option<{ reductions, alloc_bytes, mailbox, dropped, turn_reductions, turn_alloc_bytes }>`**: всего редукций и байт с рождения, `mailbox_size(pid)`, число не принятых по HWM сообщений (`dropped`, §12.2) и счётчики текущего хода; мёртвый — `None`. Для чужого актора значения racy, как `mailbox_size(pid)` (§15.2). Поля для observer (имя, статус, связи наблюдения) добавляет §12.13. `alloc_rate` и оценка размера стейта — горизонт.

### 12.11 `Timer`, `Time`, `Global`

Три маленьких модуля рантайма. Они не акторы и не прелюдия: это механизмы VM, доступные как `Module.f(...)` без `import` (как `Actor.info`, §12.10).

```brig
fn tick_loop(n) ->
    recv
        :tick ->
            _ = Timer.send_after(100, self(), :tick)
            tick_loop(n + 1)
        :stop -> n

fn main() ->
    t0 = Time.monotonic_ms()
    me = self()
    _ = Timer.send_after(100, me, :tick)
    ref = Timer.send_after(1000, me, :stop)
    Timer.cancel(ref)
    Time.monotonic_ms() - t0
```

```brig
fn main() ->
    Global.put(:config, %{:retries => 3})
    match Global.get(:config)
        Some(cfg) -> Map.get(cfg, :retries)
        None      -> Error(:not_set)
```

**`Timer.send_after(ms, pid, msg) -> Ref`.** Через `ms` миллисекунд VM отправляет `msg` актору `pid`, как это сделал бы `send(pid, msg)`. Возвращённый `Ref` — обычное значение, у него нет слота ответа (§12.9): `await` на нём — `(:type_error, (:await, ref))`.

- **Доставка.** Ровно одна, без повторов; периодика — таймер, взводимый заново в обработчике (пример выше), так дрейф и остановка видны в коде. Получатель мёртв — сообщение теряется, как у `send` (§12.3). Ящик получателя полон (HWM) — сообщение молча теряется: `Error(:busy)` некому вернуть, отправителя в момент срабатывания нет. Сообщение не связано с G1 (§15.2): у него нет отправителя-актора, порядок относительно сообщений других акторов не определён.
- **Таймер принадлежит VM, а не актору.** Он переживает актора, который его взвёл. `msg` неизменяем, поэтому копирования нет.
- **`ms`** — `Int` ≥ 0; `ms = 0` срабатывает на ближайшей итерации планировщика, не синхронно с вызовом. `ms` не `Int` или < 0, `pid` не `Pid` — `(:type_error, (:send_after, arg))`.
- **Порядок срабатывания — G4 (§15.2).** Истёкшие таймеры `Timer`, `recv ... after` и `await` — одна очередь, порядок (deadline, порядок взвода). Два `send_after` с одним `ms`, взведённые подряд одним актором, доставляются в порядке вызовов.

**`Timer.cancel(ref) -> Bool`.** `true` — таймер ещё не сработал и снят: сообщение не будет отправлено. `false` — таймер уже сработал (сообщение отправлено, пусть и потеряно у получателя), уже отменён или `ref` не принадлежит ни одному таймеру (например, из `make_ref()`). Идемпотентна; отменить может любой актор, у которого есть `ref`. `ref` не `Ref` — `(:type_error, (:cancel, ref))`. Уже лежащее в ящике сообщение `cancel` не отзывает.

**`Time.monotonic_ms() -> Int`.** Монотонные миллисекунды с произвольной точки отсчёта: не убывают, не зависят от перевода системных часов. Годятся только для разностей и дедлайнов; тот же источник времени, что у очереди таймеров.

**`Time.now() -> Int`.** Миллисекунды от 1970-01-01T00:00:00Z (UTC, Unix epoch). Это стенные часы: могут прыгать назад и вперёд, для интервалов их использовать нельзя. Тип — `Int` мс сознательно: `Instant`, `Date`, `Duration` — горизонт; когда они появятся, `Time.now` не меняет тип молча, переход будет отдельным решением. Подмены часов для тестов (фейковые часы) нет — горизонт.

**`Global.put(name, value) -> ()` и `Global.get(name) -> Option<V>`.** Глобальная таблица «имя → значение», общая для всех акторов, для конфигурации и общих справочников.

- **Иммутабельность (§0.13).** Значение неизменяемо, как любое значение Brig; меняется только привязка имени. `put` по существующему имени заменяет привязку, `get` возвращает `Some(значение)` или `None`. Удаления нет.
- **Имя** — любое значение, пригодное как ключ `Map` (§4.8): `:config`, `(:limits, :http)`. Иначе `(:type_error, (:put, name))` / `(:type_error, (:get, name))`.
- **Порядок.** Все `put` и `get` по одному имени упорядочены: `get` после `put` того же актора видит это значение или более позднее; при гонке двух `put` побеждает поздний по порядку выполнения (last-write-wins). Какой из двух актор считается поздним, спека не гарантирует (§15.4).
- **Это не состояние актора.** `Global` не заменяет стейт в аргументах цикла и не даёт атомарного «прочитать-изменить-записать»: для него нужен актор-владелец. Значение, прочитанное `get`, не меняется от последующих `put`.

### 12.12 Порты и внешние события

Всё, что ждёт ОС (сигнал, сокет, файл, подпроцесс), — не вызов, который блокирует актор, а **порт**: актор просит порт и делает `recv`, а о готовности ресурса VM сообщает сообщением. Ни одна функция прелюдии и модулей VM не ждёт ОС (§15.2).

```brig
fn guard(port) ->
    recv
        (:signal, p, :sigterm) when p == port ->
            Port.close(port)
            :stopped

fn main() ->
    _pid = spawn(() -> guard(Signal.subscribe([:sigterm])))
    :started
```

`main` завершается сразу, но программа живёт, пока открыт порт `guard`: она ждёт `SIGTERM`, закрывает порт и завершается (условие — §15.2).

**Порт** — opaque-значение вида `Port`, как `Pid` и `Ref`: равенство по identity, место в term order после `Ref` (§7.4), не сериализуется (§14.8). Порт создаёт вызов, который его возвращает (`Signal.subscribe`, `File.open`, `HttpServer.listen`), или событие другого порта (порт запроса HTTP). **Владелец** ровно один: актор, создавший порт, а у порта из события — владелец порта-источника в момент доставки. Порт открыт или закрыт.

- **Закрытие.** Порт закрывается тремя способами: владелец вызвал `Port.close(port)`; владелец умер (по любой причине, в том числе от `exit`, §12.7, и `:kill`) — порт закрывается в тот же момент, что и снимаются имена реестра (§12.8); ресурс отказал (ошибка ОС) — владелец получает `:port_error`, после него порт закрыт; у порта, который только читает, так же закрывает `:port_eof`. Закрытый порт событий не порождает; сообщения, которые уже лежат в ящике владельца, остаются.
- **`Port.close(port) -> ()`** идемпотентен: закрытие закрытого порта — `()`. `port` не `Port` или вызывающий не его владелец (в том числе владелец мёртв) — `(:type_error, (:close, port))`. Потоковый порт при закрытии дописывает уже принятые `Port.write` данные вне run-loop; ошибка этой дозаписи не доставляется. Программа при завершении, в том числе по `Sys.halt`, дожидается дозаписи.
- **События** — обычные сообщения в конец ящика владельца. Форма — `(tag, port, ...)`: порт всегда второй элемент, поэтому актор с несколькими портами различает их без selective receive. Порядок — G5 (§15.2). События порта не подчиняются HWM: получателю некому вернуть `Error(:busy)`, порт не может отправителя подождать. Поэтому поток ограничен протоколом: потоковый порт присылает порцию только по запросу владельца, события `Signal` редки.
- **Порт принадлежит VM, реализация — за интерфейсом.** Что именно ждёт ОС, знает только реализация вида порта; ядро VM ОС-зависимостей не имеет (docs/02 §6), поэтому его можно исполнять без ОС (песочница, WASI).

**`Port.give(port, pid) -> Result<(), Atom>`** передаёт владение порта любого вида. `Ok(())` — владелец теперь `pid`, в том числе когда `pid` — сам вызывающий. Незакрытый запрос (`Port.request`) переходит вместе с портом: событие получает тот, кто владеет портом в момент доставки. События, которые уже лежат в ящике прежнего владельца, остаются там. Порт закрыт — `Error(:closed)`; `pid` мёртв — `Error(:not_alive)`. `port` не `Port`, вызывающий не владелец или `pid` не `Pid` — `(:type_error, (:give, arg))`.

**Потоковый порт** — порт, который отдаёт и принимает байты (`File`, `HttpServer`; позже `Proc`, `Stdin`, `Tcp`). Протокол общий, вид порта только открывает порт.

```brig
fn read_all(port, acc) ->
    _ = Port.request(port)
    recv
        (:port_data, p, chunk) when p == port -> read_all(port, Bytes.concat(acc, chunk))
        (:port_eof, p) when p == port -> Ok(acc)
        (:port_error, p, reason) when p == port -> Error(reason)

fn main() ->
    read_all(File.open("data.bin", :read), b"")
```

- **`(:port_data, port, bytes)`** — порция данных, `Bytes`, непустая.
- **`(:port_eof, port)`** — данные кончились. Порт, который только читает (файл `:read`), после события закрыт. Двусторонний порт (запрос HTTP, позже `Tcp`) остаётся открытым для записи, и каждый следующий `Port.request` снова даёт одно `:port_eof`.
- **`(:port_error, port, reason)`** — ресурс отказал, `reason` — атом, набор задаёт вид порта; после события порт закрыт.
- **`(:port_ready, port)`** — буфер записи освободился после `Error(:busy)`.

**`Port.request(port) -> Result<(), Atom>`** — pull: один запрос даёт ровно одно событие `:port_data`, `:port_eof` или `:port_error`. Повторный запрос, пока первый не выполнен, — `Ok(())` без второго события. Порт закрыт — `Error(:closed)`. `port` не `Port`, вызывающий не владелец или порт не читает (`Signal`, файл `:write`) — `(:type_error, (:request, port))`. Push-режима у потоковых портов нет: на каждый порт в ящике не больше одного ответа на запрос, и рост ящика ограничен числом портов (§0.8).

**`Port.write(port, data) -> Result<(), Atom>`.** `data` — iodata: `Bytes`, `Str` (UTF-8) или список iodata; иначе `(:type_error, (:write, data))`. Данные не склеиваются заранее: `["HTTP/1.1 ", status, "\r\n"]` пишется как есть.

- `Ok(())` — данные приняты в буфер порта; пишет их реализация вида вне run-loop, в порядке вызовов.
- `Error(:busy)` — в буфере уже не меньше порога (64 КиБ), данные не приняты. После `:busy` порт один раз присылает `(:port_ready, port)`, когда в буфере станет меньше порога. Это та же семантика, что `send` при HWM (§12.3), но с сигналом «можно снова».
- `Error(:closed)` — порт закрыт. Вызывающий не владелец или порт не пишет (`Signal`, файл `:read`) — `(:type_error, (:write, port))`.
- Ошибка записи приходит событием `(:port_error, port, reason)` без запроса; после него порт закрыт. Подтверждения записи нет.

**`File.open(path, mode) -> Port`.** Открывает файл потоковым портом. `path` — `Str`; `mode` — `:read`, `:write` (создать или обрезать) или `:append` (создать или дописывать в конец). Иначе `(:type_error, (:open, arg))`.

- **`open` не ждёт ОС:** файл открывается вне run-loop. Ошибка открытия приходит `(:port_error, port, reason)` в ответ на первый `Port.request` или после первого `Port.write`.
- **Чтение** — порциями не больше 64 КиБ; конец файла — `:port_eof`. Запись и чтение одним портом не смешиваются: режим выбирается при открытии.
- **`reason`** — `:enoent`, `:eacces`, `:eisdir`, `:enotdir`; прочие ошибки ОС — `:eio`; VM без файловой системы (песочница) — `:enotsup`.

**`HttpServer.listen(addr) -> Port`.** HTTP-сервер — вид потокового порта. Транспорт (соединения, keep-alive, разбор HTTP/1.1) работает вне run-loop на проверенной реализации платформы (в эталонной — Go `net/http`), семантика — Brig: запросы берутся по одному через `Port.request`, тело читается и пишется общим протоколом. Своя функция у вида одна — `HttpServer.respond`. Маршрутизация, `Conn` и плаги — модуль `Http` на Brig поверх этого порта.

```brig
fn handle() ->
    recv
        (:serve, req, head) ->
            Ok(()) = HttpServer.respond(req, 200, [("content-type", "application/json")])
            Ok(()) = Port.write(req, Json.encode({ status: "ok", path: head.path }))
            Port.close(req)

fn serve(listener) ->
    Ok(()) = Port.request(listener)
    recv
        (:http_request, l, req, head) when l == listener ->
            pid = spawn(handle)
            Ok(()) = Port.give(req, pid)
            send(pid, (:serve, req, head))
            serve(listener)
        (:port_error, l, reason) when l == listener -> Error(reason)

fn main() ->
    serve(HttpServer.listen("localhost:3000"))
```

- **`addr`** — `Str` вида `host:port`: `"localhost:3000"`, `"127.0.0.1:3000"`, `":3000"` (все интерфейсы), `"[::1]:3000"`; порт от 1 до 65535. Иначе `(:type_error, (:listen, addr))`. Опций нет: лимиты и таймауты — дефолты транспорта (ниже).
- **`listen` не ждёт ОС:** адрес занимается вне run-loop. Ошибка приходит `(:port_error, listener, reason)` в ответ на первый `Port.request`: `:eaddrinuse`, `:eacces`, `:eaddrnotavail` (адрес не локальный или имя не разрешилось); прочие ошибки ОС — `:eio`; VM без сети — `:enotsup`.
- **Приём — pull.** `Port.request(listener)` даёт ровно одно событие: `(:http_request, listener, req, head)` или `(:port_error, listener, reason)`, после которого порт закрыт. Пока запрос не взведён, транспорт держит принятые запросы у себя в пределах лимита. Listener только читает: `Port.write` на нём — `:type_error`.
- **Порт запроса `req`** — потоковый порт, который читает тело запроса и пишет тело ответа. Он появляется вместе с событием; владелец — тот, кто владеет listener в момент доставки. Обработчику его передаёт `Port.give(req, pid)`: сначала `give`, потом сообщение с `req`, — получив его, обработчик уже владелец. Тело запроса — `Port.request(req)`: `(:port_data, req, bytes)` порциями не больше 64 КиБ, затем `(:port_eof, req)`; порт после этого открыт для ответа.
- **`head`** — анонимная запись `{ method, path, query, headers, remote }`. `method` — атом `:get`, `:head`, `:post`, `:put`, `:patch`, `:delete` или `:options`; на другие методы транспорт отвечает `501` сам, до программы они не доходят. `path` — путь из строки запроса как есть, без percent-декодирования; `query` — всё после `?` без декодирования, `""`, если `?` нет. `headers` — `List<(Str, Str)>`: имена в нижнем регистре, пары упорядочены по имени, значения одного имени — в порядке запроса; `host` есть всегда, `transfer-encoding` убран (тело уже раскодировано). `remote` — `(Str, Int)`, адрес и порт клиента. Путь, query или заголовок не в UTF-8 — транспорт отвечает `400`.

**`HttpServer.respond(req, status, headers) -> Result<(), Atom>`** задаёт статус и заголовки ответа; тело пишет общий `Port.write(req, iodata)` (порог, `Error(:busy)`, `:port_ready`), конец ответа — `Port.close(req)`.

- `status` — `Int` от 200 до 599 (1xx шлёт только транспорт); `headers` — `List<(Str, Str)>`, имя — token (RFC 9110), значение без CR, LF и NUL. Иначе `(:type_error, (:respond, arg))`.
- `Ok(())` — статус и заголовки приняты; `Error(:closed)` — порт закрыт. Вызывающий не владелец, порт не запрос HTTP или `respond` уже был — `(:type_error, (:respond, req))`.
- `Port.write` до `respond` — `(:type_error, (:write, req))`: неявного `200` нет. У `204` и `304` тела нет, `Port.write` после них — тоже `:type_error`.
- `Port.close(req)` без `respond` — ответ `500` без тела.

**Отказы.**

- Клиент отключился — `(:port_error, req, :closed)` без запроса; после него порт закрыт.
- Ошибка тела запроса — `(:port_error, req, reason)`: `:too_large` (тело больше лимита), `:timeout` (порция не пришла вовремя), `:eio` (битое кодирование). Если ответ ещё не начат, транспорт отвечает сам: `413`, `408` или `400`. Ошибка записи ответа — `:closed`, `:timeout` или `:eio`.
- **Законченным ответ объявляет только `Port.close(req)`.** Порт запроса закрылся иначе — владелец умер, программа завершилась (в том числе по `Sys.halt`): ответ без `respond` — `500`, начатый ответ обрывается закрытием соединения. Клиент видит неполный ответ, а не «успешный» обрезанный.
- Запрос, который транспорт принял, но не доставил (listener закрыт раньше), получает `503`.

**Закрытие listener.** `Port.close(listener)`: новые запросы не принимаются, недоставленные получают `503`, доставленные обслуживаются до конца без предела по времени. Listener закрылся иначе (владелец умер, программа завершилась, `Sys.halt`) — доставленным запросам даётся не больше 5 с, затем соединения закрываются. Выход программы ждёт этого, как дозаписи файлов.

**Лимиты транспорта** (дефолты; опций у `listen` пока нет):

| Что | Предел | Сверх |
| --- | --- | --- |
| запросов одновременно (в очереди до программы и в обработке) | 1024 | `503` до программы |
| заголовки запроса | 64 КиБ, прийти за 10 с | `431` |
| тело запроса | 8 МиБ | `Content-Length` больше — `413` до программы; поток больше — `:too_large` и `413` |
| порция тела запроса | 60 с | `:timeout`, `408` |
| одна запись в соединение | 60 с | `:timeout` |
| keep-alive без запросов | 60 с | соединение закрывается |

Таймаута обработчика нет: сколько отвечать, решает программа (`recv … after`).

**Что транспорт делает сам.** `Date` добавляется (RFC 9110). `Content-Type` не угадывается: не задан в `respond` — его нет в ответе. Без `content-length` длину выбирает транспорт: тело, которое к `Port.close` уместилось в его буфер (2 КиБ), уходит с `Content-Length`, иначе — `Transfer-Encoding: chunked` (HTTP/1.1). Заданный `content-length` уходит как есть; запись сверх него — `:port_error` с `:eio`. На `HEAD` обработчик пишет тело как для `GET`, транспорт его отбрасывает. `Expect: 100-continue` — `100 Continue` уходит при первом `Port.request(req)`; неизвестный `Expect` — `417`. `Connection`, keep-alive и регистр имён заголовков на проводе — дело транспорта. Запись буферизуется: данные уходят клиенту по заполнении буфера или при `Port.close`; принудительного сброса нет.

**`Signal.subscribe(names) -> Port`.** Подписывает вызвавшего актора на сигналы ОС. `names` — непустой список атомов из `:sigterm`, `:sigint`; иначе `(:type_error, (:subscribe, names))`. Каждый пришедший сигнал из списка — сообщение `(:signal, port, name)` владельцу порта. `Signal` — не потоковый порт: события приходят без запроса, `Port.request` и `Port.write` на нём — `:type_error`.

- **Каждая подписка — свой порт, и каждый открытый порт получает своё событие.** Порядок между владельцами разных портов не определён. Порядок сигналов одного имени в одном порту — G5.
- **Подписка перехватывает сигнал.** Пока открыт хотя бы один порт на `name`, процесс на этот сигнал сам не завершается: решение — за программой (`Sys.halt` или естественный конец, §15.2). Без подписок сигнал действует по умолчанию, `SIGTERM` завершает процесс.
- **REPL.** `Ctrl-C` в REPL прерывает ввод (§11.4) и как `:sigint` не доставляется.

**`Sys.halt(code)`** немедленно завершает программу с exit-кодом `code`. `code` — `Int` от 0 до 255, иначе `(:type_error, (:halt, code))`. Останавливаются все акторы; `ensure` не выполняются, порты закрываются, накопленный вывод сбрасывается. Вызов не возвращается.

### 12.13 Интроспекция: `Actor.list`, `Actor.info`

Живую систему можно рассмотреть изнутри программы: какие акторы есть, чем заняты, кто за кем наблюдает. На этих функциях построены хелперы observer в консоли (§11.4); любая программа может собрать из них свой вид. Лента падений `observe` — не поле `Actor.info`, а события `[:vm, :actor, :crash]` и `[:vm, :actor, :down]` (§12.14): если подписка observe уже есть, хелпер печатает «observe уже открыт» и возвращает `()`.

```brig
fn idle() ->
    recv
        :stop -> :ok

fn main() ->
    (pid, _ref) = spawn_watched(() -> idle())
    register(:idle, pid)
    assert(Enum.any?(Actor.list(), (p) -> p == pid))
    match Actor.info(pid)
        Some(i) -> (i.name, i.watchers == [self()])
        None    -> :dead
```

**`Actor.list() -> List<Pid>`** — все живые акторы в момент вызова, включая вызывающего и служебный актор телеметрии (§12.14). Порядок не определён. Актор, для которого наблюдателям уже поставлен `:down`, в список не входит; актор, созданный `spawn`, входит сразу после возврата `spawn`. Список — снимок: к моменту чтения акторы из него могут умереть.

**`Actor.info(pid) -> Option<Record>`** — к полям §12.10 (`reductions`, `alloc_bytes`, `mailbox`, `dropped`, `turn_reductions`, `turn_alloc_bytes`) добавлены:

| Поле | Значение |
| --- | --- |
| `name` | `Option`: `Some(name)` — имя из реестра (§12.8); у актора с несколькими именами — первое из ещё связанных по порядку `register`; `None` — имени нет |
| `status` | `:running` — исполняется или ждёт кванта в очереди готовых; `:recv` — ждёт сообщения в `recv` (с `after` или без); `:waiting` — ждёт ответа в `await` (§12.9) |
| `watchers` | `List<Pid>` — акторы, которые наблюдают за этим (`watch`, `spawn_watched`), каждый один раз, в порядке первого взведённого наблюдения; снятое `unwatch` наблюдение не учитывается. Связь `link`/`spawn_linked` (§12.2) — не наблюдение и здесь не видна |
| `watching` | `List<Pid>` — акторы, за которыми наблюдает этот, по тем же правилам |
| `initial_fn` | `Str` — имя функции, с которой актор начал исполнение, в том же виде, что в stack trace (T-79); для лямбды — имя, которое ей даёт trace |

Мёртвый или несуществующий `pid` → `None`; `pid` не `Pid` → `(:type_error, (:Actor.info, pid))`. Для чужого актора значения racy (§15.2): каждое поле верно на момент чтения, но поля одной записи могут относиться к соседним моментам. Состояние актора (аргументы его цикла) `Actor.info` не отдаёт: оценка размера стейта — горизонт (§12.10).

### 12.14 `Telemetry`: события инструментирования

Один механизм для метрик, логов медленных запросов, observer и отчётов о падениях: кто-то излучает событие, подписчики на его путь его получают. Библиотеки не заводят своих хуков.

```brig
fn main() ->
    me = self()
    Ok(()) = Telemetry.attach(:slow_log, [:app, :request], (event, m, meta) -> send(me, (:event, event, m.duration_ms, meta.route)))
    Telemetry.emit([:app, :request, :stop], { duration_ms: 12 }, { route: "/users" })
    Telemetry.detach(:slow_log)
    recv
        (:event, e, ms, route) -> (e, ms, route)
```

**Событие** — путь, измерения и метаданные:

- **путь** `event` — непустой `List` атомов: `[:app, :request, :stop]`;
- **измерения** `measurements` — запись с числами, которые агрегируют (длительность, размер);
- **метаданные** `meta` — запись с тем, по чему группируют и что показывают (маршрут, статус, pid).

**`Telemetry.attach(id, prefix, handler) -> Result<(), Atom>`.** Подписывает `handler` на все события, путь которых начинается с `prefix`.

- `id` — любое значение, пригодное как ключ `Map` (§4.8); занятый `id` → `Error(:already_exists)`, прежняя подписка не меняется.
- `prefix` — `List` атомов; `[:app]` совпадает с `[:app, :request, :stop]`, путь совпадает сам с собой; пустой `[]` — все события.
- `handler` — функция арности 3, `handler(event, measurements, meta)`; результат игнорируется.
- `prefix` не список атомов или `handler` не функция арности 3 → `(:type_error, (:attach, arg))`.

**`Telemetry.detach(id) -> ()`** снимает подписку; неизвестный `id` — `()`, идемпотентно.

**`Telemetry.emit(event, measurements, meta) -> ()`.** `event` не непустой список атомов, `measurements` или `meta` не запись → `(:type_error, (:emit, arg))`.

- **Доставка синхронна, в излучающем акторе.** `emit` вызывает каждый совпавший обработчик по очереди, в порядке `attach`, и возвращается после последнего. Обработчик исполняется как обычная функция излучающего актора: `self()` — его pid, редукции и аллокации идут в его счётчики и бюджет хода (§12.10). Обработчик должен быть дешёвым (обновить счётчик, `send` агрегатору); тяжёлая работа — в своём акторе. `recv` в обработчике допустим, но блокирует излучающего.
- **Подписки видны сразу всем акторам.** Реестр подписок — таблица VM, общая для всех акторов, как `Global` (§12.11); через `Global.get` не виден. `attach` и `detach` видны следующему `emit` любого актора. Набор обработчиков фиксируется в начале `emit`: `detach` из обработчика не отменяет уже начатую доставку.
- **Ошибка обработчика не роняет излучающего.** Непойманный `raise` (в том числе авто-raise) внутри обработчика снимает его подписку, как `detach(id)`, и излучает `[:telemetry, :handler, :failed]` с измерениями `{}` и метаданными `{ id, event, reason }`, где `reason` — значение ошибки. Затем доставка продолжается со следующего обработчика, а `emit` возвращается `()`. `exit` излучающему (§12.7) обработчик не ловит: он завершает актора, как в любом другом месте.
- **Вложенный `emit`** из обработчика допустим и доставляется так же синхронно, до возврата из внешнего обработчика.
- **Цена без подписчиков.** Пока подписок нет, `emit` — одна проверка без аллокаций и без вызова обработчиков; это касается и событий VM: без подписок VM не собирает для них измерения и метаданные.

**События VM.** VM излучает события в ту же шину. У всех в измерениях есть `monotonic_ms` — `Time.monotonic_ms()` в момент события (§12.11).

| Путь | Когда | Измерения | Метаданные |
| --- | --- | --- | --- |
| `[:vm, :spawn]` | актор создан `spawn`, `spawn_linked`, `spawn_watched` | `{ monotonic_ms }` | `{ pid, parent, initial_fn }`: новый актор, создатель, `initial_fn` как в `Actor.info` |
| `[:vm, :actor, :crash]` | актор упал от непойманного `raise` или авто-raise | `{ monotonic_ms, reductions, alloc_bytes }` | `{ pid, name, reason, trace }` |
| `[:vm, :actor, :down]` | любая смерть: нормальный возврат, падение, `exit` (§12.7), в том числе `:kill` и `:resource_limit` | `{ monotonic_ms, reductions, alloc_bytes, lifetime_ms }` | `{ pid, name, reason }` |
| `[:vm, :mailbox, :hwm]` | сообщение не принято из-за HWM (§12.2): `send` вернул `Error(:busy)` или сработавший `Timer.send_after` потерял сообщение (§12.11) | `{ monotonic_ms, mailbox, hwm }` | `{ pid, from }`: получатель; `from` — `Some(pid)` отправителя, `None` для таймера |

- **Кто излучает.** `[:vm, :spawn]` — создатель, сразу после создания актора (и взвода наблюдения у `spawn_watched`), до возврата из `spawn`. `[:vm, :mailbox, :hwm]` от `send` — отправитель, до возврата `Error(:busy)`. События смерти и потеря сообщения таймера — **служебный актор телеметрии**: умерший актор уже не исполняется (а `:kill` не должен исполнять в нём ничего), поэтому его обработчики нельзя запускать в нём самом. Служебный актор — обычный актор VM: виден в `Actor.list`, имени в реестре у него нет; события получает в порядке, в котором их поставила VM. Он создаётся при первом таком событии, для которого есть совпавшая подписка; без подписок его нет. Смерть самого служебного актора событий не излучает.
- **`:crash` и `:down`.** `[:vm, :actor, :down]` — на каждую смерть. `[:vm, :actor, :crash]` — дополнительно, только при падении от `raise`; `exit(pid, r)`, `:kill` и `:resource_limit` — не падение. Для одной смерти `:crash` излучается раньше `:down`. Оба излучаются после того, как наблюдателям поставлен `:down` и сняты имена (§12.8), поэтому `name` — имя, которое было у актора в момент смерти (как в `Actor.info`).
- **`reason`** — та же причина, что в `(:down, ref, reason)` (§12.2, §12.7). `lifetime_ms` — от создания до смерти по `Time.monotonic_ms`. `reductions` и `alloc_bytes` — итог жизни, как в `Actor.info`.
- **`trace`** — stack trace падения (T-79): `List` записей `{ fn: Str, file: Str, line: Int, col: Int }` от места `raise` к первой функции актора; кадры, заменённые хвостовым вызовом, в него не попадают. Это отладочный канал: в значение ошибки, `trap` и `:down` trace не попадает.
- **HWM.** Каждое `[:vm, :mailbox, :hwm]` — один инкремент счётчика `dropped` получателя (§12.10): событие даёт поток отказов, `dropped` — их итог, и он виден без подписки.
- **Бюджет хода.** Превышение (§12.10) видно как `[:vm, :actor, :down]` с `reason` `(:resource_limit, …)`; отдельное событие `[:vm, :resource_limit]` — горизонт (T-169).

`Telemetry.span`, экспорт (Prometheus, OpenTelemetry), подключение observer к чужому процессу (`brig observe` по сокету) — горизонт.

## 13. Supervisors and Behaviors

### 13.1 Супервизоры

```brig stmt
# хелперы примера
fn counter_loop(n) -> n
fn worker_loop(n) -> n

sup = Supervisor.start({
    strategy: :one_for_one,
    max_restarts: 3,
    within: 5000,
    children: [
        { name: :counter, start: () -> spawn_linked(() -> counter_loop(0)), restart: :permanent },
        { name: :worker,  start: () -> spawn_linked(() -> worker_loop(0)),  restart: :transient },
    ],
})
```

Под капотом — обычный актор, `watch`-ит детей. `max_restarts`/`within` — окно перезапусков, при превышении эскалирует.

`start` ребёнка возвращает его `Pid` и обычно зовёт `spawn_linked`, то есть делает супервизор владельцем ребёнка (§12.2). Поэтому смерть супервизора — в том числе `exit(sup, :kill)` и падение по `max_restarts` — завершает и детей: сирот не остаётся. Наблюдение и перезапуск держит `watch` супервизора, связь `link` отвечает только за уборку.

**Функции в сообщениях — только для shared-heap модели.** Для распределённых акторов — дескриптор `{ module: M, function: F, args: A }`.

**Дескриптор MFA — запись, не кортеж.** `{ module: module, function: function, args: args }`. Кортеж `(module, function, args)` не используется.

### 13.2 Протоколы / Behaviors

**Единственный способ задать Behavior — литерал `Behavior{ handlers: %{...} }`.**

`Behavior` объявлен в stdlib:

```brig module
type Behavior { handlers: Map<Atom, Function> }
```

Параметризация `Map<Atom, Function>` — через `<...>`.

Пример:

```brig module
import Map

fn main() ->
    init_state = %{}
    kv_behavior = Behavior{
        handlers: %{
            :get => fn (state, key) ->
                match Map.get(state, key)
                    Some(v) -> (Ok(v), state)
                    None    -> (Error(:not_found), state)
            :put => fn (state, key, val) ->
                (Ok(()), Map.put(state, key, val))
        }
    }
    pid = spawn_behavior(kv_behavior, init_state)
    pid
```

Ключи — атомы. Диспетч по тегу верхнего уровня. Валидация колбэков — вне MVP (**Should**).

**Контракт колбэка — `(reply, new_state)`.** Колбэк вызывается как `f(state, args...)`, где `args` — элементы сообщения после тега, и возвращает пару: `reply` — ответ вызывающему, `new_state` — состояние следующего шага цикла. Вернул не пару — `(:badmatch, v)`.

**Две формы сообщения.** `(:call, from, msg)` — запрос `Server.call` (§12.9): диспетч идёт по `msg`, ответ уходит `Server.reply(from, reply)`. Голое `msg` — cast: состояние меняется, `reply` отбрасывается. Само `msg` — тег-атом (`:size`) или кортеж `(tag, args...)`.

**Аргументов у тега — не больше трёх.** У кортежей нет спреда (§4.1), поэтому диспетч разбирает формы от `tag` до `(tag, a, b, c)`; кортеж длиннее — `(:bad_arity, tag)`.

**Тега нет в `handlers` — `(:no_handler, tag)`.** Ошибка падает в акторе по обычным правилам (§12.7): её видят `watch` и супервизор.

`spawn_behavior(Behavior, InitState)` — акторный примитив. Определяется здесь; в прелюдию не входит. Возвращает `Pid`; актор не связан с вызывающим — линк и наблюдение делаются обычными `spawn_linked`/`watch` и `Supervisor` (§13.1). Первый аргумент не `Behavior` или его `handlers` не `Map` — `(:type_error, (:spawn_behavior, v))` у вызывающего.

## 14. Type System

### 14.1 Три формы `type`

1. **Вариант-декларация:** `type Result<T, E> { Ok(T), Error(E) }`.
2. **Запись-декларация:** `type User { id: Int, name: Str }`.
3. **Алиас:** `type UserId = Int`.

Различие по первому токену: `{` → вариант/запись (различаются по содержимому: `Name(...)` vs `name:`), `=` → алиас.

### 14.2 Синтаксис конструкторов вариантов

- Конструктор **без аргументов** — **значение**: `None`, `Red`, `Green`.
- Конструктор **с аргументами** — **функция**: `Some`, `Ok`, `Error`.
- Пользовательские конструкторы работают так же: `type Color { Red, Green, Blue }` даёт три значения; `type Wrapper { Wrap(Int) }` даёт функцию `Wrap`.
- Конструктор можно передавать как функцию: `Enum.map(xs, Some)`.

### 14.3 Параметризация generic-типов

**Только через `<...>`.** Квадратные скобки `[...]` в позиции типа не используются.

### 14.4 Семантика аннотаций типов

Аннотации `u: User`, `-> Int` — **documentation-only** в MVP: не проверяются ни статически, ни в рантайме. Runtime-контракты — **Should**.

**Трение с принципом #3.** Аннотации выглядят как контракт, но игнорируются — осознанный компромисс MVP: полу-проверка хуже отсутствия.

### 14.5 Группировка типа

`(Int)` — группировка типа. 1-кортеж типа — `(Int,)`.

### 14.6 Функциональные типы

```brig module
type Callback = (Int, Str) -> Bool
```

### 14.7 Политика shadowing встроенных имён

Имена встроенных вариантов (`Option`, `Result`, `Some`, `None`, `Ok`, `Error`) и типов являются предопределёнными. Shadowing на уровне пользователя разрешён по общей политике — компилятор выдаёт info-диагностику при затенении встроенных имён. Доступ к встроенным при затенении не предусмотрен (встроенные не имеют модуля); при необходимости — переопределять в собственном модуле.

### 14.8 Предопределённые имена типов

Следующие имена типов доступны без `import` и могут использоваться в позиции `type_expr`:

- **Примитивы:** `Int`, `Float`, `Decimal`, `Bool`, `Str`, `Bytes`, `Atom`, `Function`.
- **Коллекции:** `List<T>`, `Vector<T>`, `Map<K, V>`, `Set<T>`, `Tuple<...>`, `Queue<T>`.
- **Варианты:** `Option<T>`, `Result<T, E>`.
- **Специальные:** `()`, `Range`, `Pid`, `Ref`, `Port`.

`Atom` — тип атомов. `Function` — тип функций; сериализация не поддерживается. `Pid`/`Ref`/`Port` — opaque-значения, сериализация не поддерживается.

```brig module
type UserId = Int
```

```brig module
type Color { Red, Green, Blue }
```

## 15. Runtime Architecture

### 15.1 Общие положения

- **Язык реализации — Go.**
- **Регистровая байткод-VM** (BEAM/Lua-style). Обязателен **дизассемблер** (`--dump-bytecode`) и `line:col` на инструкцию — Must.
- **Память:** общий heap + ссылки на иммутабельные значения, не per-actor heap. GC общего heap (реализация — Go GC). Действует, пока язык иммутабелен: мутация, FFI, наблюдающий алиасинг или распределённость — триггер пересмотра.
- **Представление коллекций (DD #397).** Коллекции — персистентные структуры с разделением неизменённых частей, не копирование на каждую «изменяющую» операцию (§0.13): `List` — cons-список с длиной в ячейке, `Map`/`Set` — HAMT, `Vector` — 32-арный trie. Гарантированная сложность операций — таблицы в §4.2, §4.4–§4.6, только O-оценки. Представление ячейки `Value` (T-104) решается отдельно и таблиц не меняет.
- **Функции в сообщениях** валидны только в shared-heap модели; для распределённости — `{ module: M, function: F, args: A }`.

### 15.2 Модель планирования

Спецификация фиксирует **наблюдаемые гарантии** планирования. Модель потоков (сколько ОС-потоков, goroutine или явный run-loop) — **деталь реализации** и не является нормативной.

**Гарантии:**

- **G1. FIFO в паре.** Сообщения от одного отправителя одному получателю доставляются в порядке отправки.
- **G2. `:down` впереди.** `:down` попадает в начало очереди получателя, перед пользовательскими сообщениями, и не учитывается в HWM (§12). Пользовательские сообщения подчиняются HWM. Ответ `reply` (§12.9) идёт в слот ref, а не в очередь: HWM он не учитывается и G1 с сообщениями ящика не связан.
- **G3. Fairness.** Готовый актор вытесняется не позднее чем через N редукций (N фиксирован конфигурацией VM; редукция определена в docs/02, K-4). Колбэки прелюдии учитываются в счётчике (T-58, #144). `:down` от долго считающего актора обрабатывается не позднее чем через N редукций **при условии, что актор выполняет `recv`**; без `recv` сообщение остаётся в ящике.
- **G4. Таймеры.** Истёкшие таймеры `recv ... after`, таймауты `await` (§12.9) и `Timer.send_after` (§12.11) срабатывают в порядке (deadline, порядок взвода) — это одна очередь таймеров.
- **G5. События порта.** События одного порта (§12.12) доставляются его владельцу в порядке их возникновения на ресурсе. Относительно сообщений других акторов, событий других портов и таймеров порядок не гарантирован.

**Не гарантируется:**

- чередование сообщений от **разных** отправителей одному получателю, в том числе событий портов среди них;
- значение `mailbox_size(pid)` чужого актора (racy: может устареть до использования);
- тайминги (wall-clock), в том числе точное время пробуждения по таймеру;
- параллелизм: реализация вправе исполнять акторы в одном потоке или в нескольких.

**Завершение программы.** Программа завершается, когда выполнено одно из:

- `main` завершился нормально и нет открытых портов (§12.12) — остальные акторы останавливаются без `ensure`;
- `main` завершился непойманным `raise` — сразу, порты закрываются, exit-код 2;
- вызван `Sys.halt(code)` (§12.12) — сразу, с кодом `code`.

Если `main` завершился нормально, но порт открыт, остальные акторы продолжают работать, события портов и таймеры обрабатываются. Открытый порт всегда принадлежит живому актору: порт умершего владельца закрыт. Если все акторы ждут, событие может прийти только от таймера или от порта, который его обещал: `Signal`, потоковый порт с активным `Port.request`, с недописанными данными или с обещанным `:port_ready` (§12.12). Такое ожидание — не ошибка, а штатное состояние. Если ждать неоткуда — нет ни таймеров, ни таких портов, — то при незавершённом `main` это прежняя ошибка `deadlock` (exit-код 2), а при завершённом `main` программа завершается, как без портов: открытый потоковый порт без запроса программу не держит.

**Native-вызовы не блокируют run-loop.** Ни одна функция прелюдии и модулей VM не ждёт ОС: всё, что ждёт, — порт (§12.12) и сообщение, ответ — `recv` или `await` (§12.9). Тяжёлые по CPU native-операции остаются открытым вопросом (§17.8).

**Эталонная реализация** — один кооперативный run-loop в одной goroutine: готовые акторы исполняются по очереди, вытеснение — по счётчику редукций. Когда готовых акторов нет, run-loop ждёт ближайший таймер или событие порта, а не выходит. События портов приходят в него из потокобезопасной очереди: сами ресурсы ждут в других goroutine. Такая реализация воспроизводима (кроме wall-clock и внешних событий). Эволюция в сторону N:M (собственный планировщик поверх пула потоков, в том числе с режимом `schedulers=1`) допустима без изменения этой спецификации, пока сохраняются G1–G5; goroutine-per-actor не является целевой моделью. Тяжёлые native-вызовы и эволюция к N:M — открытый вопрос (§17.8).

Редукционный счётчик нужен VM для детерминированных точек контроля (сигнал прерывания, `trace(pid)`, диагностическое сэмплирование), для отзывчивости супервизора (G3) и как единица учёта при переходе к N:M.

### 15.3 TCO

**TCO гарантирован** для само- и общих хвостовых вызовов, в том числе внутри `trap` с `ensure`: кадр заменяется, невыполненные `ensure` хранятся компактной записью в куче (O(1) кадров, O(n) памяти на n уровней `ensure`). Схема — `docs/02-register-based-virtual-machine.md` §5.1.

### 15.4 Граница наблюдаемой семантики

Наблюдаемая семантика (результаты, порядок сравнений, авто-raise, доставка `:down`) и гарантии планирования G1–G5 (§15.2) — детерминирована и гарантирована. «Детерминирована» относится к перечисленным гарантиям, а не к глобальному чередованию событий между акторами. Источники недетерминизма — `Time.now`, `Time.monotonic_ms` (§12.11), порядок конкурирующих `Global.put`, внешние события портов (§12.12: сигналы ОС, файлы и HTTP-запросы, а позже — сокеты и подпроцессы: когда и в каком порядке они придут, программа не определяет) и чередование акторов вне G1–G5. Производительность, лимиты памяти, точность Decimal, модель потоков планировщика, тайминги внутри редукционных интервалов — могут варьироваться между реализациями без нарушения гарантий.

- `Actor.list`, поля observer в `Actor.info`, `Telemetry` с событиями VM, хелперы observer в консоли (§12.13, §12.14, §11.4; волна 15)

**Nice**

- `Set`-литерал
- `Queue`
- `Rational`

**Не надо**

- `=<`
- дефолтные аргументы
- kwargs (опции — анонимная запись последним аргументом, §5.2)
- `none`/`reduce`
- `send` в pipe (и другие акторные примитивы)
- исключения через границы акторов (`(:linked_exit, reason)` от `link` им не является: передаётся `exit`, а не значение `raise`, §12.2)

От async/await он отличается тем же, чем `recv`: это блокирующая точка ожидания актора, а не раскраска функций и не промисы.

# Part II: Formal Specification

## A. Grammar (`brig.ebnf`)

    см. brig.ebnf

### A.1 Комментарии к грамматике

1. `NEWLINE` внутри скобок может выступать как `sep`, если лексер эмитирует его как разделитель элементов.
2. В паттернах разделители — только запятые. Это осознанное ограничение MVP.
3. `(x)` — группировка, `(x,)` — 1-кортеж.
4. `{ ... }` в позиции выражения — `record_literal`; в позиции `type_body` — `variant_list` или `field_list`.
5. `record_literal` и `record_pattern` поддерживают анонимную форму без имени типа.
6. `lambda_empty` — самостоятельная форма пустой лямбды. `lambda_short` принимает один параметр без скобок или список имён в скобках; `(a, b) -> …` отличается от кортежа по `->` после `)`. В `lambda_full` скобки параметров необязательны только при нуле параметров: `fn ->` (канон), `fn () ->` эквивалентен и форматируется в `fn ->`.
7. `unit_lit` — значение `()`.
8. `regex_lit` и `decimal_lit` присутствуют в грамматике как feature-flagged формы.
9. `type_primary` из `UPPER_IDENT` может быть либо именем типа, либо типовой переменной. Разрешение выполняется контекстно по `generic_params`.
10. Внутри строковой интерполяции `\(...)` в MVP запрещены блочные конструкции, требующие `NEWLINE`/`INDENT`/`DEDENT`.
11. **v0.4.7:** `ensure` — `trap_item`, а не клауза после `DEDENT`. Якорь `trap` — `stmt_indent`, как у прочих блочных конструкций (§2.4, T-124).
12. `pub` стоит только перед клозом `fn` верхнего уровня (`fn_decl`); `local_fn_decl` его не принимает. `quote` — зарезервированное слово без продукций (§1.3).
13. `ModuleName` в `record_literal`, `record_pattern`, `constructor_pattern` и `type_primary`: последний сегмент — имя типа или конструктора, предыдущие — локальное имя модуля (§11.1). Одиночный `UPPER_IDENT` — имя своего модуля, встроенное или по правилу «тип = последний сегмент модуля» (§11.1).
14. `repl_input` — порция ввода REPL: одна или несколько `repl_line`, каждая — своя область (§11.4). `script` — файл режима `script` из тех же инструкций (§11.3). Где кончается порция ввода (скобки, ожидаемый `INDENT`, пустая строка), решает REPL до разбора (§11.4, «Ввод»), а не грамматика.

## B. Lexer Specification

### B.1 Полный список токенов

#### Ключевые слова

```text
fn match cond recv with else if then after when alias import module type ensure
trap and or not div rem to true false as pub quote
```

Ключевые слова не могут быть `LOWER_IDENT`, кроме случаев, когда они являются частью `ATOM`. `quote` — зарезервированное слово без продукций (§1.3).

#### Идентификаторы

```text
LOWER_IDENT ::=
    [a-z] [a-zA-Z0-9_]* ["?"]
  | "_" [a-z] [a-zA-Z0-9_]* ["?"]

UPPER_IDENT ::= [A-Z] [a-zA-Z0-9_]*

WILDCARD ::= "_"
```

**Допустимые примеры:** `x`, `foo`, `ready?`, `done?`, `true?`, `_msg`, `_unused`.

**Недопустимые:** `_1`, `_Foo`, `x?y`.

Одиночный `_` — это `WILDCARD`.

#### Атомы

```text
ATOM ::= ":" atom_body
```

`atom_body`:

- начинается с `[a-z]`;
- может совпадать с ключевым словом;
- может заканчиваться `?`;
- не может начинаться с `_`;
- не может быть `UPPER_IDENT`.

**Допустимые:** `:ok`, `:none`, `:not_found`, `:if`, `:and`, `:true`, `:false`, `:ready?`, `:done?`.

**Недопустимые:** `:_`, `:_foo`, `:Foo`.

#### Числа

- `INT` — целые литералы: десятичные, `0x`, `0b`, `0o`.
- `FLOAT` — литералы с точкой или экспонентой.
- `DECIMAL` — `dec"..."`.

#### Строки и байты

- `STRING` — `"..."` с интерполяцией `\(...)`.
- `BYTES` — `b"..."`, без интерполяции.
- `REGEX` — `rx"..."`, без интерполяции.

#### Операторы

Длинные операторы распознаются раньше коротких:

```text
|>  **  ==  !=  <=  >=  ..  ->  <-  =>  <>
+   -   *   /   <   >   =   .
```

#### Разделители

```text
(  )  [  ]  {  }  %[  %{  ,  :
```

Одиночный `%` без последующего `[` или `{` является ошибкой лексера.

Символ `;` в языке отсутствует.

#### Служебные токены

```text
NEWLINE
INDENT
DEDENT
EOF
```

#### Комментарии

`#` начинает комментарий до конца строки. Комментарии не эмитируются как токены, не влияют на offside и не учитываются при подсчёте отступа.

---

### B.2 Порядок распознавания

На каждом шаге лексер:

1. Пропускает горизонтальные пробелы вне начала строки.
2. Если встречается `#`, пропускает комментарий до конца строки.
3. Если встречается `"`, читает `STRING`.
4. Если встречается `b"`, читает `BYTES`.
5. Если встречается `rx"`, читает `REGEX`.
6. Если встречается `dec"`, читает `DECIMAL`.
7. Если встречается `:`:
    - если предыдущий токен — `LOWER_IDENT`, `UPPER_IDENT`, `)`, `]` или `}`, эмитируется `COLON`;
    - иначе, если следующий символ — `[a-z]`, читается `ATOM`;
    - иначе эмитируется `COLON`.
8. Если встречается `0x`, `0b`, `0o`, читает `INT` соответствующей базы.
9. Если встречается цифра, читает `INT` или `FLOAT`.
10. Если встречается `[A-Z]`, читает `UPPER_IDENT`.
11. Если встречается `[a-z]`, читает идентификатор, затем проверяет его на ключевое слово.
12. Если встречается `_`:
    - одиночный `_` — `WILDCARD`;
    - `_` + `[a-z]` — `LOWER_IDENT`;
    - иначе ошибка лексера.
13. Если встречается оператор или разделитель, выбирается самая длинная подходящая лексема.
14. Иначе ошибка лексера.

### B.3 Правила для ключевых слов и идентификаторов

После чтения идентификатороподобной лексемы:

1. Если лексема не содержит финальный `?` и совпадает с ключевым словом, эмитируется соответствующий keyword.
2. Если лексема содержит финальный `?`, она всегда эмитируется как `LOWER_IDENT`.
3. `_` эмитируется как `WILDCARD`.
4. `_msg`, `_unused` и подобные эмитируются как `LOWER_IDENT`; то, что они не связываются (именованный wildcard, §1.2), проверяет контекстный анализ, а не лексер.
5. `_1`, `_Foo` — ошибка лексера.

**Примеры:**

```text
and      -> KEYWORD(and)
pub      -> KEYWORD(pub)
quote    -> KEYWORD(quote)
done?     -> LOWER_IDENT(done?)
true     -> KEYWORD(true)
true?    -> LOWER_IDENT(true?)
_msg     -> LOWER_IDENT(_msg)
_        -> WILDCARD
```

### B.4 Особые случаи

#### `..`

- `..` — один токен, не два `.`.
- `..args` — два токена: `..`, `LOWER_IDENT(args)`.

#### `%`

- `%[` — один токен.
- `%{` — один токен.
- Одиночный `%` — ошибка лексера.

```text
%[1, 2]     -> %[ ...
%{a: 1}     -> %{ ...
x % y       -> lexer error
```

#### `:`

```text
:ok        -> ATOM
:if        -> ATOM
:true      -> ATOM
a:b        -> LOWER_IDENT(a), COLON, LOWER_IDENT(b)
{a:b}      -> record field
::         -> COLON COLON
:_foo      -> COLON, затем обработка _foo
:Foo       -> COLON, UPPER_IDENT(Foo)
```

#### `?`

- `?` может быть только финальным символом `LOWER_IDENT`.
- `x?` — валидный `LOWER_IDENT`.
- `x ? y` — ошибка, так как `?` не является оператором.
- `x?y` — ошибка лексера.

#### Числа

- `1e9` — `FLOAT`.
- `1e` — ошибка лексера.
- `1.` — ошибка лексера.
- `.5` — ошибка лексера.
- `0x` без цифр — ошибка лексера.
- `_` разрешён только между цифрами.
- `1__0` — ошибка лексера.
- `1_` — ошибка лексера.
- `_1` — ошибка лексера.

#### `-1`

`-1` не является единым числовым литералом. Токены: `-` + `INT(1)`.

## C. Escape Sequences and UTF-8

### C.1 `Str` (`"..."`)

| Escape            | Значение            | Кодпоинт     |
| ----------------- | ------------------- | ------------ |
| `\n`              | новая строка        | U+000A       |
| `\t`              | табуляция           | U+0009       |
| `\r`              | возврат каретки     | U+000D       |
| `\0`              | NUL                 | U+0000       |
| `\\`              | обратный слэш       | U+005C       |
| `\"`              | двойная кавычка     | U+0022       |
| `\(`              | начало интерполяции | —            |
| `\u{H...H}`       | Unicode codepoint   | 1–6 hex-цифр |
| любой другой `\X` | ошибка лексера      | —            |

**Правила:**

- `\u{...}` содержит 1–6 шестнадцатеричных цифр.
- Значение должно быть `<= U+10FFFF`.
- Диапазон суррогатов `U+D800..U+DFFF` запрещён.
- `\u{}` — ошибка лексера.
- `\u{110000}` — ошибка лексера.
- `\u{D800}` — ошибка лексера.
- `\xHH` в `Str` запрещён.
- Строка обязана быть валидной UTF-8.
- Некорректный UTF-8 в строке — ошибка лексера.

### C.2 Интерполяция `\(...)`

Интерполяция разрешена только в `Str`.

**Границы интерполяции:**

- начинаются с `\(`;
- заканчиваются на соответствующей `)`;
- при поиске границ учитываются вложенные `()`, `[]`, `{}`;
- учитываются вложенные строковые литералы;
- учитываются вложенные интерполяции.

**Физические переносы строк внутри интерполяции запрещены** — ошибка лексера `unclosed interpolation`; выражение пишется в одной строке:

```brig
x = "sum: \(1 + 2)"
```

**Ограничение MVP:** внутри `\(...)` запрещены блочные конструкции:

- блочный `if`;
- блочный `match`;
- блочный `recv`;
- блочный `with`;
- блочный `trap`;
- блочные лямбды `fn (...) ->` с телом в виде offside-блока.

**Однострочный `if` внутри интерполяции разрешён:**

```text
x = "value: \(if ready then 1 else 0)"
```

Незакрытая интерполяция — ошибка лексера с указанием позиции открывающего `\`.

### C.3 `Bytes` (`b"..."`)

| Escape            | Значение          | Байт                |
| ----------------- | ----------------- | ------------------- |
| `\n`              | новая строка      | 0x0A                |
| `\t`              | табуляция         | 0x09                |
| `\r`              | возврат каретки   | 0x0D                |
| `\0`              | NUL               | 0x00                |
| `\\`              | обратный слэш     | 0x5C                |
| `\"`              | двойная кавычка   | 0x22                |
| `\xHH`            | произвольный байт | 1 байт, 2 hex-цифры |
| любой другой `\X` | ошибка лексера    | —                   |

**Правила:**

- интерполяция `\(` в `Bytes` запрещена;
- `\u{...}` в `Bytes` запрещён;
- любые байты могут быть представлены через `\xHH`;
- `Bytes.to_str(b)` при невалидном UTF-8 вызывает `raise((:invalid_utf8, b))`.

### C.4 `Regex` (`rx"..."`)

| Escape            | Значение             |
| ----------------- | -------------------- |
| `\"`              | литерал `"`          |
| `\\`              | литерал `\`          |
| любой другой `\X` | сохраняется как `\X` |

**Правила:**

- интерполяция отсутствует;
- тело литерала передаётся в regex-движок как есть;
- лексер не валидирует синтаксис регулярного выражения.

### C.5 `Decimal` (`dec"..."`)

**Допустимые символы внутри `dec"..."`:** `0-9`, `_`, `.`, `+`, `-`.

**Формат:** `[+-]? dec_digits [ "." dec_digits ]`, где `dec_digits` — цифры с одиночными подчёркиваниями только между цифрами.

**Валидные примеры:** `dec"1"`, `dec"+1"`, `dec"-1.5"`, `dec"1_000.5"`, `dec"1.50"`.

**Невалидные:** `dec"1e9"`, `dec".5"`, `dec"1."`, `dec"1__0"`, `dec"1_"`, `dec""`.

### C.6 Некорректный UTF-8

| Ситуация                                       | Поведжение                             |
| ---------------------------------------------- | -------------------------------------- |
| Некорректный UTF-8 в исходном файле            | ошибка лексера                         |
| Некорректный UTF-8 внутри `Str`                | ошибка лексера                         |
| Некорректный UTF-8 внутри `Bytes` через `\xHH` | допустим                               |
| `Bytes.to_str(b)` при невалидном UTF-8         | runtime `raise((:invalid_utf8, b))`    |
| `Str.to_bytes(s)`                              | всегда успешно, возвращает UTF-8-байты |

### C.7 Многострочные строки

Многострочная строка `"""..."""` даёт один токен `STRING` — тот же, что обычный `Str` (§3.5).

1. **Открытие.** `"""` в позиции начала строкового литерала. Остаток физической строки после `"""` — только пробелы, иначе ошибка `text after opening """ must be empty`.
2. **Содержимое.** Следующие физические строки читаются как есть, без offside-обработки и без пропуска пустых строк и комментариев, до первой строки, в которой после ведущих пробелов стоит `"""`.
3. **Закрытие.** Число ведущих пробелов закрывающей строки — общий отступ `k`. Каждая непустая строка содержимого обязана иметь не меньше `k` ведущих пробелов, иначе ошибка `line has less indent than closing """` с `line:col` этой строки; с неё снимаются первые `k` пробелов. Строка пустая или из одних пробелов даёт пустую строку.
4. **Значение.** Строки содержимого после снятия отступа, соединённые через `\n`; перевод строки после открывающих и перед закрывающими `"""` не входит.
5. **Escape и интерполяция** — по §C.1 и §C.2 для `Str`, но построчно: `\(...)` и escape не переходят границу строки содержимого (перенос внутри `\(...)`, допустимый в `Str`, здесь — ошибка незакрытой интерполяции); `"` — литеральный символ.
6. **Продолжение.** Текст после закрывающих `"""` продолжает ту же логическую строку; `NEWLINE`/`INDENT`/`DEDENT` между открывающими и закрывающими `"""` не эмитируются.
7. **Незакрытый литерал** (конец файла до закрывающих `"""`) — ошибка `unclosed triple-quoted string at EOF`; в REPL — запрос продолжения ввода (§11.4).

## D. Offside Algorithm

### D.1 Состояние лексера

```text
indent_stack   : [0]
paren_depth    : 0
stmt_indent    : 0
first_line     : true
prev_token     : none
block_stack    : []
interp_stack   : []
```

**Значения:**

- `indent_stack` — стек активных отступов.
- `paren_depth` — глубина обычных скобок.
- `stmt_indent` — отступ первой строки текущего логического стейтмента.
- `first_line` — признак первой логической строки.
- `prev_token` — предыдущий токен, нужен для `:` и скобочных `NEWLINE`.
- `block_stack` — стек активных offside-конструкций.
- `interp_stack` — стек активных строковых интерполяций.

### D.2 Единицы измерения

**Для offside:**

- отступ — количество ведущих пробелов;
- колонка токена — количество символов слева от токена в физической строке, начиная с 0.

**Для диагностики:**

- `line` начинается с 1;
- `col` начинается с 1.

### D.3 Основной цикл

<!-- Псевдокод алгоритма offside. Не валидный brig-код, помечен как text. -->

```text
for each physical_line:
    if inside_string_or_interpolation:
        handle_string_or_interpolation(physical_line)
        continue

    if is_blank(physical_line) or is_comment_only(physical_line):
        continue

    if paren_depth > 0 and not inside_offside_mini_block():
        if should_emit_bracket_newline(prev_token, peek_first_token(physical_line)):
            emit NEWLINE
        lex_tokens(physical_line)
        update_paren_depth()
        maybe_open_offside_mini_block()
        continue

    indent = leading_spaces(physical_line)
    first_tok = peek_first_token(physical_line)

    if first_tok in CONTINUATION_OPS:
        if indent <= stmt_indent:
            error("continuation line must be indented more than statement")
        lex_tokens(physical_line)
        update_paren_depth()
        continue

    # Новая логическая строка
    if not first_line:
        emit NEWLINE

    if indent > indent_stack.top():
        emit INDENT
        indent_stack.push(indent)
    elif indent < indent_stack.top():
        while indent_stack.top() > indent:
            indent_stack.pop()
            emit DEDENT
        if indent_stack.top() != indent:
            error("inconsistent dedent")

    if not is_clause_keyword_for_current_block(first_tok):
        emit NEWLINE
        stmt_indent = indent
    first_line = false

    lex_tokens(physical_line)
    update_paren_depth()
    maybe_open_block_anchor()
```

### D.4 Продолжение строк

**Continuation-строка** — физическая строка, первый токен которой входит в закрытый список:

```text
|> and or * / ** div rem to == != < > <= >= .. <>
```

**Правила:**

- `NEWLINE` перед такой строкой не эмитируется;
- `INDENT`/`DEDENT` для неё не эмитируются;
- отступ должен быть строго больше `stmt_indent`;
- `stmt_indent` не изменяется.

**Пример:**

```brig
fn main() ->
    x = 1
        * 2
    x
```

### D.5 `NEWLINE` как разделитель внутри скобок

Пока `paren_depth > 0` и нет активного offside-мини-блока:

- `INDENT`/`DEDENT` не эмитируются;
- физические переносы строк могут эмитироваться как `NEWLINE`-разделители элементов.

`NEWLINE` эмитируется, если:

- предыдущий токен может завершать элемент;
- следующий токен может начинать элемент;
- предыдущий токен не является открывающей скобкой;
- предыдущий токен не является запятой;
- следующий токен не является закрывающей скобкой.
- предыдущий токен не является бинарным оператором (`+ - * / ** div rem to == != < > <= >= and or |> <>`);
- следующий токен не является оператором продолжения из §2.2, кроме спреда `..`.

Так длинное выражение переносится внутри скобок: `(a +⏎ b)` и `(xs⏎ |> f)` — одно выражение. Строка с ведущим `-` или `+` начинает новый элемент: `[1⏎ -2]` — `[1, -2]`.

**Пример:**

```brig
fn main() ->
    m = %{
        "a" => 1
        "b" => 2
    }
    m
```

Внутри `%{...}` лексер эмитирует `NEWLINE` между элементами.

### D.6 Offside-блоки внутри скобок

Если внутри скобок встречается одна из конструкций `fn`, `match`, `recv`, `with`, `trap`, `if`, и грамматически ожидается блок, лексер открывает **изолированный offside-мини-блок**.

**Псевдокод:**

```text
open_offside_block(keyword):
    saved_paren_depth = paren_depth
    saved_indent_stack = indent_stack
    saved_stmt_indent = stmt_indent

    base_indent = stmt_indent   # §2.4: отступ первой строки стейтмента,
                                # внутри которого стоят скобки; колонка
                                # keyword не используется (T-124)

    indent_stack = [base_indent]
    paren_depth = 0
    block_stack.push(keyword)
```

**Завершение мини-блока:**

```text
close_offside_block():
    indent_stack = saved_indent_stack
    paren_depth = saved_paren_depth
    stmt_indent = saved_stmt_indent
    block_stack.pop()
```

**Правила:**

- тело блока должно иметь отступ строго больше `base_indent`;
- блок завершается, когда встречается токен с отступом меньше или равным `base_indent`;
- клаузы `else`, `after` могут продолжать конструкцию после `DEDENT`;
- `ensure` **не** является клаузой после `DEDENT`: это `trap_item` внутри блока;
- после завершения тела блока внешний скобочный контекст восстанавливается.

### D.7 Якоря блоков

<!-- FIXED: предыдущая версия содержала противоречивый пример (два
     идентичных блока, первый назван "неправильным", второй "правильным"),
     причём оба некорректны. Заменено на согласованный текст и пример. -->

Для всех блочных конструкций (`fn`, `match`, `recv`, `with`, `if`, `trap`), вне скобок и внутри них (§D.6):

```text
base_indent = stmt_indent   # отступ первой строки логического стейтмента,
                            # содержащего блочную конструкцию
```

Это то же правило, что в §2.4 и §D.6: колонка ключевого слова в строке на якорь не влияет. Оно одинаково для всех блочных конструкций, включая `trap`. Отдельного правила для `trap` в v0.4.7 **нет**: `ensure` — это `trap_item` внутри `INDENT`-блока, и все `trap_item` (включая `ensure`) имеют отступ строго больше `base_indent`.

**Пример (корректный):**

```brig module
fn main() ->
    result = trap
        f1()
        ensure cleanup()
        f2()
    result

# хелперы примера
fn f1() -> 1
fn cleanup() -> ()
fn f2() -> 2
```

Здесь:

- `stmt_indent` строки `result = trap` — 4;
- тело `trap` (`f1`, `ensure cleanup`, `f2`) — на отступе 8 > 4, это корректно;
- `ensure` находится на том же уровне, что и `f1`/`f2`, внутри `INDENT`-блока `trap`.

**Пример (некорректный):** `ensure` **вне** `INDENT`-блока `trap` — синтаксическая ошибка:

```brig invalid "expected expression, got ensure"
fn main() ->
    result = trap
        f1()
    ensure cleanup()
    result
```

`ensure` в колонке 4 (тот же уровень, что `result`) — грамматика v0.4.7 такого не допускает: `ensure` обязан быть `trap_item` внутри `INDENT`-блока `trap`.

### D.8 Клаузы и дополнительный `NEWLINE`

При выходе из блока по `DEDENT` лексер решает, нужен ли дополнительный `NEWLINE`.

Если первый токен после дедента — клауза текущей конструкции, дополнительный `NEWLINE` не эмитируется.

Если первый токен не является клаузой, эмитируется дополнительный `NEWLINE` как разделитель стейтментов или элементов.

| Конструкция | Клаузы          |
| ----------- | --------------- |
| `if`        | `else`          |
| `recv`      | `else`, `after` |
| `with`      | `else`          |
| `fn`        | нет             |
| `match`     | нет             |
| `trap`      | нет             |

**v0.4.7:** `trap` больше не имеет клаузы после `DEDENT` — `ensure` находится внутри блока.

**Пример перехода к клаузе:**

```text
body NEWLINE DEDENT else
```

**Пример перехода к следующему стейтменту:**

```text
body NEWLINE DEDENT NEWLINE stmt
```

### D.9 EOF

На конце файла лексер обязан:

1. Если активна интерполяция — ошибка `unterminated interpolation`.
2. Если активен строковый/байтовый/regex-литерал — ошибка `unterminated literal`.
3. Если `paren_depth > 0` — ошибка `unclosed delimiter`.
4. Если есть незавершённая логическая строка — эмитировать `NEWLINE`.
5. Эмитировать `DEDENT` до уровня `0`.
6. Эмитировать `EOF`.

### D.10 Примеры потоков токенов

#### Простой блок

```brig
fn main() ->
    x = 1
    x
```

```text
fn LOWER_IDENT(main) ( ) -> NEWLINE INDENT
LOWER_IDENT(x) = INT(1) NEWLINE
LOWER_IDENT(x) NEWLINE DEDENT EOF
```

#### Продолжение строки

```brig
fn main() ->
    x = 1
        * 2
    x
```

```text
fn LOWER_IDENT(main) ( ) -> NEWLINE INDENT
LOWER_IDENT(x) = INT(1) * INT(2) NEWLINE
LOWER_IDENT(x) NEWLINE DEDENT EOF
```

#### `if` с `else`

```text
fn main() ->
    if ready
        start()
    else
        wait()
```

```text
fn LOWER_IDENT(main) ( ) -> NEWLINE INDENT
if LOWER_IDENT(ready) NEWLINE INDENT
LOWER_IDENT(start) ( ) NEWLINE DEDENT
else NEWLINE INDENT
LOWER_IDENT(wait) ( ) NEWLINE DEDENT
NEWLINE DEDENT EOF
```

#### `trap` с `ensure` (v0.4.7)

```text
fn main() ->
    result = trap
        f1()
        ensure close_f1()
        f2()
    result
```

```text
fn LOWER_IDENT(main) ( ) -> NEWLINE INDENT
LOWER_IDENT(result) = trap NEWLINE INDENT
LOWER_IDENT(f1) ( ) NEWLINE
ensure LOWER_IDENT(close_f1) ( ) NEWLINE
LOWER_IDENT(f2) ( ) NEWLINE DEDENT
LOWER_IDENT(result) NEWLINE DEDENT EOF
```

Ключевые изменения: `ensure` эмитируется внутри INDENT-блока `trap` (на отступе 8), а не после DEDENT. Никаких специальных правил для якоря `trap` не требуется — `base_indent` = `stmt_indent` строки с `result`.

## E. Diagnostics Format

### E.1 Формат

```text
error: <file>:<line>:<col>: <message>
info: <file>:<line>:<col>: <message>
```

### E.2 Нумерация

- `line` начинается с 1.
- `col` начинается с 1.
- `col` считается в Unicode code points.

### E.3 Каналы вывода

- `error` и `info` пишутся в `stderr`.
- `info` не влияет на exit code.
- Наличие хотя бы одного `error` даёт ненулевой exit code.

### E.4 Примеры

```text
error: examples/demo.brig:3:5: unexpected token "%"
error: examples/demo.brig:7:10: unterminated interpolation
info: examples/demo.brig:12:1: `len` shadows prelude function
```

## F. Validation Stages

Нормативное распределение проверок по этапам реализации.

### F.1 Лексер

Ошибки лексера:

- некорректный UTF-8 в исходнике;
- табуляция в отступе;
- незакрытая строка;
- незакрытая интерполяция;
- незакрытый `Bytes`/`Regex`/`Decimal`;
- недопустимые escape-последовательности;
- `\u{}`;
- `\u{D800}`;
- `\u{110000}`;
- `1__0`, `1_`, `_1`;
- `1.`, `.5`, `1e`;
- одиночный `%`;
- `x?y`;
- недопустимые идентификаторы;
- многострочная строка `"""` (§C.7): текст после открывающих `"""`; строка содержимого с отступом меньше, чем у закрывающих `"""`; незакрытый литерал.

### F.2 Парсер

Ошибки парсинга:

- нарушение грамматики;
- блочное тело у короткой лямбды (`x ->` и `(a, b) ->` — только одна строка; блок — в `fn`);
- `..` без операнда в `args`;
- цепочки сравнений: `a == b == c`;
- цепочки `to`: `1 to 2 to 3`;
- убывающий литеральный range: `1 to 0`;
- top-level `let` в режиме `module`;
- неверные однострочные формы;
- неверное использование `else`/`after`;
- некорректная структура `type_decl`;
- **v0.4.7:** `ensure` вне блока `trap` (ensure может появляться только как `trap_item` внутри `INDENT`-блока `trap`).

### F.3 Контекстный анализ

Ошибки после парсинга:

- `trap` в позиции аргумента или элемента литерала;
- `..` не в конце списка/паттерна;
- несколько `..` в одной коллекции;
- `..` в `Map`/record-паттернах;
- захват ключа в `map_pattern`;
- variadic-параметр не последний;
- несколько variadic-параметров;
- локальные `fn` не в начале тела;
- rebinding внутри одной лексической области, в том числе имя, повторённое в одном паттерне (§5.1);
- обращение к именованному wildcard `_name` (§1.2);
- pipe-запрет акторных примитивов;
- **неизвестное имя**: вызов или ссылка на имя, которое не связано в области, не является функцией своего модуля, прелюдии или видимого модуля, либо не имеет функции с такой арностью (с учётом variadic): `error: main.brig:1:14: undefined function nope/1`; для `M.f` — с именем модуля: `undefined function Util.nope/0`. Вызов значения-функции из переменной не проверяется. В REPL неизвестное имя остаётся ошибкой рантайма: строка видит имена предыдущих строк (§11.4);
- вызов или ссылка на приватную функцию другого модуля (§11.2);
- клозы одной функции с `pub` и без (§11.2);
- `import`/`alias` отсутствующего модуля, расхождение `module X` с путём импортируемого файла, совпадение локальных имён модулей (§11.1);
- shadowing прелюдии и встроенных имён как `info`.

### F.4 Рантайм

Ошибки рантайма:

- непокрытый `match`;
- непокрытый `recv`;
- `function_clause`;
- `case_clause`;
- `no_field` (чтение отсутствующего поля записи; поле не из типа при record update);
- `badmatch` (несовпадение паттерна в `pattern = expr`);
- деление на ноль;
- индекс вне границ;
- `range_error` для вычисляемых range;
- `invalid_utf8` в `Bytes.to_str`;
- переполнение почтового ящика и связанные акторные ошибки.

## G. `cmd/check-examples` Specification

### G.1 Цель

Прогнать все примеры языка из документации через парсер и убедиться, что они ведут себя согласно своей метке.

Скрипт реализует принцип: примеры в документации должны быть валидными относительно `brig.ebnf`.

### G.2 Имя

```text
cmd/check-examples
```

### G.3 Вход

- Один или несколько markdown-файлов.
- `brig.ebnf` или реализованный по нему парсер.

### G.4 Извлечение примеров

Все fenced-блоки с языком `brig` считаются примерами.

**Поддерживаемые метки:**

````text
```brig module
```brig repl
```brig expr
```brig stmt
```brig invalid
```brig invalid "expected expression"
```brig pending(T-NNN)
```brig module pending(T-NNN)
````

Блоки `module`, `stmt` и `expr` проходят парсер, контекстный анализ (§F.3) и компилятор. Ошибка на любом этапе — провал с `line:col` в markdown-файле.

`invalid "текст"` — необязательная ожидаемая подстрока ошибки: блок обязан упасть именно с ней, иначе провал.

`pending(T-NNN)` — блок ждёт задачу T-NNN (нереализованная фича или правка примера). Такой блок обязан пройти парсер и round-trip форматирования, но **не** компилироваться: падать он может только в контекстном анализе (§F.3) или компиляторе. Ошибка парсера — провал; если блок компилируется — провал «снять pending». T-NNN обязан существовать в `tasks/`. Режим задаётся как обычно (`brig pending(T-NNN)` — эвристика, `brig module pending(T-NNN)` — явно). Блок, который падает из-за бага реализации, помечается не `pending`, а заводится issue.

Блок без метки обрабатывается только если эвристика однозначна. Если эвристика неоднозначна, скрипт обязан выдать ошибку и потребовать явную метку.

Для финальной документации рекомендуется использовать только явные метки.

**v0.4.7:** метка парсится через `^(module|repl|expr|stmt|invalid)\b` — регексп с границей слова, чтобы `invalid_foo` не матчился как `invalid`.

### G.5 Режимы

#### `module`

Тело блока парсится как `program`.

Разрешены только декларации верхнего уровня: `module`, `import`, `alias`, `type`, `fn`. Top-level `let` и выражения запрещены.

```brig module
fn main() ->
    1
```

#### `repl`

Каждая строка, начинающаяся с `>`, считается вводом. Префикс `>` отбрасывается. Строка без `>` сразу после ввода — ожидаемый ответ на этот ввод.

```brig repl
> x = 5
> f = () -> x
> x = 10
> f()
5
> x + 1
11
```

**Обработка:**

- строки ввода исполняются по порядку в одной REPL-сессии (§11.4); повторное связывание имени в разных строках — shadowing, не ошибка;
- ответ разбирается как выражение, вычисляется в отдельной чистой сессии (имена блока в нём не видны) и сравнивается с результатом ввода через `==`, а не как строка: ответ `6.0` на `2 * 3` верен;
- ответ `raise <терм>` — ввод обязан завершиться непойманным raise, значение которого `==` терму: `raise (:not_found, 42)`;
- ввод без ответа (обычно связывание) исполняется, но не сравнивается;
- провал — ошибка разбора, контекстного анализа или компиляции ввода, неожиданный raise, несовпадение с ответом (с ожидаемым и фактическим значением), больше одной строки ответа или ответ без ввода.

#### `expr`

Тело блока трактуется как одно выражение. Скрипт оборачивает его:

<!-- FIXED: блок `fn main() -> <expr>` — мета-пример обёртки, не валидный
     brig. Метка была `brig`, что давало parse error 2:18: expected
     expression, got <. Понижено до `text`. -->

```text
fn main() -> <expr>
```

```brig expr
1 to 10 |> list
```

Обёртка:

```brig
fn main() -> 1 to 10 |> list
```

#### `stmt`

Тело блока трактуется как последовательность стейтментов. Скрипт оборачивает его:

<!-- FIXED: блок `fn main() -> \n <stmt_list>` — мета-пример обёртки,
     не валидный brig. Метка была `brig`, что давало parse error
     3:9: expected expression, got <. Понижено до `text`. -->

```text
fn main() ->
    <stmt_list>
```

```brig stmt
x = 1
y = 2
x + y
```

Обёртка:

```brig
fn main() ->
    x = 1
    y = 2
    x + y
```

#### `invalid`

Блок обязан не парситься. Если блок с меткой `invalid` успешно парсится, `cmd/check-examples` завершается ошибкой.

```brig invalid "expected expression, got ]"
fn main() ->
    x = [1, ..]
    x
```

### G.6 Обработка псевдокода

Блоки, содержащие многоточия `...`, псевдокод или намеренно неполные конструкции, не должны помечаться как `brig`. Для них следует использовать:

````text
```text
```pseudo
```brig invalid
````

### G.7 Выход скрипта

**Коды завершения:**

- `0` — все блоки прошли проверку согласно своим меткам.
- `1` — хотя бы один блок не прошёл проверку.

**Формат отчёта:**

```text
error: <file>:<line>:<col>: <message>
info: <file>:<line>:<col>: <message>
```

`info` не влияет на код завершения.

### G.8 Дополнительные проверки

Помимо парсинга, скрипт может выполнять упрощённые контекстные проверки на уровне AST.

**Обязательные проверки для этапа документации:**

1. В `module`-блоках нет top-level `let` или выражений.
2. В `invalid`-блоках действительно возникает ошибка.
3. В примерах нет блочного тела у короткой лямбды (стрелка — одна строка; блок — только `fn`).
4. В примерах нет `Result[...]` в позиции типа.
5. В примерах нет `f(..)` без операнда.
6. В примерах нет `..` в `Map`/record-паттернах.
7. В примерах нет `trap` в позиции аргумента или элемента литерала.

Эти проверки могут быть реализованы как отдельный линт-слой поверх парсера.

**v0.4.7:** дополнительно `check-examples` выполняет sanity round-trip: `parse → Format → parse ≡ parse` для `module`/`expr`/`stmt` блоков. Несовпадение — FAIL.
