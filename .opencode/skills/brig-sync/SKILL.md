# Синхронизация скиллов с источниками

Скиллы `.opencode/skills/brig-*` — **производные** документы. У них есть
**источники истины**, и они обязаны отражать текущий контракт. Когда
источник меняется, скиллы, которые на него ссылаются, надо обновить в
том же PR. Этот скилл описывает **как найти** затронутые скиллы и **в каком
порядке** вносить правки — без жёстко зашитой таблицы «секция → скилл»,
которая неизбежно устаревает.

## Конфигурация (единственное место с конкретными путями)

Если меняется структура репозитория — правится **только этот раздел**,
остальной скилл остаётся общим.

```
Источники истины:
  01-language-design.md            §1–§16, принципы #1–#13 (нормативный дизайн)
  02.language-formalization.md     A1–A6, сводка правок (Трек A)
  brig.ebnf                        исполнительная грамматика (A1)

Производные:
  .opencode/skills/brig-*          скиллы-потребители
  docs/architecture.md             обзор слоёв
  internal/**                      код (свои скиллы, не здесь)
  cmd/**, tools/**                 CLI-тулы (свои скиллы)

Стабильные якоря (на них ссылаются скиллы, НЕ на номера строк):
  §X.Y                             секция дизайн-документа
  A#.#                             подраздел Трека A (A1–A6)
  КР-NNN, СУ-NNN, Р-NNN, П-NNN     аудит-находки Трека A
  B#, N#, M-###                    прочие находки / принципы
  #N                               основополагающий принцип
```

## Когда применять / не применять

**Применять** (любое из):

- правка `01-language-design.md`, `02.language-formalization.md`, `brig.ebnf`;
- смена версии (`v0.4.x` → следующая);
- добавление/закрытие аудит-находки (`КР-*`, `СУ-*`, `Р-*`, `П-*`, `B*`, `N*`, `M-*`);
- переименование/перенос файла-источника;
- правка самого скилла, если он ссылается на изменившийся источник;
- добавление нового скилла или удаление существующего.

**Не применять:** правки кода под спецификацию (свои скиллы:
`brig-lexer`, `brig-parser`, ...); разметка fenced-блоков (`brig-docs`);
тесты (`brig-test`). Здесь — только синхронизация скиллов с источниками.

## Инварианты

Это критично. Ломать нельзя без обновления этого скилла.

1. **Скилл не источник истины.** При расхождении прав источник. Если в
   скилле зафиксировано **решение о реализации** (не спецификация) — оно
   остаётся, но помечается как реализационное.
2. **Правка источника и синхронизация скиллов — один PR.** Источник,
   закоммиченный без синхронизации, порождает рассинхрон: агент (или
   разработчик) читает скилл и действует по устаревшему контракту.
3. **Якоря стабильны, номера строк — нет.** В скиллах только `§X.Y`,
   `A#.#`, `КР-NNN`, `B#`, `#N`. Ссылки вида «см. файл X» без якоря и
   `L1234` запрещены — они устаревают молча.
4. **Порядок правок фиксирован** (см. ниже). Нарушение = рассинхрон кода
   и скиллов, который ловится не сразу, а через несколько PR.
5. **Смена версии — триггер полного сканирования.** Пройти по **всем**
   скиллам, даже если правка кажется точечной.
6. **Переименование файла-источника — синхронизация во всех скиллах.**
   Имя файла — такой же контракт, как номер секции. Обязательный
   `rg`-проход по старому имени.
7. **Аудит-находка живёт в скилле, пока жива в источнике.** Закрыли в
   источнике — сняли/обновили статус во всех скиллах, которые её
   упоминают.
8. **Скилл обновляется целиком: инвариант → пример → проверка.**
   Расхождение между разделами одного скилла — баг скилла, не мелочь.
9. **Скиллы самодокументируют зависимости.** Каждый скилл в
   `description:` и/или в разделе `## Ссылки` перечисляет якоря, от
   которых зависит. Это то, что делает возможным обнаружение без
   таблицы. При добавлении скилла — обязательно заполнить.
10. **Дублирование спецификации в скилле — запрещено.** Скилл держит
    **инварианты и грабли**, а не пересказ. Детали — ссылкой на якорь.

## Как определить, что синхронизировать (процедура обнаружения)

Таблицы «секция → скилл» нет специально: она устаревает. Вместо этого —
три шага, работающие для любого изменения.

### Шаг 1. Собрать затронутые якоря

Из правки источника выписать **все** якоря, которых она касается:
`§5.0`, `A3.2`, `КР-003`, `#11`, ... Если правка меняет имя файла-источника
— добавить старое и новое имя в список «якорей» (для `rg`).

Пример: правка §5.0 (приоритеты) может задеть `§5.0`, `§5.4` (pipe),
`#11` (TCO-приоритеты), `B2` (`fn -> expr`).

### Шаг 2. Найти скиллы, которые на них ссылаются

```sh
# по конкретному якорю
rg -l '§5\.0' .opencode/skills/

# по нескольким сразу
rg -l '§5\.0|A3\.2|КР-003|#11' .opencode/skills/

# по старому имени файла (после переименования)
rg -l '01\.1-brig-formalization' .opencode/skills/
```

Экранируйте `.` в `§X.Y` — иначе `§5.0` матчит `§5x0`. Регулярки
безопаснее писать как `rg -F '§5.0'` для точечных якорей.

### Шаг 3. Прочитать каждый найденный скилл целиком

`rg` находит упоминания, но не показывает, **что именно** устарело.
Открыть скилл, прочитать разделы «Инварианты», «Пример», «Частые ошибки»,
«Ссылки» — они должны быть согласованы между собой и с новым источником.
Только после этого править.

Если скилл ссылается на затронутый якорь, но **не** должен меняться
(например, упоминает его в историческом контексте) — это тоже результат:
явно отметить, почему не меняется.

## Порядок правок (must follow)

```
1. Источник (дизайн-документ, §16)      ← нормативный
2. brig.ebnf                             ← регенерация из §16 (A1)
3. Код (парсер/лексер/...)               ← по EBNF (A6)
4. Скиллы brig-*                         ← ЭТОТ ШАГ
5. Тесты / check-examples / гейты        ← принцип #10
6. Коммит
```

Для чисто семантической правки (без грамматики) шаги 2–3 пропускаются,
шаг 4 — **всегда**.

При переименовании файла-источника шаги 1–3 — это правка путей и ссылок,
шаг 4 — `rg`-проход по скиллам, шаг 5 — гейты.

## Рецепты по типу изменения

### А. Правка секции дизайна (`§X.Y`)

1. Пометить правку в источнике (`⚠`).
2. Собрать затронутые якоря (шаг 1 процедуры).
3. `rg` по скиллам (шаг 2), прочитать найденные (шаг 3).
4. Обновить разделы «Инварианты» / «Пример» / «Частые ошибки» / «Ссылки».
5. Прогнать гейты (см. «Проверка»).
6. Коммит: `docs(<scope>): <суть>` + `docs(skills): sync <skill> with §X.Y`.

### Б. Правка `brig.ebnf`

Изменился EBNF → три скилла-потребителя обязательно: `brig-parser`,
`brig-ast`, `brig-docs`. Плюс `brig-test`, если менялись примеры.
Порядок — общий (источник → EBNF → код → скиллы → тесты).

### В. Смена версии (`vX.Y.Z` → следующая)

1. Открыть сводку правок в `02.language-formalization.md` («Сводка
   применённых правок»).
2. Для **каждой** правки из сводки — `rg` по её коду (`КР-001`, `СУ-003`,
   ...) во всех скиллах.
3. Проверить **все** скиллы, не только найденные: точечная правка могла
   задеть смежную секцию, на которую ссылается другой скилл.
4. Для закрытых находок — снять/обновить статус во всех упоминаниях.
5. Обновить версию в шапке дизайн-документа и в ссылках на версию в
   скиллах (если есть).

### Г. Переименование/перенос файла-источника

Пример: `01.1-brig-formalization.md` → `02.language-formalization.md`
(или переезд в `docs/`).

```sh
# 0. Чистое рабочее дерево
git status

# 1. Переименовать с сохранением истории
git mv 01.1-brig-formalization.md 02.language-formalization.md

# 2. Обновить ссылки в дизайн-документах
rg -l '01\.1-brig-formalization' docs/ Makefile .github tools/
# отредактировать найденное

# 3. Обновить brig.ebnf (если упоминается в комментарии)

# 4. Обновить скиллы — ЭТОТ ШАГ ЗАБЫВАЮТ ЧАЩЕ ВСЕГО
rg -l '01\.1-brig-formalization' .opencode/skills/
# отредактировать КАЖДЫЙ найденный скилл

# 5. Убедиться, что старого имени нигде нет
rg -n '01\.1-brig-formalization' .   # должно быть пусто

# 6. Гейты
make check-examples && make ebnf-check

# 7. Отдельный коммит
git commit -am "docs(skills): rename 01.1-brig-formalization to 02.language-formalization"
```

**Почему отдельный коммит:** массовое переименование в скиллах — отдельное
событие. Смешивать с содержательной правкой нельзя: ревьюер не отличит
«переименовали» от «поменяли контракт», а `git log --follow` теряет историю.

### Д. Добавление/закрытие аудит-находки

1. В источнике — добавить/закрыть с описанием (сводка правок).
2. `rg` по коду находки во всех скиллах.
3. Для каждого найденного — обновить раздел, где она упомянута:
    - новая — добавить в «Инварианты» / «Частые ошибки» **только** тех
      скиллов, чей контракт она меняет;
    - закрытая — снять со статуса «действующая» (удалить или пометить
      как закрытую, если скилл ведёт историю).
4. Обновить `## Ссылки` в затронутых скиллах.
5. Гейты.

### Е. Добавление нового скилла

1. Создать `.opencode/skills/<name>/SKILL.md`.
2. В `description:` — список якорей-зависимостей (формат:
   `Spec: §X, A#.# in <file>`).
3. Заполнить раздел `## Ссылки` — те же якоря + смежные скиллы.
4. Проверить, что новый скилл не дублирует спецификацию (инвариант 10).
5. `rg` по его якорям — не пересекается ли с существующими скиллами
   так, что один из них устарел.
6. Если скилл вводит новый тип якоря — обновить **этот** скилл
   (раздел «Конфигурация»).

### Ж. Удаление скилла

1. `rg` по имени скилла во всех остальных скиллах — снять ссылки.
2. `rg` по его якорям — кто ещё их покрывает? Если никто, а якоря
   важные — перенести контракт в смежный скилл или в отдельный.
3. Удалить директорию.
4. Если скилл был единственным потребителем каких-то якорей — обновить
   этот скилл (раздел «Конфигурация»).

## Проверка

```sh
# По затронутым якорям — найти скиллы
rg -n '§5\.0|A3\.2|КР-003|#11' .opencode/skills/

# По именам файлов-источников — найти скиллы
rg -n '02\.language-formalization|01-language-design|brig\.ebnf' .opencode/skills/

# Устаревшие упоминания после переименования (должно быть пусто)
rg -n '01\.1-brig-formalization' .   # ожидается пусто

# Согласованность внутри каждого затронутого скилла:
#   «Инварианты» ↔ «Пример» ↔ «Частые ошибки» ↔ «Ссылки»
#   (читается глазами, не автоматизируется)

# Гейты (ловят рассинхрон кода, не скиллов — но полезны)
make check-examples
make ebnf-check
go test ./... -race
```

Чек-лист перед коммитом:

- [ ] Собраны затронутые якоря (шаг 1 процедуры).
- [ ] `rg` по скиллам выполнен; найденные скиллы прочитаны целиком.
- [ ] В каждом затронутом скилле: инвариант, пример и «Частые ошибки»
      согласованы между собой и с источником.
- [ ] Ссылки — на якоря (`§X.Y`, `A#.#`, `КР-NNN`), не на номера строк.
- [ ] Имя файла-источника совпадает во **всех** скиллах
      (`rg` не находит старых имён).
- [ ] Закрытые находки не висят как «действующие».
- [ ] Для смены версии: пройдены **все** скиллы, не только очевидные.
- [ ] Порядок правок соблюдён (источник → EBNF → код → скиллы → тесты).
- [ ] Синхронизация скиллов — отдельный коммит или явный раздел в PR.

## Частые ошибки

- **Правка источника без синхронизации скиллов** — рассинхрон контракта.
  Симптом: скилл утверждает одно, код делает другое; агент действует по
  скиллу. Ловится `rg` по якорю.
- **Обновление только «очевидного» скилла.** Симптом: `§5.0` правился,
  `brig-parser` обновлён, а `brig-docs`/`brig-test` — нет. Причина —
  reliance на память вместо процедуры обнаружения. Всегда шаг 2 и 3.
- **Ссылки на номера строк** вместо якорей. Симптом: после правки docs
  скилл ссылается на `L1234`, где теперь совсем другое.
- **Скилл дублирует спецификацию** вместо ссылки. Симптом: правка
  источника не находит отражения в скилле — «казалось, это деталь».
  Правило: в скилле — инварианты и грабли, не пересказ.
- **Закрытая находка осталась «действующей»** в скилле. Симптом: скилл
  запрещает то, что давно разрешено.
- **Смена версии без полного сканирования.** Симптом: точечная правка
  «не заметила» скилл, ссылающийся на смежную секцию.
- **`brig.ebnf` правится вручную, минуя §16** — ломает A1 и расходится
  со скиллами. Симптом: `make ebnf-check` красный на следующем релизе.
- **Переименование файла-источника не прошло по всем скиллам.** Симптом:
  `rg '01\.1-brig-formalization' .` находит висячие ссылки в скиллах,
  которые «никто не читал много месяцев».
- **Переименование одним коммитом с содержательной правкой.** Симптом:
  `git log --follow` не отслеживает историю; на ревью непонятно, файл
  переехал или изменился.
- **Правка скиллов до правки источников.** Симптом: скилл «уехал»
  вперёд, потом источник «догнал» с другим решением; diff скилла
  переписывается. Порядок — источник → EBNF → код → скиллы → тесты.
- **Новый скилл без `description:` с якорями.** Симптом: процедура
  обнаружения его не находит; следующий релиз его не синхронизирует.
  Заполнять `description:` и `## Ссылки` при создании.
