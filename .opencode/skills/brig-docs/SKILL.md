# Документация Brig

Источники истины: `01-language-design.md` (дизайн, §1–§16) и
`01.1-brig-formalization.md` (Трек A: A1–A6). **§16 — нормативный источник
грамматики; `brig.ebnf` — исполнительный** (A1). Этот скилл описывает
порядок правок, инварианты версионирования и грабли синхронизации — не
дублирует содержание §16.

## Когда применять / не применять

**Применять:** правки `01-language-design.md`, `01.1-brig-formalization.md`,
`brig.ebnf`, любые fenced-блоки ` ```brig ` в документации, версионирование
дизайна, `make check-examples` / `make ebnf-check`.

**Не применять:** правки самого парсера, `tools/check-examples` (код), AST —
для этого свои скиллы (`brig-ast`, `brig-cli`, ...). Здесь docs — только
потребитель их результатов.

## Инварианты

Это критично. Ломать нельзя без обновления спецификации.

1. **§16 — нормативный источник грамматики; `brig.ebnf` — исполнительный
   (A1).** При расхождении правится **§16**, затем регенерируется `brig.ebnf`.
   Обратное направление (правка EBNF → §16) — ошибка.
2. **Порядок правок, влияющих на грамматику (A6):**
   §16 → регенерация `brig.ebnf` → парсер → `tools/check-examples`.
   Нарушение порядка оставляет парсер и грамматику в рассинхроне.
3. **Каждая версия дизайна — `vX.Y.Z`; документ заменяет предыдущую версию
   целиком.** Diff-режим («только изменения») не используется. В сводке —
   таблица правок (тип: КР-NNN, СУ-NNN, Р-NNN, П-NNN, Bx, Nx, M-NNN).
4. **Правка помечается `⚠` рядом с изменённым местом.** Без `⚠` правка
   считается незадокументированной.
5. **Открытых вопросов в «консолидированном» документе быть не должно.**
   Блокеры и вопросы закрываются в отдельном Треке.
6. **Все fenced-блоки ` ```brig ` обязаны парситься (принцип #10).**
   Режим указывается меткой (A2): `module`, `repl`, `expr`, `stmt`.
7. **`brig.ebnf` не редактируется вручную «по вкусу»** — только регенерацией
   из §16. Ручные правки неизбежно расходятся с §16.

## Примеры: правила разметки

- **Фрагменты без `fn main`** помечать `stmt` или `expr` — иначе
  `check-examples` не знает, как обернуть, и не сможет проверить (A2).
- **Семантические примеры** вида `Ok(x) ≡ (:ok, x)` — только в комментариях;
  `check-examples` это проверяет.
- **REPL-вывод** в ` ```brig repl ` (`6`, `11`) — строки **без `=`**, без
  оператора, не ключевое слово. Отбрасываются эвристикой; если строка не
  подходит под эвристику — это ошибка разметки, а не «пропущенный вывод».
- **Неоднозначный блок без метки** — предупреждение `check-examples`, не
  ошибка. Но в CI должно быть чисто → метку ставить обязательно.

## EBNF: feature-flag и неоднозначности

- **Feature-flag** `regex_lit` / `decimal_lit` — статус Should (Р-008).
  В грамматике помечается комментарием `(* статус: Should *)` + парсер
  отдаёт `feature not implemented`.
- **Неоднозначности грамматики** требуют комментария **прямо в EBNF** (A6):
  - `(x)` группировка vs `(x,)` 1-кортеж
  - `(Int)` группировка типа vs `(Int,)` 1-кортеж типа
  - `record_literal` vs `type_body`
      Комментарий в §16 без дублирования в EBNF — не считается исправленным;
      парсер читает EBNF, а не §16.

## Пример: правка, влияющая на грамматику

Правильная последовательность:

```sh
# 1. Правим §16 (нормативный источник) и помечаем ⚠
$EDITOR docs/01-language-design.md

# 2. Регенерируем brig.ebnf из §16 (скрипт из Трека A)
make ebnf-gen

# 3. Регенерируем/правим парсер (если есть генерация)
make parser-gen

# 4. Проверяем, что примеры всё ещё парсятся
make check-examples

# 5. Проверяем соответствие EBNF ↔ §16
make ebnf-check

# 6. Только теперь — коммит
git add docs/ internal/parser/
git commit -m "docs(§16): ..."
```

`````

Порядок нарушать нельзя: если закоммитить §16 без `brig.ebnf` — парсер
уедет вперёд, а `make ebnf-check` в CI упадёт через час, когда автор уже
забыл контекст.

## Чек-лист перед коммитом

````sh
make check-examples   # все fenced-блоки ```brig парсятся (A2)
make ebnf-check       # brig.ebnf соответствует §16
make test             # парсер/VM не сломались
`````

- [ ] Версия проставлена: `v0.4.x` → следующий номер.
- [ ] Правки помечены `⚠` и внесены в таблицу сводки.
- [ ] Для грамматических правок: §16 → `brig.ebnf` → парсер → examples.
- [ ] Открытых вопросов не осталось; блокеры вынесены в Трек.
- [ ] Fenced-блоки ` ```brig ` имеют метку (`module`/`repl`/`expr`/`stmt`).
- [ ] Subject коммита — на английском, conventional (см. `git-conventional`).

## Частые ошибки

- **Правка §16 без регенерации `brig.ebnf`** — парсер и грамматика
  расходятся. Симптом: парсер принимает то, что §16 запрещает (или наоборот);
  ловится `make ebnf-check`.
- **Правка `brig.ebnf` вручную вместо регенерации** — дрейф от §16.
  Симптом: следующий `make ebnf-gen` затирает ручные правки, `git diff`
  показывает откат. Никогда не коммитить EBNF без §16.
- **Fenced-блок ` ```brig ` без метки и неоднозначен** — предупреждение
  `check-examples`. Симптом: CI «зелёный», но с warning'ами; блок мог
  парситься не так, как задумано. Ставить явную метку.
- **Открытый вопрос в «консолидированном» документе** — нарушает инвариант
  версионирования. Симптом: ревьюер задаёт вопрос, ответа в документе нет.
  Выносить в отдельный Трек.
- **Русский subject коммита** — нарушает `git-conventional`. Симптом:
  CI-линтер коммитов падает на первом же коммите. См. скилл
  `git-conventional`.
- **Семантический пример `Ok(x) ≡ ...` в fenced-блоке** вместо комментария —
  `check-examples` попытается распарсить и упадёт. Симптом: ошибка парсинга
  в блоке, который «просто иллюстрация».
